# 用户标签推送功能文档

**状态：** 独立用户标签服务设计；运行时只依赖 foundation 组件，不依赖多 Agent / Chat / Workflow
**更新日期：** 2026-05-20
**范围：** Tweet Catcher 推文监听、标签匹配、Centrifugo 标签维度推送的功能设计；不包含前端订阅实现，不保留多 Agent 编排入口。

## 目标

用户选择国家、球员等标签后，服务端持续监听 Tweet Catcher 推文流。每条推文进入系统后，服务端用当前标签目录构造匹配规则，调用 `/internal/tag/match-text` 判断推文是否命中标签。命中后，将完整推文按标签维度推送到 Centrifugo，例如 `tag:Ronaldo`。如果一条推文命中多个标签，需要分别向多个标签频道发送。

## 配置要求

所有运行时配置仍只允许写在 `config/odd-agent.yaml`，仓库提交 `config/odd-agent.example.yaml` 模板。当前服务只保留：

- `server`：HTTP 服务。
- `logger`：结构化日志配置，对应 Foundation Logger 组件。
- `db`：用户标签与推文匹配存储使用的 PostgreSQL 配置，对应 Foundation DB 组件。
- `redis` / `memory.embedding-db`：作为独立基础能力保留，用户标签主链路不强制初始化。
- `centrifugo`：共享 Centrifugo HTTP publish 配置，可被后续功能复用。
- `tweet_catcher`：共享 Tweet Catcher WebSocket 配置，可被后续功能复用。
- `user_tag.snapshot_refresh_interval_ms`：active tag 快照刷新周期。
- `user_tag.llm`：用户标签 match-text 专用 OpenAI-compatible LLM 配置。

删除范围：`supervisor_agent`、`market_copilot_agent`、`jobs`、旧 `vector_store` 顶层配置、公开 `/api/ai/**` Chat/Session/Push Preference 路由、Agent Registry、Workflow、应用层多 Agent Memory 适配均不再属于当前运行时。

## 初始化边界

运行时入口 `src/init.ts` 是唯一组合根，但 user-tag 相关依赖必须由独立初始化方法装配，避免全局 init 继续变成长方法。

`initApp()` 只负责：

- 加载并校验 `config/odd-agent.yaml`。
- 初始化 `logger` 与 `db` 对应的 Foundation 组件。
- 调用 user-tag 初始化方法。
- 创建 HTTP server，并把生命周期 hook 接到 user-tag runtime。

`initUserTagRuntime()` 负责：

- 按 `user_tag.llm` 创建独立 `OpenAiLlmComponent`。不同功能、不同 `base_url` 或不同 `model` 必须创建不同 LLM 对象，不能共享隐式全局实例。
- 创建 `PostgresTagRepository`、`TagMatchService`、`TagSnapshotCache`、`TweetTagPushService`。
- 使用共享顶层 `centrifugo` 初始化 Centrifugo publisher。
- 使用共享顶层 `tweet_catcher` 初始化 Tweet Catcher listener。
- 对外返回 HTTP 需要注入的 `tagRepository`、`tagMatchService`，以及 `start()` / `close()` 生命周期方法。

### Centrifugo 服务端推送配置

使用 `centrifugo` section，provider 固定为 `centrifugo`。

必须包含：

- `centrifugo.endpoint`：Centrifugo HTTP API 地址，服务端推送时调用。
- `centrifugo.api_key_secret_ref`：Centrifugo API key 的受控 secret 引用。
- `centrifugo.channel_template_tag`：标签频道模板，当前默认 `tag:{tag_name}`。

标签频道命名规则：

- `tag_name` 优先取 `tags.lang_metadata.en`。
- 频道名必须做安全归一化：去除首尾空白，将连续空白折叠为 `_`，只允许字母、数字、`_`、`-`，其他字符按实现约定转义或替换。
- 示例：`Ronaldo` -> `tag:Ronaldo`，`Son Heung-min` -> `tag:Son_Heung-min`。

### Tweet Catcher 监听配置

使用 `tweet_catcher` section。

必须包含：

- `tweet_catcher.websocket_endpoint`：Tweet Catcher Monitor Pro WebSocket 地址。
- `tweet_catcher.api_key_secret_ref`：Tweet Catcher API key 的受控 secret 引用。
- `tweet_catcher.heartbeat_interval_ms`：心跳检测间隔。
- `tweet_catcher.reconnect_initial_delay_ms`：断线后的初始重连退避。
- `tweet_catcher.reconnect_max_delay_ms`：断线后的最大重连退避。

监听任务必须在服务端启动时注册，并跟随服务生命周期关闭。

### Tweet Catcher 协议处理

当前 listener 按协议消息类型分流：

- `op=10`：hello，发送 identify。
- `op=4` 或 `type=ready`：鉴权完成，进入 ready 状态。
- `op=1` / `op=11` / `type=ping|pong|heartbeat`：心跳控制消息，不进入业务链路。
- `op=3`：鉴权失败，只记录 `tweet_catcher.auth_failed` 并停止重连，不得当成推文处理。
- `op=0`：真实 monitor event，才进入 `tweet_catcher.message_received` 和后续用户标签匹配链路。

已通过真实服务验证：有效 Tweet Catcher key 可进入 `tweet_catcher.ready`；真实 `op=0` 推文会触发 LLM 匹配。

## 启动监听任务

服务启动后，应启动一个长期运行的 Tweet Catcher listener。

职责：

- 建立 Tweet Catcher WebSocket 连接。
- 发送或响应协议要求的心跳，记录最近一次收到消息或 pong 的时间。
- 当连接关闭、心跳超时或协议错误时自动重连。
- 重连采用指数退避，退避上限使用 `tweet_catcher.reconnect_max_delay_ms`。
- 每次连接、断线、重连、消息接收、推送失败都必须写结构化日志，日志包含 `trace_id`、`event`、`bounded_context=user_tag_push`。

边界：

- listener 只负责接收外部推文事件并提交内部处理任务，不在 listener 中写复杂业务规则。
- listener 不直接拼 LLM prompt，不直接访问 LLM。
- listener 不直接决定推文是否命中标签；匹配必须通过 `/internal/tag/match-text` 或其内部应用服务能力完成。

## 标签快照定时任务

需要新增一个定时任务，周期性读取所有 active tag。

职责：

- 从 `tags` 表读取 `deleted_at IS NULL` 的标签。
- 至少包含 `id`、`category`、`lang_metadata`、`sort_order`。
- 只读取 `category IN ('country', 'player')` 的标签参与第一阶段推文匹配。
- 将标签快照保存在进程内只读缓存，供推文处理任务快速构造匹配规则。
- 定时刷新失败时保留上一份可用快照，并写 error 日志。

建议刷新策略：

- 服务启动时立即刷新一次。
- 后续按固定间隔刷新，例如 60 秒。
- 后续如果 tag 管理接口修改标签，可以触发一次主动刷新；第一阶段可以先只做定时刷新。

## 推文处理流程

每条 Tweet Catcher 推文进入系统后，处理流程如下：

1. listener 接收原始推文事件，生成或继承 `trace_id`。
2. 立即打印收到的完整推文日志，事件名 `tweet_catcher.tweet_received`，字段必须包含 `tweet.raw`。
3. 从标签快照中取出 active `country` 和 `player` 标签。
4. 构造 `/internal/tag/match-text` 请求。
5. 调用标签匹配能力，必须打印 LLM 输入、输出和耗时。
   - 传给 LLM 的标签只包含英文标签名称数组，英文名称默认取 `tags.lang_metadata.en`。
   - 数据库 `tag_id`、`category`、完整 `lang_metadata` 只允许留在服务内部用于映射、存储和推送，不能传给 LLM。
   - System prompt 必须使用英文，并清楚说明 `tags` 是候选英文标签名数组，`media_input` 是 `<media_input>...</media_input>` 包裹的社交媒体原文；任务是按 OR 关系判断媒体原文命中了哪些标签，并只输出固定 JSON。
6. 如果未匹配，记录 debug/info 日志后结束。
7. 如果匹配，取出命中的 tag 列表。
8. 对每个命中的 tag，按 `tag_id` 将完整推文和匹配结果存储到数据库（match 记录与是否有订阅者无关）。
9. 对每个命中的 tag，反查活跃订阅用户（`user_tags.tag_id = ANY(...) AND deleted_at IS NULL`，DISTINCT 去重），按 `centrifugo.channel_template_user`（默认 `user#{user_id}`）构造各订阅者的个人频道。
   - 频道命名必须与主后端给前端签发的连接 token 授权频道逐字一致；前端只订 `user#<自己的 user_id>`，不订 `tag:*`。
   - 单条推文范围内对 user 去重：同一 user 订阅了多个命中 tag 也只推一次，附其首个命中 tag。
10. 逐个订阅者把完整推文 payload 推送到该用户的 `user#<id>` 频道，必须打印推送 payload、频道、结果和耗时；message body 与历史 `tag:*` 推送完全一致，仅频道不同。
11. 命中 tag 无任何活跃订阅者时跳过发布（match 仍落库，不回写 `pushed_at`）；某 tag 至少有 1 个订阅者成功收到才回写该 match 的 `pushed_at`。
12. `channel_template_tag` 仍保留作为历史/调试维度，当前 fan-out 主链路走 `channel_template_user`。

第一阶段匹配规则：

```json
{
  "operator": "or",
  "groups": [
    {
      "operator": "or",
      "tag_ids": [1, 2, 3]
    },
    {
      "operator": "or",
      "tag_ids": [10, 11, 12]
    }
  ]
}
```

语义：

- 第一组是所有 `country` tag，组内 `or`。
- 第二组是所有 `player` tag，组内 `or`。
- 外层 `or` 表示命中国家或球员任意一个标签即可。

注意：接口返回必须表达“命中的具体 tag”。`/internal/tag/match-text` 要求 LLM 输出 `{"code":0,"msg":"匹配成功","data":["标签1","标签2"]}`，其中 `data` 是命中的标签名称数组；服务端再把标签名称映射回数据库 tag，HTTP `data` 返回 `matched_tags`，例如：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "matched": true,
    "matched_tags": [
      {
        "id": 10,
        "category": "player",
        "lang_metadata": { "en": "Ronaldo" }
      }
    ],
    "llm_result": {
      "code": 0,
      "msg": "匹配成功",
      "data": ["Ronaldo"]
    }
  }
}
```

## 推送 payload

Centrifugo 推送必须发送完整推文，同时补充匹配上下文，便于订阅端展示和排查。

建议 payload：

```json
{
  "event": "tag.tweet.matched",
  "trace_id": "trace_123",
  "tag": {
    "id": 10,
    "category": "player",
    "lang_metadata": { "en": "Ronaldo" }
  },
  "tweet": {
    "raw": {}
  },
  "matched_at": "2026-05-19T00:00:00.000Z"
}
```

要求：

- `tweet.raw` 保留 Tweet Catcher 的完整原始推文对象（即 op=0 monitor event 的整体，业务层不裁剪不解析作者/链接字段）。
- 不在业务层做脱敏裁剪；下游日志采集或展示层按各自策略处理。
- 发布频道为订阅者个人频道 `user#<十进制 user_id>`（`channel_template_user`），同一 message body 逐个订阅者发送。
- 单个订阅者推送失败不影响其他订阅者，但必须记录失败明细。
- 后续如需要幂等，可使用 `tweet_id + tag_id` 作为推送幂等键。

## 匹配结果存储

每条推文只要匹配到 tag，就必须按标签维度存储到数据库。命中多个 tag 时写多条记录。

建议表：`tweet_tag_matches`

核心字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGSERIAL | 自增主键 |
| `trace_id` | TEXT | 本次推文处理 trace |
| `tweet_id` | TEXT | Tweet Catcher / Twitter 原始 tweet id；没有时为空字符串 |
| `tag_id` | BIGINT | 命中的 tag id，不建数据库外键 |
| `tag_category` | VARCHAR(30) | 命中时 tag category 快照 |
| `tag_lang_metadata` | JSONB | 命中时 tag 多语言展示名快照 |
| `tweet_payload` | JSONB | 完整原始推文 |
| `llm_result` | JSONB | tag match LLM 的结构化输出 |
| `pushed_at` | TIMESTAMPTZ | 推送成功后回写；未推送或推送失败为 NULL |
| `created_at` / `updated_at` | TIMESTAMPTZ | UTC |

存储要求：

- 按 `tag_id` 存储，不能只存 tag name。
- 不使用外键；`tag_id` 是匹配时的事实快照。
- 推荐唯一约束 `UNIQUE (tweet_id, tag_id)`；当 `tweet_id` 为空字符串时由应用层决定是否允许重复。
- 推送前先写入匹配记录；推送成功后回写 `pushed_at`。
- 推送失败时保留匹配记录，便于后续补偿或排查。

## 用户历史匹配推文查询

用户侧需要查看自己已命中标签的历史推文时，调用 `GET /internal/tag/matched-tweets?page=1&pageSize=20`。

查询要求：

- 用户身份只从可信 header `x-user-id` 读取，不允许 query/body/path 覆盖。
- 只返回该用户当前 active 的 `user_tags` 关联到的匹配推文。
- 通过 `tweet_id` 去重；同一条推文命中多个 tag 时，接口只返回一条推文，并把命中的 tag 聚合到 `matched_tags`。
- `tweet_id` 为空字符串的记录不返回，因为无法可靠去重。
- 按最近匹配时间倒序分页，返回 `items`、`page`、`pageSize`、`total`。

- `tweet_tag_match.stored`

- `tag_push.publish_failed`

日志字段至少包含：

- `trace_id`
- `level`
- `event`

额外要求：

- 收到推文时日志必须包含完整原始推文：`tweet.raw`。
- 调用 tag LLM 时必须单独打印输入 messages、输出 content / parsed result、token 和耗时。
- 推送时必须打印 Centrifugo channel、完整 publish payload、HTTP 状态、返回结果和耗时。

## DDD 分层归属

- `interface`：启动 HTTP server、listener 和 tag snapshot cache 的进程生命周期挂载点。
- `application`：推文处理用例、标签快照刷新用例、推送 fan-out 编排。
- `domain`：标签规则、匹配结果、推送任务的值对象和领域规则。
- `infrastructure`：Tweet Catcher WebSocket client、Centrifugo HTTP publisher、标签 repository 实现、内部 HTTP client 或应用服务适配器。

业务规则应保持简单：接收推文 -> 读取标签快照 -> 调用匹配 -> 按命中标签推送。重连、心跳、HTTP 调用、Centrifugo 协议封装都属于基础设施组件。用户标签链路不得 import 多 Agent、Registry、Workflow、AI Facade 或应用层 Memory。
