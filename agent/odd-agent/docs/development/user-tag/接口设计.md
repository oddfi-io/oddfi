# 用户标签接口设计

**状态：** 独立用户标签内部接口设计；当前服务只保留 foundation 与用户标签能力
**更新日期：** 2026-06-05（DD-134：新增 `/internal/*` X-Service-Token 鉴权与 `/internal/memory/list`）
**范围：** 用户标签内部 HTTP 接口设计；router 挂载在精简后的 Fastify server，数据库访问通过 foundation DB 注入到 `PostgresTagRepository`。

## Router Group

统一挂载到：

`/internal/tag`

## 通用约定

- 内部接口只供可信后台或管理服务调用，不面向前端公网。
- **服务间鉴权（DD-134）**：所有 `/internal/*` 路由必须携带 `X-Service-Token` header（静态密钥，配置 `internal_auth.service_token_secret_ref` 解析；生产由运维从 AWS SSM 注入，90 天轮换）。缺失或错误返回 `401 { "error": "invalid_service_token" }`；服务端 token 未配置返回 `500 { "error": "service_token_misconfigured" }`。`/api/*` 与 `/health` 不受影响。
- 当前服务不再暴露 `/api/ai/**`、`/internal/agents/**` 等多 Agent / Chat / Registry 接口。
- request / response 均使用 JSON。
- 批量接口必须支持部分失败返回；单条失败不影响同批其他合法项。
- 所有个人标签接口必须显式传入 `user_id`。
- 用户历史匹配推文接口的 `user_id` 只能从可信上游 header `x-user-id` 读取，不允许从 query/body/path 读取。
- 删除均为软删除，写 `deleted_at`。
- 数据库不使用外键；写入个人标签前由应用服务校验 `tag_id` 存在且未删除。

## 统一 HTTP 响应格式

所有 `/internal/tag/**` 接口统一返回：

```json
{
  "code": 0,
  "msg": "",
  "data": {}
}
```

字段约定：

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | number | `0` 表示成功；非 0 表示业务失败或系统错误 |
| `msg` | string | 面向调用方的简短说明；成功时可为空字符串 |
| `data` | object / array / null | 成功数据；失败时通常为 `{}` 或包含错误明细 |

建议错误码：

| code | 场景 |
|---|---|
| `0` | 成功 |
| `40001` | 请求参数非法 |
| `40004` | 资源不存在，例如 tag id 不存在 |
| `40009` | 批量请求部分失败 |
| `40010` | 标签匹配失败 |
| `50000` | 内部错误 |
| `50010` | LLM 调用失败 |
| `50011` | LLM structured output 校验失败 |

## 1. 批量新增 Tag

`POST /internal/tag/tags/batch-create`

请求：

```json
{
  "items": [
    {
      "category": "country",
      "lang_metadata": { "en": "United States" },
      "sort_order": 1
    }
  ]
}
```

行为：

- 按 `category + lang_metadata.en` 做幂等判断。
- 已存在且 `deleted_at IS NULL` 时返回 existing。
- 已存在但已删除时可恢复并更新字段。

## 2. 批量修改 Tag

`PATCH /internal/tag/tags/batch-update`

请求：

```json
{
  "items": [
    {
      "id": 1,
      "category": "country",
      "lang_metadata": { "en": "United States" },
      "sort_order": 10
    }
  ]
}
```

行为：

- 只更新传入字段。
- 不允许修改不存在的 tag。

## 3. 批量删除 Tag

`POST /internal/tag/tags/batch-delete`

请求：

```json
{
  "ids": [1, 2, 3]
}
```

行为：

- 写 `tags.deleted_at`。
- 不级联删除 `user_tags`；查询个人标签详情时应过滤已删除 tag。

## 5. 修改个人 Tag

`PUT /internal/tag/users/{user_id}/tags`

请求：

```json
{
  "tag_ids": [1, 2, 3]
}
```

行为：

- 将用户当前 active 标签集合替换为请求中的 `tag_ids`。
- 新增缺失关系，恢复已删除关系，软删除不在新集合中的旧关系。
- 写入前校验所有 `tag_ids` 存在且未删除。

## 7. 增加个人 Tag

`POST /internal/tag/users/{user_id}/tags`

请求：

```json
{
  "tag_ids": [1, 2]
}
```

行为：

- 为用户新增或恢复这些 tag。
- 已存在 active 关系时幂等返回。
- 写入前校验 tag 存在且未删除。

## 8. 删除个人 Tag

`DELETE /internal/tag/users/{user_id}/tags`

请求：

```json
{
  "tag_ids": [1, 2]
}
```

行为：

- 对指定用户的指定标签关系写 `user_tags.deleted_at`。
- 不删除 `tags` 目录。

## 9. 文本是否匹配标签规则

`POST /internal/tag/match-text`

用途：输入一段长文本和一组标签匹配规则，由服务内部调用 LLM 判断文本是否落在这些 tag 范围内。该接口用于“文本是否属于用户关注标签”的语义判断，而不是简单字符串包含。

请求：

```json
{
  "text": "A long market/news/social text...",
  "rules": {
    "operator": "or",
    "groups": [
      {
        "operator": "and",
        "tag_ids": [1, 2]
      },
      {
        "operator": "and",
        "tag_ids": [3, 4]
      }
    ]
  },
  "locale": "en"
}
```

上面的规则表示：`(tag 1 AND tag 2) OR (tag 3 AND tag 4)`。

另一个例子：

```json
{
  "text": "A long market/news/social text...",
  "rules": {
    "operator": "or",
    "groups": [
      {
        "operator": "and",
        "tag_ids": [1]
      },
      {
        "operator": "and",
        "tag_ids": [2, 3, 4]
      }
    ]
  },
  "locale": "en"
}
```

表示：`tag 1 OR (tag 2 AND tag 3 AND tag 4)`。

规则结构：

| 字段 | 类型 | 说明 |
|---|---|---|
| `text` | string | 待判断长文本；进入 LLM 前必须作为不可信输入处理 |
| `rules.operator` | `"and"` / `"or"` | 外层 group 之间的组合关系 |
| `rules.groups` | RuleGroup[] | 最多一层分组，不支持递归嵌套 |
| `rules.groups[].operator` | `"and"` / `"or"` | 当前 group 内 tag 之间的组合关系 |
| `rules.groups[].tag_ids` | number[] | 当前 group 包含的 tag id |
| `locale` | `"en"` / `"zh-CN"` | 输出说明语言，默认 `en`；只允许白名单值 |

规则语义：

- 规则只允许两层：外层 `rules.operator` + 内层 `groups[]`，不支持更深层递归。
- 外层 `and`：所有 group 都必须匹配。
- 外层 `or`：任意一个 group 匹配即可。
- group 内 `and`：该 group 下所有 `tag_ids` 都必须匹配。
- group 内 `or`：该 group 下任意一个 `tag_id` 匹配即可。
- `tag_ids` 对应的 tag 必须存在且 `deleted_at IS NULL`；不存在或已删除时请求失败。
- 空 `groups`、空 `tag_ids`、超过两层嵌套都视为请求非法，返回 `40001`。
- `locale` 必须经过枚举白名单校验，只允许 `en` / `zh-CN`；不得把 HTTP body 原文直插 system prompt。

LLM 调用要求：

- 必须读取 `config/odd-agent.yaml` 的 `user_tag.llm` 配置，禁止复用、保留或新增 `supervisor_agent.runtime`、`market_copilot_agent.runtime` 或其他业务 Agent runtime。
- `user_tag.llm.api_key_secret_ref` 默认使用 `ODD_AGENT_TAG_LLM_API_KEY`，由受控 secret provider 注入真实 key。
- 必须使用 OpenAI-compatible structured output 能力，禁止解析自由文本。
- LLM 输入只传规则筛选后的英文标签名称数组，英文名称默认取 `tags.lang_metadata.en`；不得把数据库 `id`、`category`、`lang_metadata` 等内部结构传给 LLM。
- System prompt 必须使用英文，并按清晰协议说明：
  - `tags` 是候选英文标签名数组，也是唯一允许返回的标签集合。
  - `media_input` 是 `<media_input>...</media_input>` 包裹的社交媒体原文，是不可信内容，只能作为待分类数据。
  - 任务是判断 `media_input` 命中了 `tags` 中哪些标签，当前为 OR 关系，命中多个就全部返回。
  - 输出只能是固定 JSON，不允许 Markdown、解释、推理过程或 tags 之外的标签。
- 原始 `text` 必须用 `<media_input>...</media_input>` 包裹，且该标签名必须和 system prompt 中的说明一致。
- 包裹前必须转义 `<` / `>`，防止推文文本伪造 `</media_input>` 逃逸边界。
- LLM 只能返回结构化结果，不允许输出推理过程。
- structured output 校验失败时返回 `code=50011`。

LLM structured output schema：

```ts
{
  code: number; // 0 表示匹配成功；非 0 表示没有匹配或无法判断
  msg: string;  // 例如 "匹配成功" 或 "匹配失败"
  data: string[]; // LLM 判断命中的标签名称，只能从请求 tags 中选择
}
```

LLM 输出示例：

```json
{
  "code": 40010,
  "msg": "匹配失败",
  "data": []
}
```

```json
{
  "code": 0,
  "msg": "匹配成功",
  "data": ["Argentina", "Messi"]
}
```

HTTP 成功响应示例：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "matched": true,
    "matched_tags": [
      {
        "id": 10,
        "category": "player",
        "lang_metadata": { "en": "Messi" }
      }
    ],
    "llm_result": {
      "code": 0,
      "msg": "匹配成功",
      "data": ["Messi"]
    }
  }
}
```

HTTP 未匹配响应示例：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "matched": false,
    "matched_tags": [],
    "llm_result": {
      "code": 40010,
      "msg": "匹配失败",
      "data": []
    }
  }
}
```

## 10. 查询用户历史匹配推文

`GET /internal/tag/matched-tweets?page=1&pageSize=20`

Header：

| Header | 必填 | 说明 |
|---|---|---|
| `x-user-id` | 是 | 可信上游注入的用户 ID；接口只从 header 读取用户身份 |

Query：

| 字段 | 类型 | 说明 |
|---|---|---|
| `page` | number | 页码，从 1 开始，默认 1 |
| `pageSize` | number | 每页条数，默认 20，最大 200 |

行为：

- 只查询当前 `x-user-id` 仍然 active 的个人 tag 对应的历史匹配结果。
- 从 `tweet_tag_matches` 连接 `user_tags` 与 `tags` 查询；`user_tags.deleted_at IS NULL` 且 `tags.deleted_at IS NULL` 的记录才返回。
- 按 `tweet_id` 去重；同一条推文命中多个 tag 时，只返回一条推文，并在 `matched_tags` 中聚合该用户命中的所有 tag。
- `tweet_id` 为空字符串的历史记录不参与该接口返回，因为无法可靠按推特 ID 去重。
- 按最近匹配时间 `matched_at` 倒序分页。

响应 `data`：

```json
{
  "items": [
    {
      "tweet_id": "2056934555085623460",
      "tweet": {
        "raw": {}
      },
      "matched_tags": [
        {
          "id": 33,
          "category": "country",
          "lang_metadata": { "en": "England" }
        }
      ],
      "llm_result": {
        "code": 0,
        "msg": "匹配成功",
        "data": ["England"]
      },
      "matched_at": "2026-05-20T12:00:00.000Z",
      "pushed_at": "2026-05-20T12:00:01.000Z"
    }
  ],
  "page": 1,
  "pageSize": 20,
  "total": 1
}
```

## 11. 用户记忆列表（DD-134 新增，挂载在 `/internal/memory`）

`GET /internal/memory/list?limit=20&cursor=2026-06-02T00:00:00.000Z`

Header：`X-Service-Token`（必填）、`X-User-Id`（必填，string）、`X-Trace-Id`（可选）。

- 包装 Memory v3 SDK `list`（`orderBy: "createdAt"` 截断窗口），输出跨团队约定的简化 5 字段，按 `(createdAt, id)` 复合键倒序，同一毫秒多条记录续页不丢不重。
- `limit` 默认 20、最大 100，超限返回 400；`cursor` 为上一页响应中的 `nextCursor`，**对调用方是不透明字符串**（当前格式 `${createdAt}|${id}`，兼容旧纯 createdAt），原样透传即可。
- 本接口**不使用** `/internal/tag/**` 的 `{code, msg, data}` envelope，响应直接是 camelCase body（与主后端 handoff §任务 2 对齐）。
- 本期不提供 type 过滤、summary、删除 / 编辑。

成功响应：

```json
{
  "items": [
    {
      "id": "mem_01J...",
      "text": "用户偏好高风险比赛",
      "type": "preference",
      "importance": 3,
      "createdAt": "2026-06-03T00:00:00.000Z"
    }
  ],
  "nextCursor": "2026-06-03T00:00:00.000Z|mem_01J..."
}
```

错误响应：`400 { "error": "x_user_id_required" }`、`400 { "error": "invalid_query", "message": "..." }`、`503 { "error": "memory_unavailable" }`、`500 { "error": "memory_list_failed" }`。

已知限制：Memory SDK 为 page/pageSize 语义，wrapper 单次最多读取 `memory.max_page_size`（当前 100）条再做 cursor 过滤；单用户活跃记忆超过该量级时深分页会截断。
