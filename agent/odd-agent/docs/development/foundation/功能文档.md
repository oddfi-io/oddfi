# Foundation 组件功能文档

**状态：** 当前实现口径
**更新日期：** 2026-05-22
**适用范围：** 当前 Foundation 组件。旧 foundation / infrastructure 兼容对象不再作为当前实现依据；组件功能以本文和代码为准，保持独立性。

## 1. 目标

Foundation 是 Memory、用户标签推送服务和其他业务组件共同依赖的基础组件集合。它们只负责封装外部基础设施或横切能力，不承载业务规则。当前代码保留 foundation 组件与用户标签功能，多 Agent / Chat / Workflow 运行时已经从当前服务范围移除。

本设计包含 6 个组件：

- LLM 组件：通过 OpenAI SDK 初始化 Chat Completions 客户端，通过配置创建模型实例。
- LLM Embedding 组件：通过 OpenAI SDK 初始化 Embeddings 客户端，通过配置生成 embedding 向量。
- DB 组件：通过配置初始化 SQL 数据库连接。
- Redis 组件：通过配置初始化 Redis 连接。
- Embedding DB 组件：通过公共配置和注入的 provider 初始化向量数据库，提供 embedding 写入/召回能力。
- Logger 组件：通过配置初始化结构化日志输出。

所有组件必须保持独立：

- 组件之间不互相 new。
- 组件不读取全局配置文件。
- 组件不直接读取散落的 `process.env.XXX`。
- Logger 组件只通过自己的配置初始化；除 Logger 外的所有组件，`init(config, deps)` 必须显式接收 `logger`，并用它输出初始化、命令、输入输出、耗时和失败日志。缺少 logger 必须 fail-fast 返回 `FOUNDATION_LOGGER_REQUIRED`。
- 组件只通过 `init(config, deps?)` 或构造参数接收配置和必要依赖。
- 组件初始化失败必须返回 error，并输出可定位日志。
- 旧 `PostgresDatabase`、`RedisKeyValueCache`、旧 LLM adapter、旧 memory foundation 类等不再作为兼容对象；后续代码必须迁移到本文组件。
- 运行时配置采用扁平顶层 section：`logger`、`db`、`redis`、`chatllm`、`memory`。业务功能不得继续读取旧顶层 `foundation`、`logging`、`database`、`vector_store`、`tag_llm`。
- 当前用户标签链路只强制初始化 `logger`、`db` 与 `user_tag.llm`；`redis` 和 Memory 使用的 `memory.embedding-db` 作为独立组件与测试能力保留。

## 2. 统一设计原则

### 2.1 生命周期

每个 Foundation 组件都提供统一生命周期：

```ts
type FoundationComponent<TConfig> = {
  init(config: TConfig, deps?: FoundationInitDeps): Promise<void>;
  healthCheck(): Promise<FoundationHealth>;
  close(): Promise<void>;
};

type FoundationInitDeps = {
  readonly logger?: LoggerComponent;
  readonly secretProvider?: SecretProvider;
};

type FoundationHealth = {
  readonly status: "healthy" | "degraded" | "unhealthy";
  readonly message: string;
  readonly checkedAt: string;
};
```

约束：

- `init()` 只能调用一次；重复调用必须返回明确错误或幂等成功，不能创建多个隐藏连接。
- `healthCheck()` 不修改状态，只检查依赖可用性。
- `close()` 必须释放连接、flush buffer 或停止后台任务。
- 组件未 init 时调用业务方法必须返回 `FOUNDATION_NOT_INITIALIZED`。
- Logger 之外的组件若 `init()` 未传 `logger`，必须返回 `FOUNDATION_LOGGER_REQUIRED`；禁止内部创建静默 logger。
- Logger 之外的组件必须在 `init_started` / `init_succeeded` / `init_failed` 之外，继续记录业务命令级日志，例如 DB query、Redis command、LLM chat completion、LLM embedding、Embedding upsert/search/delete。

### 2.2 配置与 Secret

配置从单一 YAML 的上层 loader 传入组件。Foundation 组件只接收解析后的配置对象。

Secret 只允许通过受控 secret provider 注入：

```ts
type SecretProvider = {
  getSecret(secretRef: string): Promise<string>;
};
```

禁止：

- 在组件内部解析 YAML。
- 在组件内部直接读取 `.env`。
- 在日志里输出连接串、API key、password、token。

### 2.3 错误模型

```ts
type FoundationError = {
  readonly code: string;
  readonly message: string;
  readonly retryable: boolean;
  readonly component: "llm" | "llm_embedding" | "db" | "redis" | "embedding_db" | "logger";
  readonly cause?: unknown;
};
```

所有组件错误必须带 `component`，方便 Memory 聚合日志定位。

## 3. Logger 组件

Logger 是其他 Foundation 组件的基础依赖。它通过配置初始化，并输出结构化日志。

### 3.1 配置

```ts
type LoggerConfig = {
  readonly level: "debug" | "info" | "warn" | "error";
  readonly output: "stdout" | "file";
  readonly directory?: string;
  readonly filenamePrefix?: string;
  readonly redactKeys: readonly string[];
};
```

说明：

- `output=stdout` 时写标准输出。
- `output=file` 时写入 `directory/filenamePrefix-yyyy-MM-dd.log`。
- `redactKeys` 用于日志字段脱敏，例如 `api_key`、`password`、`token`。

### 3.2 接口

```ts
type LoggerComponent = FoundationComponent<LoggerConfig> & {
  debug(event: string, fields?: Record<string, unknown>): void;
  info(event: string, fields?: Record<string, unknown>): void;
  warn(event: string, fields?: Record<string, unknown>): void;
  error(event: string, fields?: Record<string, unknown>): void;
};
```

约束：

- Logger 是可独立拿走的 foundation 组件，只依赖 `@opentelemetry/api`、`@opentelemetry/context-async-hooks` 和自己的配置，不依赖 odd_agent 的业务 telemetry helper、HTTP、Agent、Memory 或隔离键模型。
- Logger 初始化时注册 `AsyncLocalStorageContextManager`；日志方法不接收 `context` 参数，统一读取 `context.active()`。
- Logger 只从 OpenTelemetry active span context 读取 `trace_id` / `span_id`。
- `user_id`、`agent_id`、`session_id`、`conversation_id`、`bounded_context`、`request_trace_id`、`component` 等业务或调用方字段必须由调用方显式放入 `fields`，Logger 不理解、不推断、不从业务 ContextValue 中读取。
- 不导出 `JsonLogEntry` 这类单独日志结构类型；日志条目是内部 JSON 序列化细节，对外只暴露 `Logger` 与 `LogFields`。

### 3.3 日志格式

```json
{
  "timestamp": "2026-05-19T00:00:00.000Z",
  "level": "info",
  "event": "memory.query_succeeded",
  "span_id": "0123456789abcdef",
  "trace_id": "0123456789abcdef0123456789abcdef",
  "fields": {
    "request_trace_id": "trace_1",
    "user_id": "user_1",
    "conversation_id": "conv_1",
    "session_id": "sess_1",
    "component": "memory",
    "bounded_context": "memory"
  }
}
```

### 3.4 验收

- 按 level 过滤日志。
- stdout/file 两种输出可切换。
- secret 字段被脱敏。
- logger 初始化失败时不得影响错误返回，至少 fallback 到 stderr。
- logger 会读取 OpenTelemetry active context。
- 业务字段必须在 `fields` 中输出，不能放入 logger context。

## 4. LLM 组件

LLM 组件通过 OpenAI SDK 初始化，用于用户标签匹配、Memory candidate extraction、Memory diff 和其他需要模型调用的场景。组件只轻量封装 OpenAI-compatible Chat Completions：统一配置、日志、超时、结构化输出、tool/function calling 与 streaming；不引入 LangChain 抽象。

### 4.1 配置

```ts
type LlmConfig = {
  readonly model: string;
  readonly modelTier: "cheap" | "standard" | "strong";
  readonly baseUrl?: string;
  readonly apiKeySecretRef: string;
  readonly temperature: number;
  readonly timeoutMs: number;
  readonly maxRetries: number;
  readonly defaultHeaders?: Record<string, string>;
};
```

### 4.2 初始化

```ts
init(config: LlmConfig, deps: {
  secretProvider: SecretProvider;
  logger: LoggerComponent;
}): Promise<void>
```

初始化职责：

- 创建 OpenAI SDK client；`baseUrl` 为空时使用 OpenAI 默认 endpoint，非空时连接 OpenAI-compatible endpoint。
- 通过 `apiKeySecretRef` 获取 API key。
- 设置 timeout、retry、temperature、headers。
- 不在业务方法中重复创建 OpenAI SDK client。
- 使用传入的 `logger` 记录 `foundation.llm.init_*`、`foundation.llm.chat_completion_*`；生产是否打印 message 原文由配置控制。
- 未传 `logger` 时必须拒绝初始化；未传 `secretProvider` 时必须拒绝初始化。

### 4.3 接口

```ts
type LlmComponent = FoundationComponent<LlmConfig> & {
  readonly client: OpenAI;
  readonly chatCompletions: {
    readonly model: string;
    readonly temperature: number;
    create(params: ChatCompletionCreateParamsNonStreaming): Promise<ChatCompletion>;
    stream(params: ChatCompletionCreateParamsStreaming): Promise<Stream<ChatCompletionChunk>>;
  };
};
```

说明：

- `client` 暴露原生 OpenAI SDK 实例，供少数调用方直接使用 OpenAI 方法。
- `chatCompletions.create()` 是对 `client.chat.completions.create()` 的轻量包装，只补统一 timeout 和日志；请求参数保持 OpenAI 原生形态。
- `chatCompletions.stream()` 是对 `stream:true` 的轻量包装，返回 OpenAI SDK stream。
- `chatCompletions.model` 与 `chatCompletions.temperature` 来自初始化配置，调用方构造请求时直接复用，避免在业务层散落模型名和温度。
- Tool Calling、Function Calling、Structured Output、Response Schema、Streaming 都由调用方按 OpenAI Chat Completions 参数直接传入，Foundation LLM 不再做二次抽象或自动工具执行编排。
- Memory 和用户标签调用方自己解析 OpenAI response，并用 zod 做业务 schema 校验。

### 4.4 日志

事件：

- `foundation.llm.init_started`
- `foundation.llm.init_succeeded`
- `foundation.llm.init_failed`
- `foundation.llm.chat_completion_started`
- `foundation.llm.chat_completion_succeeded`
- `foundation.llm.chat_completion_stream_opened`
- `foundation.llm.chat_completion_failed`

字段：

- `provider`
- `model`
- `model_tier`
- `trace_id`
- `conversation_id`
- `tool_call_count`
- `tool_names`
- `duration_ms`
- `input_tokens`
- `output_tokens`
- `retry_count`

禁止日志输出 API key。请求 messages 是否完整打印由配置控制，生产默认不打印原文。

### 4.5 验收

- 能通过配置初始化 OpenAI SDK client。
- timeout 生效。
- retry 次数可配置。
- JSON 输出模式失败时返回明确错误。
- token usage 可记录时必须写日志。
- 一个 LLM 组件实例只能绑定一个 `provider/baseUrl/model/apiKeySecretRef/temperature/timeoutMs` 配置；不同模型、不同 baseUrl 或不同 timeout 策略必须创建不同 LLM 对象，禁止在 `complete()` 中覆盖这些初始化配置。

## 5. LLM Embedding 组件

LLM Embedding 组件通过 OpenAI SDK 初始化，用于调用 OpenAI-compatible Embeddings API 生成向量。它只生成 vector，不负责存储、检索或 metadata 管理；向量落库仍由 Embedding DB 组件负责。

该组件必须和 Chat Completions LLM 组件隔离：独立文件 `src/foundation/llm/llm-embedding.ts`、独立配置、独立初始化实例、独立日志事件；不得复用 `OpenAiLlmComponent` 或 `LlmConfig`。

### 5.1 配置

```ts
type LlmEmbeddingConfig = {
  readonly model: string;
  readonly baseUrl?: string;
  readonly apiKeySecretRef: string;
  readonly timeoutMs: number;
  readonly maxRetries: number;
  readonly dimensions?: number;
  readonly encodingFormat?: "float" | "base64";
  readonly defaultHeaders?: Record<string, string>;
};
```

### 5.2 初始化

```ts
init(config: LlmEmbeddingConfig, deps: {
  secretProvider: SecretProvider;
  logger: LoggerComponent;
}): Promise<void>
```

初始化职责：

- 创建独立 OpenAI SDK client；`baseUrl` 为空时使用 OpenAI 默认 endpoint，非空时连接阿里百炼等 OpenAI-compatible endpoint。
- 通过 `apiKeySecretRef` 获取 API key。
- 设置 timeout、retry、headers。
- 不复用 Chat Completions LLM 组件实例。
- 未传 `logger` 或 `secretProvider` 时必须 fail-fast。

### 5.3 接口

```ts
type LlmEmbeddingComponent = FoundationComponent<LlmEmbeddingConfig> & {
  readonly client: OpenAI;
  readonly embeddings: {
    readonly model: string;
    readonly dimensions?: number;
    create(params: EmbeddingCreateParams): Promise<CreateEmbeddingResponse>;
    embedText(text: string, options?: { user?: string; dimensions?: number }): Promise<readonly number[]>;
    embedTexts(texts: readonly string[], options?: { user?: string; dimensions?: number }): Promise<readonly (readonly number[])[]>;
  };
};
```

说明：

- `embeddings.create()` 是对 `client.embeddings.create()` 的轻量包装，只补统一 timeout 和日志；请求参数保持 OpenAI 原生形态。
- `embedText()` 和 `embedTexts()` 是常用便捷方法，默认使用初始化时的 model、dimensions 和 encodingFormat。
- 返回向量必须是 number 数组；如果 provider 返回空向量或非 number 值，组件必须抛错。
- dimensions 是 embedding 模型能力，不属于向量库配置；Embedding DB 的 dimension 仍要和最终向量长度一致。

### 5.4 日志

事件：

- `foundation.llm_embedding.init_started`
- `foundation.llm_embedding.init_succeeded`
- `foundation.llm_embedding.init_failed`
- `foundation.llm_embedding.embedding_started`
- `foundation.llm_embedding.embedding_succeeded`
- `foundation.llm_embedding.embedding_failed`

字段：

- `component=llm_embedding`
- `model`
- `input_count`
- `dimensions`
- `duration_ms`
- `input_tokens`
- `total_tokens`

禁止日志输出 API key 或 embedding 原文全文。

### 5.5 验收

- 能通过 OpenAI-compatible fake server 初始化并生成单条、多条 embedding。
- 能透传 OpenAI 原生 `embeddings.create()` 参数。
- 未初始化、缺 logger、缺 secretProvider、空向量或维度不匹配时返回明确错误。
- 真实 E2E 使用阿里百炼 OpenAI-compatible base URL、`text-embedding-v4` 生成向量，并写入真实 pgvector 后完成检索、更新、删除；`qwen3-vl-embedding` 是多模态 embedding 模型，实测不支持百炼 OpenAI-compatible `/embeddings`。

## 6. DB 组件

DB 组件通过配置初始化 SQL 数据库连接，供用户标签业务 repository、migration runner 和 pgvector provider 底层连接使用。Memory 长期记忆不再使用 DB 主表。

### 6.1 配置

```ts
type DbConfig = {
  readonly provider: "postgres";
  readonly connectionStringSecretRef: string;
  readonly maxPoolSize: number;
  readonly statementTimeoutMs: number;
  readonly idleTimeoutMs: number;
  readonly ssl: boolean;
};
```

### 5.2 初始化

```ts
init(config: DbConfig, deps: {
  secretProvider: SecretProvider;
  logger: LoggerComponent;
}): Promise<void>
```

初始化职责：

- 从 secret provider 获取连接串。
- 创建连接池。
- 设置 statement timeout。
- 初始化后执行轻量 `select 1`。
- 使用传入的 `logger` 记录 DB 初始化、query、transaction 的 SQL hash/耗时/行数/错误。
- 未传 `logger` 时必须拒绝初始化；未传 `secretProvider` 时必须拒绝初始化。

### 5.3 接口

```ts
type DbQueryCommand = {
  readonly traceId?: string;
  readonly text?: string;
  readonly sql?: string;
  readonly values?: readonly unknown[];
  readonly params?: readonly unknown[];
};

type DbQueryResult<T> = {
  readonly rows: readonly T[];
  readonly rowCount: number;
  readonly durationMs: number;
};

type DbTransaction = {
  query<T>(command: DbQueryCommand): Promise<DbQueryResult<T>>;
  query<T>(text: string, values?: readonly unknown[]): Promise<DbQueryResult<T>>;
};

type DbComponent = FoundationComponent<DbConfig> & {
  query<T>(command: DbQueryCommand): Promise<DbQueryResult<T>>;
  query<T>(text: string, values?: readonly unknown[]): Promise<DbQueryResult<T>>;
  transaction<T>(handler: (tx: DbTransaction) => Promise<T>): Promise<T>;
};
```

约束：

- 只允许参数化 SQL，禁止字符串拼接用户输入。
- query 日志不能输出 secret；SQL 文本是否完整输出由配置控制，生产默认只输出 statement name 或 hash。
- transaction 失败必须 rollback。

### 5.4 日志

事件：

- `foundation.db.init_started`
- `foundation.db.init_succeeded`
- `foundation.db.init_failed`
- `foundation.db.query_started`
- `foundation.db.query_succeeded`
- `foundation.db.query_failed`
- `foundation.db.transaction_started`
- `foundation.db.transaction_succeeded`
- `foundation.db.transaction_failed`

### 5.5 验收

- 连接失败返回 `FOUNDATION_DB_INIT_FAILED`。
- query 超时返回 retryable error。
- transaction 失败自动 rollback。
- `close()` 后连接池释放。

## 6. Redis 组件

Redis 组件通过配置初始化，供锁、缓存或短期运行时状态使用。Memory v3 长期语义记忆 SDK 不依赖 Redis。

### 6.1 配置

```ts
type RedisConfig = {
  readonly urlSecretRef: string;
  readonly keyPrefix: string;
  readonly commandTimeoutMs: number;
  readonly maxRetries: number;
  readonly defaultTtlSeconds?: number;
};
```

### 6.2 初始化

```ts
init(config: RedisConfig, deps: {
  secretProvider: SecretProvider;
  logger: LoggerComponent;
}): Promise<void>
```

初始化职责：

- 从 secret provider 获取 Redis URL。
- 建立连接。
- 执行 ping。
- 保存 `keyPrefix`，所有 key 必须自动加前缀。
- 使用传入的 `logger` 记录 Redis command、key、TTL、耗时、错误。
- 未传 `logger` 时必须拒绝初始化；未传 `secretProvider` 时必须拒绝初始化。

### 6.3 接口

```ts
type RedisSetOptions = {
  readonly ttlSeconds?: number;
  readonly nx?: boolean;
};

type RedisComponent = FoundationComponent<RedisConfig> & {
  get<T>(key: string): Promise<T | undefined>;
  set<T>(key: string, value: T, options?: RedisSetOptions): Promise<boolean>;
  del(key: string): Promise<number>;
  lpush<T>(key: string, values: readonly T[]): Promise<number>;
  lrange<T>(key: string, start: number, stop: number): Promise<readonly T[]>;
  ltrim(key: string, start: number, stop: number): Promise<void>;
  ping(): Promise<"PONG">;
};
```

约束：

- value 必须 JSON 序列化。
- 写入前由调用方完成 schema 校验；Redis 组件只负责存取。
- key 必须自动加 `keyPrefix`，调用方不需要手写前缀。
- Redis 丢失不能作为业务事实丢失；事实源必须在 DB 或向量库。
- Redis 组件必须使用成熟 client（当前实现选型 `ioredis`），禁止维护自实现 RESP 协议解析、每条命令新开 TCP socket 或每条命令重复 AUTH/SELECT。
- `maxRetries` 由 Redis client 的 retry strategy 执行，必须包含递增退避并受 `commandTimeoutMs` 约束。

### 6.4 日志

事件：

- `foundation.redis.init_started`
- `foundation.redis.init_succeeded`
- `foundation.redis.init_failed`
- `foundation.redis.command_started`
- `foundation.redis.command_succeeded`
- `foundation.redis.command_failed`

字段：

- `command`
- `key`
- `duration_ms`
- `ttl_seconds`
- `retry_count`

### 6.5 验收

- key prefix 强制生效。
- command timeout 生效。
- JSON parse 失败返回明确错误。
- `nx` 语义正确。
- 连接断开后 healthCheck 返回 degraded 或 unhealthy。

## 7. Embedding DB 组件

Embedding DB 组件通过配置和注入的 provider 初始化，封装向量数据库 collection/index、embedding 写入和相似召回。

### 7.1 配置

```ts
type EmbeddingDbConfig = {
  readonly collectionName: string;
  readonly dimension: number;
  readonly distance: "cosine" | "dot" | "l2";
  readonly topKDefault: number;
  readonly maxContentBytes: number;
  readonly maxMetadataBytes: number;
};
```

说明：

- `EmbeddingDbConfig` 只包含 Foundation Embedding DB 的通用约束，不包含 provider 名称、endpoint、connection string 或 API key。
- 组件必须通过 provider 接口装配，初始化时由调用方注入具体实现；组件本体只做公共校验、日志、健康检查和生命周期编排。
- Qdrant 是本地和默认真实回归常用 provider，provider 自己持有 `endpoint` 和可选 `apiKeySecretRef`，向量数据不进入 PostgreSQL。
- pgvector 保留为兼容 provider，provider 自己持有 SQL connection string secret ref。
- `memory` 仅用于本地 fuzz/unit 测试，不作为生产向量库。
- `collectionName` 必须有真实存储含义：pgvector 中是表名，Qdrant/Chroma/Milvus 中是 collection，Pinecone 中是 namespace；Pinecone index 由 endpoint 指向，不再额外配置 namespace 字段。
- Milvus/Pinecone/Chroma 均已有独立 provider 类实现标准接口；真实服务 endpoint、token、tenant、API version 等配置放在各自 provider config 中，不能进入 `EmbeddingDbConfig`。
- Pinecone provider 私有配置当前包含 `endpoint`、`apiKeySecretRef`、`apiVersion`、`timeoutMs`、`maxRetries`、`retryDelayMs`；真实服务请求失败时会把网络错误归一为 Foundation AppError，并按 provider 配置做线性退避重试。
- provider 文件按实现拆分，例如 `embedding-db-provider-qdrant.ts`、`embedding-db-provider-pgvector.ts`、`embedding-db-provider-milvus.ts`、`embedding-db-provider-pinecone.ts`、`embedding-db-provider-chroma.ts`。
- collection/index 必须在 init 时检查，不存在时按配置决定创建或 fail-fast。默认 fail-fast。
- `maxContentBytes` / `maxMetadataBytes` 是写入入口硬限制，防止超长文本或 metadata 撑爆存储。
- `topKDefault` 在 search 未传 `topK` 时使用。

### 7.2 初始化

```ts
init(config: EmbeddingDbConfig, deps: {
  logger: LoggerComponent;
  provider: EmbeddingDbProvider;
  secretProvider?: SecretProvider;
}): Promise<void>
```

初始化职责：

- 建立向量库连接。
- 检查 collection、dimension、distance 是否匹配。
- healthCheck 验证可查询。
- 使用传入的 `logger` 记录 upsert/search/delete 的 collection、filter、topK、结果数、耗时、错误。
- 未传 `logger` 或 `provider` 时必须拒绝初始化；需要 secret 的 provider 未传 `secretProvider` 时必须拒绝初始化。

### 7.3 接口

```ts
type EmbeddingVector = readonly number[];

type EmbeddingUpsertCommand<TMetadata> = {
  readonly traceId?: string;
  readonly userId: string;
  readonly id: string;
  readonly vector: EmbeddingVector;
  readonly content: string;
  readonly metadata: TMetadata;
};

type EmbeddingSearchCommand<TFilter> = {
  readonly traceId?: string;
  readonly userId: string;
  readonly vector: EmbeddingVector;
  readonly filter: TFilter;
  readonly topK?: number;
};

type EmbeddingSearchResult<TMetadata> = {
  readonly id: string;
  readonly content: string;
  readonly metadata: TMetadata;
  readonly score: number;
};

type EmbeddingDbComponent = FoundationComponent<EmbeddingDbConfig> & {
  upsert<TMetadata>(command: EmbeddingUpsertCommand<TMetadata>): Promise<void>;
  search<TFilter, TMetadata>(
    command: EmbeddingSearchCommand<TFilter>
  ): Promise<readonly EmbeddingSearchResult<TMetadata>[]>;
  deleteByFilter<TFilter>(userId: string, filter: TFilter): Promise<number>;
  deleteByUser(userId: string): Promise<number>;
};
```

约束：

- `userId` 是组件 API 的一等参数，upsert/search/delete 都必须显式传入；filter 只表达业务维度，禁止靠 filter 里的 `userId` 做租户隔离。
- Qdrant point id 由 `userId + id` 稳定映射，原始业务 id 保存在 payload，避免 provider id 格式泄漏到调用方。
- Pinecone vector id 由 `userId + id` 稳定映射，真实 data-plane 请求里的 namespace 来自 `EmbeddingDbConfig.collectionName`。
- 组件写入时必须把 `userId` 同步写入 provider 原生隔离字段或 payload，并把 `userId` 补入 metadata，便于审计和兼容读取。
- pgvector 表必须使用 `(user_id, id)` 复合主键，避免不同用户相同业务 id 互相覆盖。
- pgvector 搜索必须先 `WHERE user_id = $2`，再做 metadata 业务过滤，避免 ANN topK 后置过滤导致召回塌缩。
- pgvector 必须创建向量 HNSW 索引、metadata GIN 索引和 `(user_id, created_at DESC)` B-tree 索引。
- pgvector 搜索的 `ORDER BY` 必须使用原生 vector operator，例如 `embedding <=> $1::vector`，score 在 SELECT 列中计算。
- 禁止无 filter 的全局向量召回。
- filter 值不得包含 `undefined`，嵌套对象也不得包含 `undefined`；序列化前必须校验。
- memory provider 的 filter 语义必须与真实 provider 的 metadata 子集匹配语义对齐，而不是只做顶层严格相等。
- metadata 必须由调用方 schema 校验后传入。
- dimension 不匹配必须拒绝写入。
- Qdrant / pgvector init 如果发现已有 collection 的 embedding 维度与配置不一致，必须 fail-fast；distance 变化会影响索引或 collection 配置，已有配置不匹配时也必须 fail-fast 或按明确策略重建。
- `memory` provider 的 healthCheck 返回 `degraded`，message 必须说明使用 in-memory backing。

### 7.5 验收

- Qdrant 当前实现会显式创建 collection；pgvector 兼容 provider 会显式创建 extension/table。
- dimension 不一致时报错。
- search 必须带 filter。
- topK=0 时调用方应跳过；组件收到 topK=0 时返回空数组。
- deleteByFilter 返回删除数量。
- deleteByUser 返回删除数量，并按用户维度隔离。

## 8. Memory 初始化依赖关系

Memory 组件初始化时接收这些 Foundation 实例：

```ts
type MemoryFoundationDeps = {
  readonly embeddingDb: EmbeddingDbComponent;
  readonly llm: LlmComponent;
  readonly llmEmbedding: LlmEmbeddingComponent;
  readonly logger: LoggerComponent;
};
```

初始化顺序建议：

1. Logger
2. Secret provider
3. DB
4. Embedding DB
5. LLM
6. LLM Embedding
7. Memory

说明：

- Logger 先初始化，后续组件初始化日志才能输出。
- DB/Redis/Embedding DB/LLM/LLM Embedding 互不依赖。
- Memory v3 是长期语义记忆 SDK，只依赖 Embedding DB、LLM、LLM Embedding、Logger，不再依赖 DB/Redis，也不再实现旧 L1/L2/L3/L4 或结构化记忆 `update/queryStructureMemory`。

## 10. 验收清单

- 五个组件都能只通过配置初始化。
- 五个组件都提供 `init/healthCheck/close`。
- 除 Logger 外的四个组件初始化时缺少 logger 必须失败，错误码为 `FOUNDATION_LOGGER_REQUIRED`。
- LLM 通过 OpenAI SDK 初始化，不在业务调用时重复 new。
- DB query 只支持参数化 values。
- Redis keyPrefix 自动生效。
- Embedding DB search 必须带非空业务 filter；Memory 调用时 `userId` 通过 Embedding DB 一等参数传入，不再把 `userId` 当普通 filter 字段。
- Logger 输出结构化 JSON，并按 level 过滤。
- 所有组件初始化、成功、失败都有日志。
- 所有 secret 只通过 secret provider 注入，日志不输出明文 secret。
- Foundation 组件不依赖 Memory，不依赖具体业务 Agent。
- 旧 foundation 组件名不能作为新业务代码入口；实现验收时必须检查没有新增对旧组件的依赖。
