# 数据库迁移说明

**更新日期：** 2026-05-26

## 当前规则

- 所有 PostgreSQL 表和索引必须通过 `db/migrations/*.sql` 管理。
- 业务运行时与 foundation 组件不得 lazy `CREATE TABLE IF NOT EXISTS`。
- migration 文件按文件名版本顺序执行，已写入 `schema_migrations` 的版本不再重复执行。
- 当前仓库保留可用于新环境 replay 的最小迁移集合；已经废弃且会被立即清理的历史表不再继续保留建表 SQL。
- Supabase 新环境可用 `npm run db:provision:supabase` 初始化；脚本读取 `SUPABASE_DATABASE_URL`，执行当前 migrations，并可按 `memory.embedding_collection_name` 创建 pgvector 兼容 provider 的 embedding collection。Memory 默认运行时使用 `memory.embedding-db` 指定的 provider。

## 当前迁移

## Supabase 初始化

脚本：`scripts/supabase-provision.ts`。

用途：

- 创建 `schema_migrations`。
- 按顺序执行 `db/migrations/*.sql`。
- 启用 `vector` 扩展。
- 为 pgvector 兼容 provider 创建当前配置中的 `odd_agent_vectors` embedding collection 及 HNSW / GIN / B-tree 索引，当前维度为 `512`。Qdrant/Pinecone/Milvus/Chroma provider 的 collection/index 由各自 provider 初始化或外部服务管理。
- 输出已执行 migration 和当前 managed tables。

运行方式：

```bash
SUPABASE_DATABASE_URL="postgresql://postgres:<password>@db.<project-ref>.supabase.co:5432/postgres" npm run db:provision:supabase
```

连接串只应通过环境变量或受控 secret 注入，不写入仓库文件。

说明：早期 `0001_core_ai_facade.sql` 会创建已经废弃的 Chat / Session / Agent invocation 表，当前运行时不再依赖这些表，新环境不应继续创建它们。

## 回滚策略

- 历史 `0003_memory.sql` 和 `0005_drop_memory_postgresql_tables.sql` 已从仓库迁移集合中移除。当前 Memory 已切换到 Foundation Embedding DB 事实源，新环境不需要依赖 `memories` / `memory_events`。
- 已经执行过旧 migration 且仍残留旧 Memory PostgreSQL 表的环境，在确认没有旧数据读取需求后手工执行：

```sql
drop table if exists memory_events;
drop table if exists memories;
delete from schema_migrations where version = '0003_memory';
delete from schema_migrations where version = '0005_drop_memory_postgresql_tables';
```
