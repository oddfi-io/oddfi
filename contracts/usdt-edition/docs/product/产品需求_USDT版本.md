# OddFi 产品需求文档 — USDT 版本

**版本：** v1.1
**日期：** 2026-03-29
**最后更新：** 2026-04-01
**目标上线：** 2026-06-11（世界杯开赛）
**适用范围：** 面向普通用户的稳定币下注版本

---

## 一、产品定位

USDT 版本是平台基础版本，用户以 USDT 参与体育预测市场，核心价值主张：

- **无摩擦下注**：充值即可下注，不需要额外操作
- **链上保障**：资金由智能合约托管，提现和结算由链上规则执行，不可篡改
- **透明结算**：结算由链上多签触发，过程可查

---

## 二、整体流程

```
用户连接钱包（MetaMask / WalletConnect）
        ↓
充值 USDT → 进入智能合约（BettingPool）
        ↓
浏览赛事列表，查看实时赔率
        ↓
选择盘口（胜负平 / 让分 / 总分）→ 输入金额 → 确认下注
        ↓
后端验证通过 → 合约锁定余额（用户无需签名）
        ↓
赛事结束 → 双源核实 → Admin 多签触发链上结算
        ↓
赢家余额自动到账 → 用户随时提现
```

## 四、模块详情

### 4.0 赛事与盘口管理

#### 赛事生命周期

```
后端从 Sportmonks 拉取赛事数据
        ↓
赛事创建（DB 入库，前端可见但不可下注）
        ↓
开盘 → 各盘口依次开放（接单中）
        ↓
封盘（赛事开始前由后端触发，停止接单）
        ↓
赛事结束 → 双源核实
        ↓
结算（Admin 多签） 或 取消（赛事因故取消）
```

| 状态 | 说明 | 前端展示 |
|------|------|---------|
| 未开盘 | 赛事已创建，但尚未开放下注 | 显示赛事信息，赔率置灰 |
| 接单中 | 盘口已开放，用户可正常下注 | 赔率可点击，信号灯正常显示 |
| 已封盘 | 赛事即将或已开始，停止接受新注单 | 所有盘口赔率置灰，提示"已封盘" |
| 已结算 | 赛事结束且已完成链上结算 | 显示赛果和派彩详情 |
| 已取消 | 赛事因故取消 | 提示"赛事取消，注单已退款" |

#### 盘口生命周期

每个盘口（如"让分 -0.5"）独立管理状态：

| 操作 | 触发方 | 说明 |
|------|-------|------|
| 开盘 | Jason 后端 | 调用合约 `openMarket()` 或 `batchOpenMarkets()`（同赛事多盘口批量），盘口进入"接单中" |
| 封盘 | Jason 后端 | 调用合约 `closeMarket()` 或 `batchCloseMarkets()`（批量），停止接单 |
| 重新开盘 | Admin 多签 | 赛事延期或误封盘时，调用 `reopenMarket()` 恢复接单（需多签审批） |
| 结算 | Admin 多签 | 调用合约 `settle()`，派彩到账（支持分批） |
| 取消 | Admin 多签 | 调用合约 `cancelMatch()` 或 `batchCancelMatch()`（批量），注单退款 |

> 每场赛事最多 9 个独立盘口（3 类型 × 3 条线），每个盘口独立开/关/结算。开盘时合约自动将盘口注册到赛事（`matchMarkets[matchId]`），支持链上查询某赛事的所有盘口。Jason 负责赛事数据同步和盘口开关时机，合约层通过 `marketStatus` 强制执行状态检查，确保已封盘/已结算的盘口无法下注。

### 4.1 充值

| 环节 | 说明 |
|------|------|
| 充值方式 | 用户从个人钱包向 BettingPool 合约地址直接发起 USDT `transfer()` |
| 确认规则 | BSC 链 12 个区块确认后到账（约 36 秒） |
| 监听方式 | 后端监听 **USDT 合约的 `Transfer` 事件**（`to` = BettingPool 合约地址），确认后调用合约 `creditDeposit()` 为用户入账；合约 `Deposited` 事件用于确认入账成功，防止重复入账 |
| 前端展示 | 合约地址 + 一键复制；充值状态：确认中 / 已到账 |

### 4.2 下注

**下注流程：**
1. 用户点击赔率按钮，弹出 Bet Slip
2. 输入金额，查看预计赔付
3. 点击「确认下注」
4. 后端完成所有验证后，调用合约 `lockBet()`，用户余额锁定
5. 返回 betId + 锁定赔率 + 预计赔付

**下注校验规则：**

| 校验项 | 规则 | 错误提示 |
|-------|------|---------|
| 盘口状态 | 盘口必须为"接单中"（Open） | "盘口不可下注" |
| 余额 | stake ≤ 可用余额 | "余额不足，去充值" |
| 单注上限 | 赔率 <2.0 → $800；2.0–3.5 → $500；>3.5 → $300 | "超过单注限额 $X" |
| 每日限额 | 普通用户 $1,000 / 标准 $5,000 / VIP $15,000 | "今日限额已用完" |
| 赔率变动 | 差值 >0.05 → 返回 409，前端弹窗确认新赔率（链下校验，合约不重复检查） | 弹窗：原赔率 → 新赔率 |
| 信号灯 | 红灯方向拒绝接单 | 按钮置灰："暂停接单" |
| 流动性 | 潜在赔付 ≤ Betting Pool 可用余额 | "当前盘口暂无法接受此金额" |

> 串关注单的 stake 同样受单注上限和每日限额约束。
>
> **赔率变动与串关：** 串关下单时，若任意一腿赔率变动 >0.05，整张串关返回 409，前端弹窗展示所有变动腿的新旧赔率，用户确认后以新赔率重新提交。
>
> **合约层兜底：** 赔率变动、单注上限、每日限额均为链下校验。合约层设有全局单注硬上限（$10,000）作为最终防线，防止后端异常时的极端情况。

### 4.3 赔率机制

> **赔率精度：** 赔率在链上以 ×1000 整数存储（如 1.818 存为 1818），链下展示时除以 1000。产品文档中的赔率均为链下展示值。

**开盘：**
- 从 Sportmonks 获取参考赔率
- 去除参考 Margin，还原真实概率
- 加入平台 10% Margin，生成开盘赔率
- 写入 DB + Redis，推送 WebSocket

**动态调整（下注后异步触发）：**
- 计算三方向各自累计投注额，找出重仓方向
- 重仓方向压低赔率，轻仓方向上浮（k=1.0）
- 变动 >0.05 推送 WebSocket，≤0.05 静默更新

**信号灯（多盘口模式，每盘口独立计算）：**

| 颜色 | 重仓方向累计差额 | 处理 |
|------|--------------|------|
| 🟢 绿 | $0 – $8,000 | 正常接单 |
| 🟡 黄 | $8,000 – $18,000 | 后端预警，继续接单 |
| 🟠 橙 | $18,000 – $28,000 | 限额接单（单注上限降至正常值的 50%） |
| 🔴 红 | > $28,000 | 重仓方向停止接单，前端置灰 |

> 世界杯期间（多场次同时进行），Admin 可将红灯阈值收紧至 $5,000–$8,000/盘口。

### 4.4 结算派彩

**流程：**
1. 赛事结束，Sportmonks + API-Football 双源核实结果
2. 两源一致 → 进入「待确认」队列
3. 两源不一致 → 状态设为 disputed，Telegram 告警
4. 运营后台人工确认最终结果
5. Admin 多签钱包调用合约 `settle()`，链上自动派彩
6. 赢家余额实时到账，用户可立即提现

**派彩规则：**
- 赢家：`payout = stake × lockedOdds`
- 资金来源：Betting Pool（LP 对赌资金）
- 输家 stake：70% → Betting Pool，30% → 平台

### 4.5 串关（Parlay）

用户从**不同赛事**各选一个盘口，组合成一张注单。全部命中才算赢，赔率连乘。

**串关规则：**

| 规则项 | 说明 |
|-------|------|
| 最少腿数 | 2 腿 |
| 最多腿数 | 6 腿 |
| 同赛事限制 | 同一赛事只能选 1 个盘口，不允许跨盘口串关 |
| 赔率计算 | 各腿锁定赔率连乘，下单时锁定 |
| 最大赔付 | $10,000 / 张（超出提示减少金额） |
| 流动性校验 | 潜在赔付 = stake × 组合赔率，≤ Betting Pool 可用余额 |
| 红灯拦截 | 任意一腿所在盘口为红灯方向 → 整张串关拒绝 |
| Lending 限制 | 串关注单**不可**作为 Lending 抵押 |
| 赛事取消 | 取消该腿（视为赔率 1.0），重新计算组合赔率；若剩余腿数 < 2 则退化为单注处理（见 4.8） |

**串关流程：**
1. 用户在 Bet Slip 中添加多场赛事的赔率按钮（跨赛事）
2. 选满 ≥2 腿后切换为「串关模式」，显示组合赔率和预计赔付
3. 输入金额，点击「确认串关」
4. 后端验证通过后，调用合约 `lockParlay()` 锁定余额并生成关联的 parlayId
5. 任意一腿赛事结算为输 → 整张串关标记为输，剩余腿不再结算派彩
6. 全部腿均赢 → 按组合赔率派彩

### 4.6 提现

| 环节 | 说明 |
|------|------|
| 可提金额 | 余额 - 锁定中注单金额 |
| 提现方式（≤ $5,000） | 用户调用合约 `withdraw()`，USDT 直接到账个人钱包 |
| 大额提现（> $5,000） | 调用 `withdraw()` 进入 24h 审核等待期；等待期内 Admin 可拒绝（余额解冻），未拒绝则用户调用 `executeLargeWithdrawal()` 自行完成提现 |
| 手续费 | 无平台手续费，用户自行承担 Gas（含 withdraw / executeLargeWithdrawal 的 Gas）；Admin 操作（rejectLargeWithdrawal 等）的 Gas 为平台运营成本 |

### 4.7 Lending（信用仓位）

用户可以将已锁定的注单作为抵押，获得信用额度用于下注。

**规则：**

| 项目 | 说明 |
|------|------|
| 信用比例 | 抵押注单本金的 50%（同一抵押仓位的所有信用仓位累计不超过 50%） |
| 信用来源 | 信用额度由 Betting Pool 出资，锁定时从池中扣减 |
| 信用用途 | 下注任意比赛 |
| 有效期 | 抵押注单比赛结束时间 + 7 天 |
| 赛事限制 | 信用仓位 B 的比赛须在有效期内结束 |
| 禁止连环借贷 | 信用仓位不可再作为抵押借出新信用，最多借一层 |
| 串关限制 | 串关注单不可作为抵押 |

**结算规则（A = 抵押仓位，B = 信用仓位）：**

| 场景 | 处理 |
|------|------|
| A 赢 + B 赢 | A 正常赔付；B 正常赔付，**信用额从 B 赔付中扣回归还资金池** |
| A 赢 + B 输 | A 正常赔付；B 本金按 70/30 分配（资金池/平台） |
| A 输 + B 赢 | B 赢得赔付归入 platformBalance（平台收益） |
| A 输 + B 输 | B 信用额全额归还资金池（信用收回，无 70/30 分配）。**原因：** Pool 出资借出信用，A 输意味着抵押失效，Pool 优先收回本金以控制风险敞口，不再按正常输家规则分配 |
| A 赛事取消 | 资金池承担信用风险（不归还出资），B 按普通注单独立结算。**说明：** 此处"不归还出资"指 lockCreditBet 时从 Pool 扣减的 amount 不做退回，Pool 继续作为出资方承担 B 的对赌风险；B 自身盘口被取消时则直接退回出资（见 4.8） |

### 4.8 赛事取消

当赛事因故取消（如天气、安全等原因），平台需处理该赛事下所有盘口的注单：

**普通注单：**
- Admin 调用合约 `batchCancelMatch()` 批量取消该赛事所有盘口（或逐盘口调用 `cancelMatch()`）
- 所有 Pending 注单设为 Cancelled，锁定余额全额退还用户
- 若注单为信用仓位的抵押仓位，联动处理关联信用注单（见 4.7 "A 赛事取消"规则）

**串关注单（某腿赛事取消）：**

| 场景 | 处理 |
|------|------|
| 取消后剩余 ≥ 2 腿 | 取消该腿（视为赔率 1.0），重新计算组合赔率 = 原组合赔率 / 被取消腿赔率；剩余腿继续正常结算 |
| 取消后剩余 = 1 腿 | 串关退化为单注，赔率 = 该腿锁定赔率，stake 不变。**退化后不重新校验单注上限**（原始 stake 已通过串关规则校验，取消非用户过错，不应因退化而拒绝） |
| 取消后剩余 = 0 腿（所有赛事取消） | 全额退款 |

> 串关腿取消不影响已结算的其他腿状态。若串关已因某腿输球而标记为 Lost，赛事取消不追溯改判。
>
> **处理顺序说明：** 串关结算按赛事结束时间依次处理。若某腿先输导致整张串关 Lost，后续其他腿的赛事取消不会改变已有判定。这对用户而言是公平的：输球事实与取消事件是独立的，取消不改变已发生的输球结果。

## 五、Betting Pool（对赌池）

### 5.1 产品说明

Betting Pool 是平台庄家资金池，作为所有用户下注的对手方：
- 用户赢了，从池中赔付
- 用户输了，输掉的钱进入池中
- 信用仓位的资金由 Betting Pool 出借

### 5.2 LP 参与方式

| 环节 | 说明 |
|------|------|
| 存入 | 调用合约 `addLiquidity(amount)`，按比例获得 LP 份额 |
| 收益 | 按份额分得 Betting Pool 每期净收益（用户输掉金额的 70%） |
| 提取 | 调用 `removeLiquidity(shares)`，按份额取回本金+收益；提取受可用流动性限制，不可取出已被注单锁定的资金 |

### 5.3 收益分配

```
用户输掉 $100：
  $70 → Betting Pool（按 LP 份额分配）
  $30 → 平台

用户赢了 $100（赔率2.0，下注$100）：
  Betting Pool 赔出 $100（用户净赚）
```

### 5.4 预期收益参考

> 基于人均 $1,000 入金、3 次换手、9.1% 理论 Margin 的行业标准估算

| 用户规模 | LP 池总收益 | $20万 LP 池年化回报 |
|---------|-----------|-----------------|
| 1,000 人 | $273,000 | 约 136% |
| 3,000 人 | $819,000 | 约 410% |
| 6,000 人 | $1,638,000 | 约 819% |

> 实际收益与用户活跃度、盘口平衡情况相关，以上为理论估算。

## 八、错误码

| 错误码 | 合约 error | 含义 | 前端处理 |
|-------|-----------|------|---------|
| `INSUFFICIENT_BALANCE` | `InsufficientBalance()` | 余额不足 | 提示 + 去充值 |
| `BET_TOO_LARGE` | — (链下校验) | 超单注限额 | 提示最大可投额 |
| `DAILY_LIMIT_EXCEEDED` | — (链下校验) | 超每日限额 | 提示剩余额度 |
| `ODDS_CHANGED` | — (链下校验) | 赔率变动 | 弹窗确认新赔率 |
| `MARKET_RED_LIGHT` | `MarketRedLight()` | 红灯停止接单 | 按钮置灰 |
| `MARKET_NOT_OPEN` | `MarketNotOpen()` | 盘口未开放或已封盘 | 赔率置灰，提示"盘口不可下注" |
| `INSUFFICIENT_LIQUIDITY` | `InsufficientLiquidity()` | 池子流动性不足 | 提示减小金额 |
