# 文档索引

本目录是当前工程的文档总入口。

当前项目尚未完成，因此文档被明确拆成几个职责不同的目录。其中最需要优先区分的是：

- `architecture/`：目标架构、目标能力、产品与客户端设计
- `progress/`：当前代码真实状态, 按模块总结的目前项目状态
- `development/`：开发文档、实施清单、待开发任务与阶段计划
- `testing`: 测试文档，审计文档
- `research`: 复杂功能的调研文档
- `product`: 产品文档的存放位置
- `deployment`: 项目的部署文档，包括开发&测试&生产部署文档 

开始任何代码修改前，至少先阅读：

1. `docs/README.md`
2. `docs/progress` 当前开发现状
3. 与项目架构相关的 `docs/architecture/` 文档
4. 任务已有实施清单或开发文档 `docs/development/` 文档

## 目录结构

```text
docs/
├── README.md
├── architecture/
├── progress/
├── research/
├── deployment/
├── testing/
└── ...
```


## architecture/

用于存放项目架构设计包括开发规范等。

> 以下为文件命名示例，项目初始阶段部分文档可能尚未创建，属正常状态。

| 文件 | 说明 |
|------|------|
| `architecture/solidity-ddd-mapping.md` | **基础规范** — DDD 在本 Solidity 项目中的映射规则、目录结构与命名约定 |
| `architecture/xxx功能架构文档.md` | 当前xxx功能的架构文档，后续的xxx功能的开发都遵守目前这种架构 |

## progress/

用于存放当前项目的真实进度与阶段状态。

| 文件 | 说明 |
|------|------|
| `progress/xxx功能开发现状.md` | 当前版本的开发现状基线文档，后续功能完成、进行中、范围调整都要更新这里或在该目录追加新版本文档 |

## development/

用于归档开发文档、实施清单、任务拆分、待开发能力设计与阶段性落地计划。

适用内容：

- 开发实施清单
- 服务拆分任务
- 开发阶段计划
- 待开发能力说明

说明：

- 2026-03-31 新增 xxx功能的实施计划，后续开发以此为准

| 文件 | 说明 |
|------|------|
| `development/2026-03-31-xxx-plan.md` | **当前有效** — xxx 功能 完整实施计划 |



## research/

用于归档协议调研、第三方能力评估、技术选型比较与风险分析。

| 文件 | 说明 |
|------|------|
| `research/xxx-capability.md` | xxx 能力调研，结论：当前公开文档未确认支持 |

## deployment/

用于归档部署方式、环境变量说明、运维手册与上线检查项。

## testing/

用于归档测试方案、测试报告、联调记录与验收结论。


## product/

用于归档产品方案与会议结论。


## 维护规则

- `docs/` 根目录只允许保留 `README.md`
- 新文档必须进入已分类子目录，禁止继续在根目录堆散文件
- 架构、接口、交互设计变化先更新 `architecture/`，再改代码
- 新功能如果 `product` 有产品文档，需要对齐 `product` 产品文档和 `development` 开发文档。对齐标准：功能范围一致、接口定义无冲突、业务规则无矛盾。对齐之后才能变更代码进行开发
- 功能完成、功能变更中、实现范围变化，必须同步更新 `progress/`，`progress/` 里的文档必须按模块更新
- 功能开发需要在 `development/` 找到对应文档才能进行开发（豁免范围见 `AGENTS.md` 第1节豁免列表）
- 若**已有**设计文档与当前代码不一致，以当前代码和 `progress/` 为准，由人工控制决定是否回写设计文档。**新的变更**则必须先更新设计文档再改代码
