# AH 扩盘口最小改造调研

**日期：** 2026-05-24  
**状态：** 调研结论  
**目标：** 将 AH 完整支持集合扩展为 `-0.25 / -0.5 / -0.75 / -1 / -1.25 / -1.5 / +0 / +0.25 / +0.5 / +0.75`，并支持所有已开放线路的正确结算，同时尽量减少前端和后端新增调用复杂度。

说明：OU 的 `1.5 / 2.5 / 3.5` 已由现有 `marketType=2,line=0..2` 支持，本次不调整 OU；本次只是在 AH 现有 `-0.5 / -1 / -1.5` 基础上追加缺失的 7 条 AH line。

## 1. 背景

当前 `marketType + line` 模板只覆盖：

| marketType | line | 业务含义 |
|---:|---:|---|
| 0 | 0 | 1x2 |
| 1 | 0 | AH -0.5 |
| 1 | 1 | AH -1 |
| 1 | 2 | AH -1.5 |
| 2 | 0 | OU 1.5 |
| 2 | 1 | OU 2.5 |
| 2 | 2 | OU 3.5 |

代码事实：

- `BettingConstants.ASIAN_HANDICAP_LINE_COUNT = 3`
- `BettingOddsLib.validateTemplate` 只校验 `marketType == 1 && line < ASIAN_HANDICAP_LINE_COUNT`
- `openMarket` 先执行模板校验，再创建 `marketId = keccak256(abi.encode(matchId, marketType, line))`

因此，单纯开放更多 AH 盘口时，链上最小入口是扩 `line` 编码范围；但四分之一线和 `+0` 还涉及 Push / 半赢 / 半输结算，不能只改白名单。

## 2. 外部盘口规则核对

亚洲让球四分之一线的通用规则是将投注拆成相邻两条线的一半一半：

- `-0.25` = 一半 `+0`，一半 `-0.5`
- `-0.75` = 一半 `-0.5`，一半 `-1`
- `-1.25` = 一半 `-1`，一半 `-1.5`
- `+0.25` = 一半 `+0`，一半 `+0.5`
- `+0.75` = 一半 `+0.5`，一半 `+1`

外部资料均指向同一结论：四分之一线会出现 full win、full loss、half win、half loss；整数线 `0 / 1 / ...` 会出现 full push。参考：

- https://arbworld.net/en/info/handicap-outcomes-explained
- https://handicap-bet.com/articles/quarter-asian-handicap-explained-025/
- https://statsbet.org/blog/asian-handicap-explained

## 4. 结算复杂度来源

当前合约正常结算只有两类结果：

1. 某个 outcome 全赢：`claimablePayout = stake * odds`
2. 其他 outcome 全输：`loserStakes += stake`

当前 Push 只通过 `pushRefundMarket` 对 `marketType=1,line=1` 做全额退款。

新增盘口后会出现以下情况：

| 结算结果 | 用户资金结果 | 当前模型是否原生支持 |
|---|---|---|
| full win | 全额按赔率待 claim | 支持 |
| full loss | 全额输 | 支持 |
| full push | 全额退本金，不收派奖税 | 仅通过退款路径间接支持 |
| half win | 50% 本金退回，50% 按赔率待 claim | 不支持 |
| half loss | 50% 本金退回，50% 输 | 不支持 |

如果把 half win / half loss 交给后端用 `refundBets + settleMarketBets` 拼出来，后端必须逐笔计算退款金额、处理 bet 分页和状态顺序，调用复杂度明显上升，不符合本次目标。

进一步看，如果后端还要分别为 1X2、AH、OU 维护 `winningOutcome / settlementCode` 推导规则，所有线路的结算复杂度仍会散在链下。更稳的方向是：**后端提交比分，合约按 marketType + line 统一推导结算结果。**

## 5. 最终方案：分批比分结算

- `settleMarketBetsByScore(bytes32 marketId, uint16 homeScore, uint16 awayScore, bytes32[] betIds)`

链上根据 `marketType + line + homeScore + awayScore` 算出每笔 bet 的 full win / half win / push / half loss / full loss。

覆盖范围：

- 1X2：按 `homeScore / awayScore` 推导 home win / draw / away win；
- AH：按 `homeScore - awayScore` 与 AH line 推导 full / half / push；
- OU：按 `homeScore + awayScore` 与 OU line 推导 over / under。

确定规则：

1. AH line 扩到 10 条，旧 line 编码不变。
2. 不新增前端下注接口。
3. 不新增后端 refund 编排流程。
4. 新增唯一正常赛果结算入口 `settleMarketBetsByScore`，链上统一推导 1X2 / AH / OU 的结算结果。
5. 删除旧 `settleMarket`，避免后端在全量/分批/终态标记多套路径间选择。
6. 删除旧 `settleMarketBets(marketId, winningOutcome, betIds)` 和 `pushRefundMarket`，从 ABI 移除，正常赛果与 full push 都走 score-based 分批结算。
7. 将 `finalizeMarketSettlement` 改为统一终态收口入口，参数带 `resultKindRaw`：
   - `0 = Settled`：要求 score-based 分批结算已处理完全部 bet，然后完成 margin / 瀑布 / market `Settled`；
   - `1 = Refunded`：不要求分批赛果结算，直接把 market 标记为 `Refunded`，后续真实退款继续走 `refundBets` 分批；
   - `2 = Cancelled`：不要求分批赛果结算，直接把 market 标记为 `Cancelled`，后续真实退款继续走 `refundBets` 分批。
8. `finalizeMarketSettlement(marketId, 0/1/2)` 必须等比赛结束后才能调用；正常结算、取消、退款都不允许赛前或赛中提前终态化。
9. 一旦某个 market 已开始 score-based 分批结算，禁止再 finalize 为 `Refunded / Cancelled`。

该方案把复杂资金逻辑留在合约内，后端只需要提交最终比分：

```text
settleMarketBetsByScore(marketId, homeScore, awayScore, betIds)
finalizeMarketSettlement(marketId, 0)
```

退款/取消场景：

```text
finalizeMarketSettlement(marketId, 1 or 2)
refundBets(marketId, betIds, refundAmounts)
```

零下注 market：

```text
finalizeMarketSettlement(marketId, 0)
```

若该 market 没有任何 bet，允许比赛结束后直接正常结算为 `Settled`，不需要先调用 `settleMarketBetsByScore`。
该路径不记录比分；若索引侧需要赛事比分，应以赛事结果源为准，不能把事件中的默认比分当作真实比分。

## 6. 统一比分结算口径

本次推荐的结算目标是：**前端不新增结算概念，后端不逐笔拼退款，也不维护各线路胜负矩阵，链上根据比分完成 1X2 / AH / OU 的结算推导与 full / half / push 资金拆分。**

### 6.1 结算入口

旧入口处理口径：

- `settleMarket(marketId, resultKindRaw, winningOutcome)`：删除，不再承担正常赛果结算，也不再承担 `Refunded / Cancelled` 终态标记。
- `settleMarketBets(marketId, winningOutcome, betIds)`：删除并从 ABI 移除，避免和 score-based 分批结算双轨并存。
- `pushRefundMarket`：删除并从 ABI 移除；`-1` 与新增 AH line 的 full push 均由 score-based 分批结算处理，减少后端可调用结算方法数量。

新增推荐入口：

- `settleMarketBetsByScore(bytes32 marketId, uint16 homeScore, uint16 awayScore, bytes32[] betIds)`
- `finalizeMarketSettlement(bytes32 marketId, uint8 resultKindRaw)`

说明：

- `resultKind=Refunded/Cancelled` 不是比分结算，但可以由 `finalizeMarketSettlement` 统一做终态标记；
- `homeScore/awayScore` 是最终确认比分；本方案建议单队比分上限先定为 `50`，超过则 revert，避免异常输入污染结算；
- 1X2 默认 outcome `0/1/2 = home/draw/away`；
- AH 默认 outcome `0 = home side with line`，outcome `1 = away side against line`；链上只接受主队视角 AH line；
- OU 默认 outcome `0 = Over`，outcome `1 = Under`。
- 即使 bet 数量很少，正常赛果也统一走 `settleMarketBetsByScore -> finalizeMarketSettlement(marketId, 0)`，不再提供全量结算捷径。
- `finalizeMarketSettlement(marketId, 1/2)` 只标记 market 终态，不遍历 bet、不计算 margin、不执行瀑布；真实逐笔退款仍由 `refundBets` 完成。
- `finalizeMarketSettlement(marketId, 0/1/2)` 必须满足 `block.timestamp >= matchEndTime`。
- `finalizeMarketSettlement(marketId, 1/2)` 必须在 score-based 分批结算开始前调用；若 `marketSettlementProgress.active == true`，必须 revert。

### 6.2 AH 客队视角归一化

为避免新增 `lineSide` 字段、改变 `marketId` 组成或让前端/后端面对主客两套结算语义，链上 AH 统一采用主队视角：

- `line` 永远表示主队让球；
- outcome `0` 永远表示主队按该 line 结算；
- outcome `1` 永远表示客队作为对手侧结算；
- `homeScore / awayScore` 使用真实比分。

如果数据源返回的是客队视角盘口，后端在开盘前必须归一化：

```text
homeLine = -awayLine
baseOdds[0] = home side odds
baseOdds[1] = away side odds
```

示例：

| 数据源盘口 | 链上归一化 |
|---|---|
| away -0.5 / home +0.5 | `line = +0.5`，`baseOdds[0] = home +0.5 odds`，`baseOdds[1] = away -0.5 odds` |
| away +0.25 / home -0.25 | `line = -0.25`，`baseOdds[0] = home -0.25 odds`，`baseOdds[1] = away +0.25 odds` |

如果未来必须链上同时表达“同一 match 同一数值但不同队伍视角”的盘口，则需要改变 market identity，例如引入 `lineSide` 或把主客视角编码进新的 line 范围；这会改变 `marketId = keccak256(matchId, marketType, line)` 的设计，不属于本次最小改造。

### 6.3 单笔 bet 资金拆分

链上对每笔 pending bet 先计算未处理本金：

```text
currentStake = acceptedAmount - refundedAmount
```

再按 bet 所选 outcome 的推导结果拆成三段：

| 单笔结果 | refundStake | winStake | lossStake |
|---|---:|---:|---:|
| full win | 0% | 100% | 0% |
| full loss | 0% | 0% | 100% |
| full push | 100% | 0% | 0% |
| half win | 50% | 50% | 0% |
| half loss | 50% | 0% | 50% |

half win / half loss 的整数拆分口径：

```text
halfStake = currentStake / 2
remainder = currentStake - halfStake * 2

half win:
    refundStake = halfStake + remainder
    winStake = halfStake
    lossStake = 0

half loss:
    refundStake = halfStake + remainder
    winStake = 0
    lossStake = halfStake
```

余数统一归入 `refundStake`，避免因为不可整除而多计 win/loss、margin 或 payout tax。

账务处理：

- `refundStake`：结算交易中立即退回用户，增加 `bet.refundedAmount`；不收派奖税。
- `winStake`：按 `winStake * lockedOdds / ODDS_RATE_SCALE` 写入 `claimablePayout`，后续用户正常 `claimPayout`；派奖税只对这部分 gross payout 计算。
- `lossStake`：计入 `loserStakes`，用于 L1 抵扣。
- `SettlementContext.totalStake` 只累计 `winStake + lossStake`，不把 push/refund 部分计入 margin。
- market 级 `netLoss = grossPayout - loserStakes` 仍按现有 L1/L2/L3/L4 瀑布处理。
- score-based 分批结算对每笔 bet 只做一次风险释放：`unsettledStake` 与 `potentialPayoutCommitted` 按 `currentStake` / `releasedPotentialPayout` 全量释放；`refundStake` 只负责转账和记录 `refundedAmount`，不得再复用会二次扣减风险账本的退款 rollback 逻辑。

对于 1X2 / OU，因为现有开放线路不会出现 half win / half loss：

- full win：`winStake = currentStake`
- full loss：`lossStake = currentStake`
- OU 当前 `1.5 / 2.5 / 3.5` 不存在 push
- 1X2 draw 是 outcome 1 full win，不是 push

### 6.4 市场状态

AH full push 走 `resultKindRaw=0` 正常结算路径，并让 market 最终进入 `Settled`：

- market 是“有赛果的已结算市场”，不是取消或无效市场；
- bet 可以全部是 `Refunded`；
- 不需要后端再调用 `refundBets`；
- 不再依赖 `pushRefundMarket`。
- 资金口径：full push 的每笔 bet `refundStake = currentStake`，`winStake = 0`，`lossStake = 0`，`grossPayout = 0`，`loserStakes = 0`，`totalStake = 0`，不产生 margin、不走瀑布、不征派奖税。

### 6.5 1X2 结算推导

| 比分关系 | winning outcome |
|---|---:|
| `homeScore > awayScore` | 0 |
| `homeScore == awayScore` | 1 |
| `homeScore < awayScore` | 2 |

### 6.6 OU 结算推导

OU line 编码保持现状：

| line | OU | threshold goals |
|---:|---|---:|
| 0 | 1.5 | 1.5 |
| 1 | 2.5 | 2.5 |
| 2 | 3.5 | 3.5 |

链上可用半球单位表示，避免小数：

| line | threshold half-goals |
|---:|---:|
| 0 | 3 |
| 1 | 5 |
| 2 | 7 |

推导：

```text
totalHalfGoals = (homeScore + awayScore) * 2
if totalHalfGoals > thresholdHalfGoals:
    outcome 0 Over full win
else:
    outcome 1 Under full win
```

### 6.7 AH 结算推导口径

约定 outcome 0 是“选择 line 所描述的一侧”，outcome 1 是对手侧。`scoreDiff = side0Score - side1Score`。

`line` 可映射为 quarter units：

| line | AH | quarter units |
|---:|---|---:|
| 0 | -0.5 | -2 |
| 1 | -1 | -4 |
| 2 | -1.5 | -6 |
| 3 | -0.25 | -1 |
| 4 | -0.75 | -3 |
| 5 | -1.25 | -5 |
| 6 | +0 | 0 |
| 7 | +0.25 | 1 |
| 8 | +0.5 | 2 |
| 9 | +0.75 | 3 |

对 quarter line，可拆为相邻两条半注线分别结算，再合并成 code：

- 两半都赢：code 0
- 两半都输：code 1
- 两半都 push：code 2
- 一赢一 push：code 3
- 一输一 push：code 4

从 outcome 1 视角自动取反：

- outcome 0 code 0 -> outcome 1 full loss
- outcome 0 code 1 -> outcome 1 full win
- outcome 0 code 2 -> outcome 1 full push
- outcome 0 code 3 -> outcome 1 half loss
- outcome 0 code 4 -> outcome 1 half win

- AH `+0.5` draw -> outcome 0 full win
- AH `+0.25` draw -> outcome 0 half win / outcome 1 half loss
- AH `+0.75` 客队赢 1 球 -> outcome 0 half loss / outcome 1 half win
- AH `-1` 主赢 1 球 -> full push，market `Settled`，相关 bet `Refunded`
- score-based batch settlement 半赢/半输后 `finalizeMarketSettlement`
- batch settlement 第二批使用不同比分必须 revert
- `finalizeMarketSettlement(marketId, 0)` 未处理完全部 bet 必须 revert
- `finalizeMarketSettlement(marketId, 0)` 在 `block.timestamp < matchEndTime` 时必须 revert
- 已开始 score-based 分批结算后，`finalizeMarketSettlement(marketId, 1/2)` 必须 revert
- `finalizeMarketSettlement(marketId, 1/2)` 可将 market 标记为 `Refunded/Cancelled`，且不遍历 bet、不计算 margin、不执行瀑布
- `finalizeMarketSettlement(marketId, 1/2)` 后 `refundBets` 可继续分批真实退款
- `finalizeMarketSettlement(marketId, 1/2)` 在 `block.timestamp < matchEndTime` 时必须 revert
- 旧 `settleMarket(...)` 必须已从 ABI 删除
- 旧 `settleMarketBets(..., winningOutcome, ...)` 必须已从 ABI 删除
- 旧 `pushRefundMarket(...)` 必须已从 ABI 删除
- half win 订单 `claimPayout` 只对 winning half 的 gross payout 收派奖税
- full push 订单不产生 `claimablePayout`，不征派奖税，不产生 margin，不走瀑布
- `MarketSettlementScoreBatchProcessed` 或升级后的批次事件记录比分与处理进度
- `MarketSettlementFinalized` 事件记录终态与结算汇总；当 `scoreSettled=true` 时同时记录比分，索引侧不依赖旧 `winningOutcome` 还原比分

## 8. 待确认点

以下不是扩 AH line 的基础阻塞，但进入架构/开发文档前需要确认：

1. 零下注 market 直接 `finalizeMarketSettlement(marketId, 0)` 时不携带比分；如果索引侧要求所有 `Settled` market 都有链上比分，需要额外设计比分记录入口或调整 `finalizeMarketSettlement` 参数。
2. 本方案删除旧 `MarketSettled` 事件，统一使用 `MarketSettlementFinalized`；测试网重部署可接受，但后端索引需要同步切换事件订阅。
3. `MAX_SETTLEMENT_SCORE = 50` 是建议值；如产品希望允许更极端比分，需要在实现前调整常量。
4. 半赢/半输不新增 `BetSettlementState`，用 `refundedAmount + WonUnclaimed/Lost` 表达；如果前端需要直接区分 half win / half loss，需要另加事件字段或状态字段。

## 9. 风险与注意事项

1. 新增 score-based 分批入口会改变后端结算参数：从 `winningOutcome/code` 改为 `homeScore/awayScore + betIds`。
2. `finalizeMarketSettlement` 新增 `resultKindRaw` 参数后，后端正常结算固定传 `0`；退款/取消固定传 `1/2`。
3. 旧 `MarketSettled` 事件删除，索引侧统一消费 `MarketSettlementFinalized`；旧 `winningOutcome` 不再作为结算事件字段。
4. half win / half loss 中的退款会在 settle 阶段立即转账，`claimPayout` 只领取 winning half。
5. half win / half loss 遇到奇数最小单位本金时，余数归入退款本金，不进入 win/loss 结算本金。
6. `totalMargin` 应基于扣除 push/refund 后的实际结算本金，不应对退回本金收 margin。
7. 分批结算必须保证同一 market 的所有 batch 使用同一比分；本方案在 progress 中记录 `homeScore/awayScore`，第二批开始比分不一致必须 revert。
8. `finalizeMarketSettlement(marketId, 1/2)` 只标记 market 终态，真实退款仍依赖后续 `refundBets`；后端不能把终态标记误认为用户已到账。
9. 当前 `BetSettlementState` 不新增状态，半赢/半输通过 `refundedAmount + settlementState` 组合表达；前端展示需按组合状态解释。
10. 合约需要明确 score 上限，避免异常比分造成不必要的整数范围风险；建议先采用 `MAX_SETTLEMENT_SCORE = 50`，后续如产品需要再调整。
11. 链上 AH 统一主队视角；若后端未归一化客队视角盘口，会导致所有 AH score-based 结算反向。
12. 当前处于测试网阶段，可重新部署整套合约，不要求处理旧部署的存储兼容迁移；该结论不能自动外推到主网升级。
