## 2. 当前代码主结论

### 2.1 Token 已极简化

- `ODDToken` 只保留 ERC20、pause、upgrade、角色
- 不再承载买税、卖税、推荐关系、成本价、swap

### 2.2 BettingPool 是主业务中心

当前以下逻辑都收口到 `BettingPool`：

- 市场创建与赔率更新
- 下单风控
- Cash Out 提前结算
- 下注税
- 派奖税
- 推荐关系
- 推荐奖励主账
- ODD 直领推荐奖励
- USDT 签名领取推荐奖励
- score-based 正常赛果结算

其中：

- 对外结算入口仍在 `BettingPool`
- Cash Out / 结算 / 退款 / 瀑布重逻辑当前已迁到 `BettingSettlementModule`
- `BettingPool` 通过 `delegatecall` 路由到模块执行
- 正常赛果结算通过 `getMarketBetIds -> settleMarketBetsByScore -> finalizeMarketSettlement(marketId,0)` 分批完成，避免单笔交易扫全量注单

### 2.3 Staking / Liquidity 已被重新收口

- `StakingPool.notifyReward` 只接 `BettingPool`
- `StakingPool.notifyReward` 不受 `StakingPool.pause()` 阻断，避免已结算胜单领奖卡死
- `StakingPool` 现在支持治理动态调整最小质押量、VIP 门槛和每日限额
- `LiquidityPool.distributeLoss` 会回传 L2 实际扣减值
- `LiquidityPool` 现在支持治理动态调整最小存入量和解绑等待 Epoch
- `BettingPool` 现在支持治理动态调整信号灯阈值和 LP Margin 分成比例
- `LiquidityPool` 仍保留旧字段名，但当前语义按新规则运行

### 2.4 BettingSettlementModule 承接重结算逻辑

- `settleMarketBetsByScore`
- `finalizeMarketSettlement`
- `refundBets`
- `cashOut`
- `claimPayout`
- 瀑布、税缓冲、LP loss offset 更新
- 所有执行仍写入 `BettingPool` 的 proxy storage

## 6. 当前部署补充

- `BettingPool` 现在依赖额外部署的 `BettingSettlementModule`
- 部署完成后必须执行 `BettingPool.setSettlementModule(...)`
- `BettingSettlementModule` 是实现模块，不作为前后端直接调用入口
- `setBettingDependencies(...)` 只用于依赖全空的 bootstrap / migration，一旦 ODDToken、StakingPool、LiquidityPool 任一依赖已设置，就不能用于运行期热替换。

## 4. 当前推荐奖励实现

推荐奖励当前有两种领取方式：

1. `claimReferralRewards(uint256 oddAmount)`
   - 直接领取 ODD
2. `claimUSDTReferralRewards(...)`
   - 走签名授权
   - 通过治理配置的 Pancake V3 Router 和 USDT token 直接换成 USDT
   - 用 USDT 余额前后差额校验真实到账量

共同点：

- 主账都在 `referrerRewardsOdd`
- 推荐奖励首先按 ODD 累积
