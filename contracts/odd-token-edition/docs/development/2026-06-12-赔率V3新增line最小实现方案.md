# 赔率 V3 新增 line 最小实现方案

**日期：** 2026-06-12
**状态：** 已本地实现并发布到 BSC Testnet，当前 `BettingPool` proxy 可用
**产品基线：** `docs/product/赔率_规则设计_V3.md`
**实现基线：** 当前 AH 扩盘口、score-based settlement、赔率 V2 WCL、手动封锁、Cash Out、串关 MVP、BettingPool 模块化入口壳

## 1. 目标

本次只实现 V3 新增 line 的最小闭环：

1. AH 追加支持 `line=10/11/12`，分别表示主队 `-1.75 / -2 / -3`。
2. OU 追加支持 `line=3..10`，分别表示 `0 / 0.5 / 1 / 1.75 / 2 / 2.25 / 2.75 / 3`。
3. 保留当前所有已实现 line，不因 V3 产品文档历史遗漏而下线。
4. 保持当前四分之一线单 market 语义，不引入 `sub_bet`、`parent_line` 或链上拆单。
5. 保持当前 WCL、信号灯、红灯容量、Cash Out、串关和 LP 瀑布语义。

## 2. 非目标

本期不做以下改动：

- 不重排既有 line 编码；
- 不新增市场类型；
- 不修改 `openMarket / updateOdds / placeBet / settleMarketBetsByScore / finalizeMarketSettlement` 外部函数签名；
- 不新增 storage 字段，不改 proxy storage layout；
- 不支持 AH `-2.25 / -2.5 / -2.75`；
- 不把四分之一盘口拆成两条子 market；
- 不修改 Base Odds、WCL 或滑点公式。

## 3. 实现前失败原因

实现前 V3 新 line 开盘失败发生在开盘模板校验阶段：

```text
BettingPool.openMarket
  -> BettingMarketModule.openMarket
  -> BettingOddsLib.validateTemplate
```

实现前常量为：

```solidity
ASIAN_HANDICAP_LINE_COUNT = 10;
OVER_UNDER_LINE_COUNT = 3;
```

因此：

- AH 只允许 `line < 10`，`line=10/11/12` 会 revert `MarketTemplateNotAllowed`；
- OU 只允许 `line < 3`，`line=3..10` 会 revert `MarketTemplateNotAllowed`。

即使只放开常量也不够，因为 `BettingScoreResultLib` 当前只解析 AH `0..9` 和 OU `0..2`。所以本期最小实现必须同时补齐模板计数和 score-based settlement resolver。

## 4. 下注到结算路径核对

对照产品文档，本期新增 line 的产品功能必须覆盖“可开盘 -> 可报价/更新赔率 -> 可下注 -> 可结算 -> 可领取/退款 -> 可进入串关结算”整条链路。最小修改不是只改常量，而是只在必要节点打开新 line，其他 line-agnostic 路径保持复用。

| 路径 | 产品要求 | 当前代码机制 | V3 最小动作 |
|---|---|---|---|
| 开盘 `openMarket` | AH `10..12`、OU `3..10` 能作为独立 market 开盘 | `BettingOddsLib.validateTemplate(marketType,line,baseOdds.length)` 用 line count 判定合法模板 | 必须更新 AH/OU line count；每个新增 line 仍要求 `baseOdds.length == 2` |
| marketId | 新 line 是独立 market，不拆子 market | `marketId = keccak256(abi.encode(matchId, marketType, line))` | 不改，天然保证不同 line 独立 |
| 赔率更新 `updateOdds` | 每条 line 独立维护 odds / quoteVersion | 只校验 `baseOdds.length == market.outcomeCount` | 不改；新增 line 开盘后同样是二元 market |
| 预览/信号灯 `previewSignal` | WCL、信号灯、滑点沿用 V2 | 只依赖 market exposure、odds、outcomeCount | 不改；新增 line 独立维护 `S_i/P_i` |
| 普通下注 `placeBet` | 新 line 可下注，注单结构不变 | `BettingValidationLib.validateMarketGuard` 只校验 `outcome < outcomeCount` | 不改；新增 line 的 `outcomeCount=2` 后自动可下注 |
| Cash Out / 估值 | 保持当前 Cash Out 与过程估值语义 | 按 market odds、`lockedOdds`、remaining stake 计算，不按 line 分支 | 不改；新 line 赛前 Cash Out 自动复用 |
| 普通结算 `settleMarketBetsByScore` | 新整数线支持 full push，新四分之一线支持 half win/loss | 每笔调用 `BettingScoreResultLib.resolve` 再走 `_resolveBetBreakdown` | 必须改 resolver；资金拆分不改 |
| 结算收口 `finalizeMarketSettlement` | 结算后 margin、payout tax、瀑布沿用现状 | 使用批处理累计的 `totalStake/grossPayout/loserStakes` | 不改；由 resolver 输出决定累计结果 |
| 领取/退款 `claimPayout` | win/half win 可领取，push/half refund 退款正确落账 | 结算时写 `claimablePayout/refundedAmount/settlementState` | 不改；测试必须覆盖 claimable/refund 结果 |
| 串关下注 `placeParlay` | 新 line 可作为 leg，full push/half 语义保持 | leg snapshot 存 `marketType/line/outcome/lockedOdds`，只校验 `outcome < outcomeCount` | 不改下注；必须保证 resolver 支持新 line |
| 串关结算/估值 | full push 不计入组合；half win/half loss 使用现有组合因子 | `BettingParlayModule` 和 `BettingParlayLens` 都复用 `BettingScoreResultLib.resolve` | resolver 一处修改即可覆盖；测试必须覆盖新增 OU/AH 的 push/half leg |

核对结论：

- 产品文档要求的“新增 line 完整下注到结算”不能只改 `ASIAN_HANDICAP_LINE_COUNT / OVER_UNDER_LINE_COUNT`；
- 最小且完整的实现必须包含三类改动：line 编码/计数、score-based resolver、端到端测试与文档同步；
- `placeBet / updateOdds / previewSignal / cashOut / claimPayout / finalizeMarketSettlement` 本身不需要新增 line 分支，强行修改反而会扩大风险面；
- 串关产品语义由同一个 resolver 继承，必须纳入回归测试，否则普通单注正确但串关 half/push 可能漏验。

## 6. 最小代码触点

结算也必须修改，但本期只修改“比分到结算结果”的推导层，不改结算入口和资金流：

- `settleMarketBetsByScore` 的外部签名、批处理流程、比分一致性校验继续保持现状；
- `finalizeMarketSettlement(marketId, 0)` 的收口条件和瀑布结算继续保持现状；
- `_resolveBetBreakdown` 的 `FullWin / FullLoss / FullPush / HalfWin / HalfLoss` 资金拆分继续保持现状；
- 必须修改 `BettingScoreResultLib.resolve`，让新增 AH/OU line 能从比分推导出正确 `Result`；
- 串关、串关估值和普通单注结算都复用 `BettingScoreResultLib.resolve`，因此 resolver 一处变更会自然覆盖这些结算路径。


### 6.3 `src/modules/betting/BettingScoreResultLib.sol`

本期核心改动在 resolver：

1. `resolve` 中 OU 分支需要校验 `betOutcome <= 1`。
2. OU 不再只用 threshold half-goals 推导 full win/full loss，需要按逐线返回 `FullWin / FullLoss / FullPush / HalfWin / HalfLoss`。
3. AH `resolveAhHomeResult` 追加 `line=10/11/12`。
4. `opposite` 继续复用现有逻辑，保证 Under 和 AH 客队方向自动取反。

建议结构：

```solidity
if (marketType == 2) {
    if (betOutcome > 1) revert SettlementCannotClose(bytes32(0));
    Result overResult = resolveOuOverResult(line, homeScore + awayScore);
    return betOutcome == 0 ? overResult : opposite(overResult);
}
```

保留当前 `MAX_SETTLEMENT_SCORE` 校验，`homeScore + awayScore` 最大为 `100`，在 `uint16` 内安全。

## 7. 新增结算规则

### 7.1 AH 新增 line

`scoreDiff = homeScore - awayScore`。下表为 `outcome=0` 主队方向；`outcome=1` 使用 `opposite`。

| line | home 盘口 | `outcome=0` 结果 |
|---:|---|---|
| 10 | `-1.75` | `scoreDiff >= 3` full win；`scoreDiff == 2` half win；`scoreDiff <= 1` full loss |
| 11 | `-2` | `scoreDiff >= 3` full win；`scoreDiff == 2` full push；`scoreDiff <= 1` full loss |
| 12 | `-3` | `scoreDiff >= 4` full win；`scoreDiff == 3` full push；`scoreDiff <= 2` full loss |

### 7.2 OU 新增 line

`totalGoals = homeScore + awayScore`。下表为 `outcome=0` Over；`outcome=1` Under 使用 `opposite`。

| line | 盘口 | Over 结果 |
|---:|---|---|
| 3 | `0` | `totalGoals >= 1` full win；`totalGoals == 0` full push |
| 4 | `0.5` | `totalGoals >= 1` full win；`totalGoals == 0` full loss |
| 5 | `1` | `totalGoals >= 2` full win；`totalGoals == 1` full push；`totalGoals == 0` full loss |
| 6 | `1.75` | `totalGoals >= 3` full win；`totalGoals == 2` half win；`totalGoals <= 1` full loss |
| 7 | `2` | `totalGoals >= 3` full win；`totalGoals == 2` full push；`totalGoals <= 1` full loss |
| 8 | `2.25` | `totalGoals >= 3` full win；`totalGoals == 2` half loss；`totalGoals <= 1` full loss |
| 9 | `2.75` | `totalGoals >= 4` full win；`totalGoals == 3` half win；`totalGoals <= 2` full loss |
| 10 | `3` | `totalGoals >= 4` full win；`totalGoals == 3` full push；`totalGoals <= 2` full loss |

已有 OU line 保持当前语义：

| line | 盘口 | Over 结果 |
|---:|---|---|
| 0 | `1.5` | `totalGoals >= 2` full win；`totalGoals <= 1` full loss |
| 1 | `2.5` | `totalGoals >= 3` full win；`totalGoals <= 2` full loss |
| 2 | `3.5` | `totalGoals >= 4` full win；`totalGoals <= 3` full loss |

## 11. 风险与对抗性检查

1. **编码兼容性**：只能追加 enum 和 line count，不能重排 `0..9` 与 `0..2`，否则历史 marketId 与前后端认知会错位。
2. **开盘与结算一致性**：只放开 `line count` 不够，resolver 必须覆盖同一范围，否则可开盘但赛后无法结算。
3. **OU `line=0` 边界**：Under 0 在 `totalGoals=0` 是 push，`totalGoals>=1` 是 full loss；不存在 `totalGoals < 0` 的 winning 区间。
4. **半赢半输余数**：继续复用当前资金拆分，奇数 wei 的余数进入退款半边，不引入新 rounding。
5. **OU 反向结果遗漏**：OU 产品表写的是 Over 结果，Under 依赖 `opposite`；测试若只测 Over，会漏掉 Under half win/half loss 与 push。
6. **串关继承影响**：串关和进行中估值复用 resolver，新 line 会自动影响 leg settlement，需要最小回归防止 half/push 组合因子偏移。
7. **合约体积**：新增分支集中在 `BettingScoreResultLib`，应关注 `BettingSettlementModule / BettingParlayModule / BettingParlayLens` 链接后体积，但预计不触碰 `BettingPool` storage 或入口壳。
8. **文档状态**：实现前产品文档应保持“待合约落地”；实现后再同步 progress/API/testing，避免文档提前宣称已上线。
9. **端到端误判风险**：若测试只覆盖 `openMarket` 和 resolver unit-like helper，可能漏掉下注、finalize、claim/refund 或串关路径；本期验收必须有新 line 的完整路径样例。
