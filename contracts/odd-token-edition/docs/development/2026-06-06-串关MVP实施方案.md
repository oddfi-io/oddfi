## 1. 背景与目标

产品文档已预留串关规则：

| 产品规则 | 本期落地口径 |
| --- | --- |
| 同场禁止串关 | 同一 `matchId` 在一张串关单中只能出现一次 |
| 总赔率上限 | `lockedComboOdds` 最高 `200x`，超过按 `200x` 截断并通过 preview 暴露 |
| 最高赔付上限 | 单张串关最高 gross payout `30,000 ODD` |
| 最大腿数 | `2串1` 到 `6串1` |
| 支持市场 | 当前已实现的 `1X2 / AH / OU` |

当前 Solidity 实现没有串关入口，`BettingPool.placeBet(...)` 只支持单个 `marketId + outcome` 的单注。上一版方案把串关设计成独立 `ParlayPool + parlayReserve`，虽然实现隔离，但和当前体系兼容性不足：

1. 会绕开 `BettingPool` 的下注税、派奖税、推荐奖励和 USDT 推荐领取主账；
2. 会绕开 `StakingPool.getUserDailyLimit`、活跃质押额和未结算仓位限制；
3. 会绕开 `MarketExposure`、WCL 信号灯和赔率压缩；
4. 会绕开 `LiquidityPool.distributeLoss / requestPayoutLiquidity` 的 `onlyBettingPool` 限制；
5. 会新增一套独立准备金，和当前 `platformReserve / taxBuffer / lpLossOffsetRemaining` 形成双账本。

因此本期重新设计为：

```text
用户
  -> BettingPool.placeParlay(...)
      -> delegatecall BettingParlayModule
          -> 写 BettingPool proxy storage
          -> ODDToken 转账
          -> StakingPool 读取 VIP / 活跃质押
          -> LiquidityPool 通过 BettingPool 地址走现有 L2/L3/L4 瀑布
```

`BettingParlayModule` 是新增合约，但不是独立业务资金池。它和当前 `BettingSettlementModule` 类似，只承载重逻辑；串关注单、风险、税、派奖和资金仍由 `BettingPool` 作为聚合根 owner。

## 2. 本期支持范围

| 能力 | 本期结论 |
| --- | --- |
| 串关类型 | `2串1` 到 `6串1` |
| 支持 market | 当前 `BettingPool` 已开出的 `1X2 / AH / OU` |
| AH 结果 | 复用当前 full win / full loss / full push / half win / half loss |
| OU 结果 | 当前 `.5` 线，无 Push |
| 同场限制 | 同一 `matchId` 只能出现一个 leg |
| Quote guard | 每个 leg 都校验 `quoteVersion / updatedAt / minOdds` |
| 部分成交 | 不支持；任一 leg 风控不足则整张串关失败 |
| Cash Out | 禁止串关 Cash Out；不设计、不预留、不暴露任何提前结算入口 |
| 下注税 | 复用 `BettingPool.betTaxBps` 和推荐奖励路径 |
| 派奖税 | 复用 `BettingPool.payoutTaxBps` 和 staking / taxBuffer / platform / referrer 分配 |
| VIP 限额 | 串关 stake 计入同一个 `userRiskLedger.dailyAcceptedAmount` |
| 未结算仓位 | 串关 stake 计入同一个 `userRiskLedger.unsettledStake` |
| 单张最高赔付 | `grossPayout <= BettingConstants.SINGLE_MATCH_PAYOUT_CAP`，当前为 `30,000 ODD` |
| 流动性 | 复用 Global LP 可请求流动性 + `taxBuffer + platformReserve`；不使用任一单场 Match Pool 承担跨场串关 |
| 结算 | 等所有 leg 的底层 market 终态后，由 `settleParlay(parlayId)` 读取 `BettingPool` 持久化赛果结算 |

不支持项必须在前端隐藏或置灰，不允许产品层显示为已上线能力。

串关 Cash Out 是硬禁用项，不是延期功能。原因是串关赔付依赖多个 leg 的联合状态，只要存在未终态 leg，就无法用当前单 market 赔率安全释放 synthetic exposure、用户未结算仓位和 Global LP payout window。强行提前 Cash Out 会导致结算和账务不闭合。

## 3. 当前代码约束

### 3.1 `BettingPool` 是业务聚合根

当前以下状态已经由 `BettingPool` owner：

- market 与 odds；
- single bet 注单；
- `userRiskLedger`；
- `userMarketExposure`；
- 推荐关系与 `referrerRewardsOdd`；
- `platformReserve / taxBuffer / lpLossOffsetRemaining / accountedBalance`；
- `settlementModule`；
- 结算、Cash Out、claimPayout 和四层瀑布。

串关必须接入这些状态，否则会造成单注和串关两套风控、两套税、两套资金池。

### 3.2 `LiquidityPool` 只认 `BettingPool`

当前 `LiquidityPool.requestPayoutLiquidity`、`distributeLoss`、`distributeMargin` 都是 `onlyBettingPool`。如果新合约直接持有资金，将无法合法拉取 LP 赔付流动性。

因此串关亏损必须通过 `BettingPool` 地址调用 `LiquidityPool`。delegatecall 模式满足这个要求。

### 3.3 当前 market 终态不持久化比分

`BettingSettlementModule.finalizeMarketSettlement` 当前会在事件里发出比分，但没有把最终比分写入 storage。串关不能让 keeper 对每张串关重复提交比分，否则会出现“底层 market 结算比分”和“串关结算比分”不一致的风险。

本期必须新增 market final result storage，让串关只读取已终态 market 的链上事实源。

## 4. 架构方案

新增合约：

```text
BettingParlayModule
```

新增或修改入口仍放在 `BettingPool`：

```solidity
function setParlayModule(address newModule) external onlyRole(DEFAULT_ADMIN_ROLE);
function placeParlay(
    ParlayLegInput[] calldata legs,
    uint256 stake,
    uint256 minComboOdds,
    uint256 deadline,
    address referrer
) external returns (bytes32 parlayId);
function settleParlay(bytes32 parlayId) external onlyRole(SETTLER_ROLE);
function claimParlayPayout(bytes32 parlayId) external;
```

`BettingPool` wrapper 负责：

- `nonReentrant`；
- `whenNotPaused`；
- role 校验；
- delegatecall 到 `BettingParlayModule`。

`BettingParlayModule` 负责：

- 串关注单记录；
- leg 校验；
- 组合赔率计算；
- synthetic exposure 写入与释放；
- 用户风控账本写入与释放；
- 串关结算；
- 串关 claim；
- 复用现有税务和瀑布会计。

`previewParlay` 和进行中估值不放进 `BettingParlayModule`。原因是 Solidity 没有 `staticdelegatecall`，`BettingPool` 的 `view` 函数不能安全地通过普通 `delegatecall` 复用模块逻辑。本期推荐新增只读 `BettingParlayLens`：

```text
前端 / 脚本
  -> BettingParlayLens.previewParlay(...)
  -> BettingParlayLens.estimateParlayValue(...)
      -> 只读调用 BettingPool getter / StakingPool / LiquidityPool
```

`BettingPool.placeParlay` 仍是唯一写入事实源，并且必须完整重做所有校验。`BettingParlayLens` 只服务前端展示，不允许作为链上风控依据。`estimateParlayValue` 只能返回 `estimatedValue / floatingPnL` 展示估值与浮动盈亏，不得被命名或解释为 cash out、claimable、withdrawable 或可提前结算金额。

uint256 internal constant PARLAY_MAX_ODDS = 200;

### 6.3 `BettingPoolStorage` 追加字段

只允许在 storage 末尾追加字段，并同步减少 `__gap`：

```solidity
uint256 public nextParlayNonce;
address public parlayModule;
uint256 public openParlayMaxPayout;

mapping(bytes32 => MarketFinalResult) internal marketFinalResults;
mapping(bytes32 => ParlayBet) internal parlays;
mapping(bytes32 => ParlayLeg[]) internal parlayLegs;
mapping(address => bytes32[]) internal userParlayIds;
```

若按上述 7 个 storage slot 追加字段，`__gap` 从 `uint256[17]` 减少为 `uint256[10]`。实际实现前必须用 storage layout diff 确认只发生末尾追加。

明确不新增：

- `parlayReserve`
- `parlayUserRiskLedger`
- 独立 ODD 资金池

串关资金进入 `BettingPool`，串关风险进入 `BettingPool` 现有账本。

`openParlayMaxPayout` 是 `BettingPool` 聚合根内的未结算串关最大赔付占用账本，不是独立资金池，也不代表已锁定 ODD 余额。其用途是防止多张未结算串关反复复用同一份 Global LP / taxBuffer / platformReserve 容量。

### 6.4 共享 helper 边界

`BettingParlayModule` 通过 delegatecall 执行，但不能直接调用 `BettingPool` 或 `BettingSettlementModule` 的 internal 函数。本期必须处理以下 helper 的复用问题：

- 比分结果推导：抽成 `BettingScoreResultLib`，single bet 和 parlay 共用；
- exposure 刷新：复用或复制 `_refreshExposureAndOdds`，必须和 `BettingPool / BettingSettlementModule` 当前实现保持一致；
- 税分配：复用或复制 `_distributePayoutTax / _injectTaxBuffer`，必须和 single bet claim 保持一致；
- 瀑布：复用或复制 `_waterfall / _emitReserveStepAlerts`，必须和 single bet settlement / Cash Out 保持一致。

验收要求增加 golden tests：同一输入下，parlay helper 与 single bet helper 的税分配、reserve/taxBuffer 变化、LP loss booking 和 reserve alert 行为一致。若实现阶段发现复制 helper 造成体积或维护风险过高，应先抽共享库再继续。

## 7. Market 赛果事实源

本期必须补充 market final result storage：

1. `settleMarketBetsByScore` 仍负责按批处理 single bet；
2. `finalizeMarketSettlement` 在 market 终态时写入 `marketFinalResults[marketId]`；
3. 对 `Settled` market，必须保存 `homeScore / awayScore`；
4. 对 `Refunded / Cancelled` market，保存 result kind；
5. 新增 `marketFinalResults(marketId)` 自动 getter 供前端、脚本和 parlay lens 读取。

需要同步调整一个边界：如果某个 market 没有 single bet，但存在串关 leg，也必须能记录最终比分。可选实现：

- 允许 `settleMarketBetsByScore(marketId, score, emptyBetIds)` 在 `marketBetIds.length == 0` 时只记录比分进 progress；
- 或新增 `recordMarketFinalScore(marketId, homeScore, awayScore)`，再由 `finalizeMarketSettlement(marketId,0)` 写终态。

推荐第一种，复用现有 SETTLER 工作流，但必须补测试：`0 single bet + parlay leg` 的 market 可以保存比分并服务串关结算。

比分推导逻辑必须从 `BettingSettlementModule` 抽成 `BettingScoreResultLib`，由 single bet 和 parlay 共用，避免 AH half win / half loss 规则分叉。

## 8. 下单流程

### 8.1 用户入口

```solidity
function placeParlay(
    ParlayLegInput[] calldata legs,
    uint256 stake,
    uint256 minComboOdds,
    uint256 deadline,
    address referrer
) external nonReentrant whenNotPaused returns (bytes32 parlayId);
```

`referrer` 传 `address(0)` 表示不绑定推荐人。本期不提供无 `referrer` 参数的重载，减少 `BettingPool` wrapper 体积。

### 8.2 基础校验

必须校验：

1. `2 <= legs.length <= 6`；
2. `stake >= BettingConstants.MIN_BET_AMOUNT`；
3. `block.timestamp <= deadline`；
4. 每个 leg 的 market 存在；
5. market 状态必须是 `Open`；
6. market 未手动 `Locked`；
7. `block.timestamp < market.matchEndTime`；
8. `outcome < market.outcomeCount`；
9. `quoteVersion == marketOdds.quoteVersion`；
10. `quotedAt == marketOdds.updatedAt`；
11. `lockedOdds >= minOdds`；
12. 不允许重复 `marketId`；
13. 不允许重复 `matchId`；
14. 用户日限额和未结算仓位满足现有 `StakingPool` 规则；
15. 每个 leg 对应的用户 market 潜在赔付不超过 `SINGLE_MATCH_PAYOUT_CAP`；
16. 每个 leg 写入 synthetic exposure 后不得超过红灯阈值；
17. `maxPayout` 不得超过现有 L2/L3/L4 可覆盖能力。

### 8.3 组合赔率和最高赔付

下单时锁定每个 leg 当前 `quotedOdds[outcome]`：

```text
rawComboOdds = product(leg.lockedOdds) / 1e4^(n-1)
lockedComboOdds = min(rawComboOdds, 200 * 1e4)
rawMaxPayout = stake * lockedComboOdds / 1e4
maxPayout = min(rawMaxPayout, SINGLE_MATCH_PAYOUT_CAP)
```

若 `lockedComboOdds < minComboOdds`，revert。

`rawMaxPayout > SINGLE_MATCH_PAYOUT_CAP` 时不直接拒单。该订单仍可下单，但链上记录和后续结算都只承认截断后的 `maxPayout = SINGLE_MATCH_PAYOUT_CAP`，`previewParlay.cappedByPayout = true`。若产品不希望用户接受被截断的赔付，只能由前端在看到 `cappedByPayout` 后阻断或要求用户确认；本期合约不增加 `maxPayout` guard 参数。

结算阶段同样执行：

```text
grossPayout = min(calculatedGrossPayout, parlay.maxPayout)
```

因此不存在“最终实际 payout 超过 `maxPayout`”的合法状态。

`parlayId` 生成必须使用单调 nonce，不使用用户输入数组直接哈希作为唯一来源：

```text
nonce = nextParlayNonce++
parlayId = keccak256(abi.encodePacked(address(this), "ODDFI_PARLAY", nonce))
parlayRiskId = keccak256(abi.encodePacked("ODDFI_PARLAY_RISK", parlayId))
```

前端通过 `previewParlay` 展示：

- `rawComboOdds`
- `lockedComboOdds`
- `maxPayout`
- `availableParlayCapacity`
- `cappedByOdds`
- `cappedByPayout`
- 每个 leg 的 synthetic WCL 预览

`previewParlay` 不返回 `parlayId` 或 `parlayRiskId`。真实 `parlayId / parlayRiskId` 依赖 `placeParlay` 执行时的 `nextParlayNonce`，预览和上链之间可能有其他交易先消耗 nonce；因此 risk id 只能以下单成功后的返回值、事件和 `parlays(parlayId)` 为准。

### 8.4 Synthetic exposure 写入

串关不能绕过单市场 WCL。下单成功后，每个 leg 都向对应 market 写入保守 synthetic exposure：

```text
syntheticPayout = maxPayout

marketExposure[marketId].payoutByOutcome[outcome] += syntheticPayout
userMarketExposure[user][marketId].potentialPayoutCommitted += syntheticPayout
```

设计理由：

1. 串关最终最大赔付发生时，所选 leg 必须同时命中；
2. 对任一 leg 所在 market 来说，该 outcome 命中是串关赔付的必要条件；
3. 将 `maxPayout` 作为该 outcome 的 synthetic payout 是保守口径，可以防止通过串关绕开单市场红灯；
4. 不把串关 `stake` 加进 `totalStakedByOutcome`。原因是串关不是该 market 的单注，不会进入该 market 的 `marketBetIds`，底层 market 结算时也不会作为该 market 的 loser stake 参与 `context.loserStakes`。若把串关本金计入每个 leg market 的 stake，会虚增其他方向容量，低估单场 WCL。

若任一 leg 模拟后 `maxWcl > wclRedThreshold`，整张串关失败，不做部分成交。

写入后必须：

- `_refreshExposureAndOdds(marketId)`；
- `marketOdds[marketId].quoteVersion += 1`；
- emit `OddsUpdated`。

### 8.5 用户风控账本

串关 stake 计入用户现有风险账本：

```text
userRiskLedger[user].dailyAcceptedAmount += stake
userRiskLedger[user].unsettledStake += stake
```

不新增 `parlayUserRiskLedger`。原因是用户的每日额度和未结算仓位必须横跨单注和串关统一计算。

### 8.6 流动性校验

串关最大赔付能力校验：

```text
maxRequiredPayout = maxPayout
rawParlayCapacity = LiquidityPool.getGlobalRequestableLiquidity()
    + taxBuffer
    + platformReserve
availableParlayCapacity = rawParlayCapacity > openParlayMaxPayout
    ? rawParlayCapacity - openParlayMaxPayout
    : 0
```

下单前必须满足：

```text
maxRequiredPayout <= availableParlayCapacity
```

下单成功后：

```text
openParlayMaxPayout += maxRequiredPayout
```

`settleParlay` 无论最终 Lost / Refundable / WonUnclaimed，都必须释放：

```text
openParlayMaxPayout -= parlay.maxPayout
```

该口径和当前 `BettingPool.placeBet` 的 `potentialPayout <= availableLiquidity` 保持同一 gross payout 风控原则，不从最高赔付中扣除用户自己的 stake。但串关跨多个 match，本期不能使用任一单场 Match Pool 的专项流动性，只允许使用 Global LP、`taxBuffer` 和 `platformReserve`。本期也不把其他单注/串关注单的潜在输家筹码计入可用流动性，避免跨 market 串关高估 L1 抵扣。

`openParlayMaxPayout` 是串关特有的聚合敞口占用。没有这个字段时，多张跨不同 match 的未结算串关都可能通过同一份 Global LP 容量校验，形成会计上不可接受的超卖。

### 8.7 串关风险键与 Global LP

串关跨多个 match，不能把 L2 损失归属到任意一个 leg 的 Match Pool。否则用户可以通过选择最晚结束的 leg 间接影响哪个 match-specific LP 承担串关亏损，造成会计不公平。

本期规则：

```text
parlayRiskId = keccak256("ODDFI_PARLAY_RISK", parlayId)
```

`parlayRiskId` 只用于 `LiquidityPool` 的 parlay payout window，不代表真实比赛。

理由：

1. 串关是跨 match 风险，应由 Global LP 承担，不应污染单场 Match Pool；
2. `parlayRiskId` 可以为每张串关建立独立 payout window，claim 阶段按该 window 拉款；
3. `BettingParlayModule` 通过 delegatecall 以 `BettingPool` 地址调用 LiquidityPool，仍符合当前 `onlyBettingPool` 安全模型；
4. Match Pool LP 只承担自己指定 match 的单场风险，账本边界清晰。

需要同步扩展 `LiquidityPool`：

```solidity
function getGlobalRequestableLiquidity() external view returns (uint256);
function distributeGlobalMargin(bytes32 riskId, uint256 lpMarginShare) external onlyBettingPool;
function distributeGlobalLoss(bytes32 riskId, uint256 netLoss)
    external
    onlyBettingPool
    returns (uint256 lpLossBooked);
function requestPayoutLiquidity(bytes32 riskId, uint256 amount) external onlyBettingPool;
function releasePayoutReserve(bytes32 riskId) external onlyBettingPool returns (uint256 releasedAmount);
```

`distributeGlobalMargin` 和 `distributeGlobalLoss` 都只影响 Global Pool，不影响 Match Pool。`distributeGlobalLoss` 使用 `riskId` 写入 payout window。现有 `requestPayoutLiquidity(bytes32,uint256)` 可以复用，但参数语义需要从 `matchId` 扩展为 `settlementKey`。单注继续传真实 `matchId`，串关传 `parlayRiskId`。

`LiquidityPool` 必须在 reserve、实际拉款和 release 后发出 `PayoutReserveOutstanding(riskId,outstandingAmount)`。后端以 `outstandingAmount > 0` 的 `riskId` 建立待检查队列；当产品/运营确认该普通单注 `matchId` 或串关 `parlayRiskId` 不再需要保留赔付 reserve 时，由 `SETTLER_ROLE` 调用 `BettingPool.releasePayoutReserve(riskId)` 释放 `reservedAmount - paidOutAmount`。本期不新增链上 claim 过期状态机。

`getGlobalRequestableLiquidity()` 必须是 O(1) 账本值，不能遍历 LP positions，也不能直接返回当前全局 `requestableLiquidity`。需要在 `LiquidityPool` 中新增并维护：

```solidity
uint256 public globalRequestableLiquidity;
bool public globalRequestableLiquidityInitialized;
```

该字段必须追加在 `LiquidityPool` storage 末尾，并将 `LiquidityPool.__gap` 从 `uint256[42]` 减少为 `uint256[40]`。若实现时字段数量不同，必须以 storage layout diff 为准。

维护规则：

| 场景 | `globalRequestableLiquidity` 变化 |
| --- | --- |
| Global Pool deposit | 增加对应 active position value |
| Global Pool unbond | 减少该 position 的 requestable share |
| `distributeGlobalMargin` | 增加全部 `lpMarginShare` |
| `distributeGlobalLoss` | 减少实际 booked global loss |
| 单场 `distributeMargin` | 只增加分给 Global Pool 的 `globalShare` |
| 单场 `distributeLoss` | 只减少分给 Global Pool 的 `globalLossShare` |

升级已有测试网 proxy 时，必须通过 reinitializer 或一次性治理迁移写入 `globalRequestableLiquidity` 初值，并在部署报告中记录计算来源。迁移入口必须只能执行一次，成功后设置 `globalRequestableLiquidityInitialized = true`。生产上线前若无法无歧义重建该值，应选择重新部署 `LiquidityPool` 或暂停串关功能，不允许用总 `requestableLiquidity` 近似替代。

### 8.8 资金和税

资金进入 `BettingPool`：

```text
betTax = stake * betTaxBps / 1e4
totalDeduct = stake + betTax
ODD.transferFrom(user, BettingPool, totalDeduct)
accountedBalance += totalDeduct
```

下注税复用现有推荐逻辑：

- 若用户已有 `referrers[user]`，下注税进入 `referrerRewardsOdd[referrer]`；
- 若首次下单传入合法 `referrer`，先绑定再累计下注税；
- 没有推荐人时，下注税转 `platformTreasury`，并从 `accountedBalance` 扣除。

## 9. 结算流程

### 9.1 入口

```solidity
function settleParlay(bytes32 parlayId)
    external
    onlyRole(SETTLER_ROLE)
    nonReentrant;
```

结算不再接收比分参数，只读取 `marketFinalResults`。

### 9.2 前置条件

1. parlay 状态为 `Pending`；
2. 所有 leg 的 `marketFinalResults[marketId].finalized == true`；
3. 若任一 leg market 仍为 `Open / Locked`，revert；
4. 若任一 `Settled` market 没有 `scoreSettled`，revert。

### 9.3 Leg 结果

对于 `Settled` market：

- 使用 `BettingScoreResultLib` 根据 `marketType / line / outcome / homeScore / awayScore` 推导；
- 推导结果必须和 single bet settlement 使用同一套代码。

对于 `Refunded / Cancelled` market：

- leg 结果记为 `Void`；
- factor 为 `1.0`；
- 不视为有效串关腿。

### 9.4 Void 后有效腿数

本期规则：

```text
effectiveLegCount = 非 Void 且非 FullPush 的 leg 数量
```

结算顺序必须先判断 `FullLoss`：

1. 任一 leg 为 `FullLoss`：整张串关立即进入 `Lost`；
2. 没有 `FullLoss`，且 `effectiveLegCount == 0`：整张串关进入 `Refundable`，用户领取原 stake，不收派奖税，不分配 LP/platform margin；
3. 其余情况再按因子计算 `grossPayout`。

说明：若 Void/FullPush 后只剩一个有效 leg，不直接全额退款，而是按剩余 leg 的因子结算。否则 `Void + HalfLoss` 或 `Void + FullLoss` 会错误地忽略已经发生的负向结果。

### 9.5 派奖因子

使用 `1e18` 作为中间精度：

| Leg 结果 | 因子 |
| --- | --- |
| `FullWin` | `lockedOdds / 1e4` |
| `FullPush` | `1.0` |
| `Void` | `1.0` |
| `FullLoss` | `0` |
| `HalfWin` | `(lockedOdds + 1e4) / 2e4` |
| `HalfLoss` | `0.5` |

计算：

```text
factorProduct = 1e18
FullWin:  factorProduct = factorProduct * lockedOdds / 1e4
FullPush: factorProduct = factorProduct
Void:     factorProduct = factorProduct
HalfWin:  factorProduct = factorProduct * (lockedOdds + 1e4) / 2 / 1e4
HalfLoss: factorProduct = factorProduct / 2
FullLoss: grossPayout = 0

grossPayout = stake * factorProduct / 1e18
grossPayout = min(grossPayout, maxPayout)
```

### 9.6 结算会计

结算时必须先释放所有 synthetic exposure：

```text
marketExposure[marketId].payoutByOutcome[outcome] -= syntheticPayout
userMarketExposure[user][marketId].potentialPayoutCommitted -= syntheticPayout
```

同时释放用户未结算仓位：

```text
userRiskLedger[user].unsettledStake -= stake
openParlayMaxPayout -= parlay.maxPayout
```

不回滚 `dailyAcceptedAmount`。该口径与 Cash Out 不回滚日限额一致，避免用户用短周期串关结算绕每日额度。

若 `grossPayout == 0`：

- state = `Lost`；
- `claimablePayout = 0`；
- stake 留在 `BettingPool`；
- 按现有 settlement margin 口径，从 `stake` 中计算 LP/platform margin。
- margin 后剩余 stake 继续留在 `BettingPool.accountedBalance`，作为当前单注体系同口径的内部可用余额，不进入独立串关准备金。

若 `effectiveLegCount == 0`：

- state = `Refundable`；
- `claimablePayout = stake`；
- 不走 payout tax；
- 不分配 margin。

若 `0 < grossPayout <= stake` 且 `effectiveLegCount >= 2`：

- state = `Refundable`；
- `claimablePayout = grossPayout`；
- 不走 payout tax；
- 不拉 LP；
- `retainedStake = stake - grossPayout` 留在 `BettingPool`；
- 若 `retainedStake > 0`，仅对 `retainedStake` 按现有 settlement margin 口径分配 LP/platform margin。
- margin 后剩余 retained stake 继续留在 `BettingPool.accountedBalance`，不转入独立 reserve。

该分支覆盖 AH half loss、组合后保本或小亏等情况。会计上它不是胜单派奖，而是“部分退款 + 部分亏损”，不能按 `payoutTaxBps` 对用户退回本金部分收税。

若 `grossPayout > stake`：

- state = `WonUnclaimed`；
- `claimablePayout = grossPayout`；
- 快照当前 `payoutTaxBps` 和税分配比例；
- 快照当前 `referrers[user]`；
- 以 `parlayRiskId` 走 Global LP -> L3 -> L4 瀑布。

2026-06-13 结算缺口 hotfix 后，串关盈利胜单的亏损瀑布只承担真实经济缺口：

```text
fundingBase = stake
totalMargin = stake * 1000 / 1e4
selfFundedPayout = stake - totalMargin
netLoss = max(grossPayout - selfFundedPayout, 0)
```

该口径把串关用户自己的 `stake` 扣除 settlement margin 后作为池内可自付赔付，避免冷启动无 Global LP 时把整笔 `grossPayout` 虚送入 L4 瀑布。`Refundable` 分支仍不进入亏损瀑布；`WonUnclaimed` claim 阶段仍以 `grossPayout` 作为领取前所需实际余额，余额不足时只从已 book 的 payout reserve 拉取真实需要补足的部分。

Margin 分配复用当前 `BettingSettlementModule` 口径：

```text
marginBase = state == Lost ? stake
    : state == Refundable ? stake - claimablePayout
    : stake

totalMargin = marginBase * 1000 / 1e4
lpMarginShare = totalMargin * lpMarginShareBps / 1e4
platformMarginShare = totalMargin - lpMarginShare
```

- 有 Global LP 权重时，`lpMarginShare` 转入 `LiquidityPool` 并调用 `distributeGlobalMargin(parlayRiskId, lpMarginShare)` 计入 Global Pool reward；
- 无 Global LP 权重时，`lpMarginShare` 进入 `platformReserve`；
- `platformMarginShare` 进入 `platformReserve`。

若 `state == Refundable && claimablePayout == stake`，`marginBase = 0`，不分配 margin。若 `state == WonUnclaimed`，`marginBase = stake`，该口径与当前 single bet settlement 使用 `totalStake` 计算 settlement margin 保持一致。

## 10. Claim 流程

### 10.1 入口

```solidity
function claimParlayPayout(bytes32 parlayId)
    external
    nonReentrant
    whenNotPaused;
```

### 10.2 校验

1. `msg.sender == parlay.owner`；
2. state 为 `WonUnclaimed` 或 `Refundable`；
3. `claimablePayout > 0`。

### 10.3 Refundable claim

`Refundable` 返还 `claimablePayout`，可能是全额 stake，也可能是 `grossPayout < stake` 的部分退款：

```text
grossPayout = claimablePayout
taxAmount = 0
netPayout = grossPayout
state = Refunded
```

若 `BettingPool` 实际 ODD 余额小于 `grossPayout`，本分支直接 revert `PoolLiquidityInsufficient`，不允许向 `LiquidityPool` 拉款。退款/部分退款必须由已持有的用户 stake 覆盖。

### 10.4 Won claim

`WonUnclaimed` 复用 single bet 派奖税路径：

```text
grossPayout = claimablePayout
taxAmount = grossPayout * payoutTaxRateBps / 1e4
netPayout = grossPayout - taxAmount
state = WonClaimed
```

若 `BettingPool` 实际 ODD 余额小于 `grossPayout`：

```solidity
LiquidityPool.requestPayoutLiquidity(parlayRiskId, grossPayout - actualBalance)
```

之后按快照分配派奖税：

- staking share：转 `StakingPool` 并调用 `notifyReward`；
- taxBuffer share：优先冲抵 `lpLossOffsetRemaining`，再填充 `taxBuffer`，溢出进入 `platformReserve`；
- referrer share：有 `referrerSnapshot` 时进入 `referrerRewardsOdd`，否则并入平台份额；
- platform share：转 `platformTreasury`。

最后用户收到 `netPayout`。

claim 后如果 `parlayRiskId` 的 payout window 仍存在 `reservedAmount > paidOutAmount`，该残留不会自动释放。后端应通过 `PayoutReserveOutstanding(parlayRiskId,outstandingAmount)` 识别 residual，并在确认无需继续保留后调用 `BettingPool.releasePayoutReserve(parlayRiskId)`。

### 11.3 只读进行中估值入口

串关进行中需要展示浮动估值时，由 `BettingParlayLens` 提供只读入口：

```solidity
function estimateParlayValue(address bettingPool, address userAddress, bytes32 parlayId)
    external
    view
    returns (ParlayEstimatedValue memory);
```

返回结构中的核心展示字段命名为 `estimatedValue`：

```solidity
struct ParlayEstimatedValue {
    uint8 state;
    uint256 stake;
    uint256 lockedComboOdds;
    uint256 maxPayout;
    uint256 estimatedValue;
    int256 floatingPnL;
    uint256 factorProduct;
    uint8 finalizedLegCount;
    uint8 unresolvedLegCount;
    bool hasFullLoss;
    bool isFinal;
}
```

语义约束：

- `estimatedValue` 是当前信息下的 gross mark-to-market 估值，只用于前端/后台展示；
- `floatingPnL = estimatedValue - stake`，只用于过程浮动盈亏展示；
- `estimatedValue` 不是 `claimablePayout`，不是可提现金额，不允许作为结算或提前退出依据；
- 不新增 `cashOutParlay`、`quoteParlayCashOut` 或任何提前结算入口；
- `estimateParlayValue` 只允许查询 `userAddress` 名下 `Pending` 串关；user 不匹配返回默认 0 值，parlay 已进入终态或待 claim 状态时 revert；
- 对 `Pending` 串关，若所有未终局 leg 的当前赔率等于下注锁定赔率，且没有任何 leg 已终局，`estimatedValue` 应接近 `stake`，而不是 `maxPayout`；
- 对已终局 leg，按 `marketFinalResults` 和正式结算同一套 factor 计算；
- 对 `Refunded / Cancelled` leg，factor 为 `1.0`；
- 对未终局 leg，使用 `lockedOdds / currentQuotedOdds[outcome]` 作为估值因子，而不是直接把当前赔率相乘；
- 若任一已终局 leg 为 `FullLoss`，`estimatedValue = 0`，`hasFullLoss = true`；
- 若所有 leg 都已终局且 parlay 仍为 `Pending`，`isFinal = true`，此时 `estimatedValue` 应与 `settleParlay` 的 `grossPayout` 参考公式一致；
- 若 parlay 已经 `WonUnclaimed / Refundable / WonClaimed / Refunded / Lost`，本接口 revert；历史 gross payout 通过事件或 `parlays(parlayId)` 查看；
- `factorProduct` 必须和返回的 `estimatedValue` 保持一致，避免前端用 factor 反算出不同数值；
- 计算结果必须执行 `estimatedValue = min(stake * factorProduct / 1e18, maxPayout)`。

估值因子示例：

```text
factorProduct = 1e18

已终局 FullWin:  factorProduct = factorProduct * lockedOdds / 1e4
已终局 FullPush: factorProduct = factorProduct
已终局 Void:     factorProduct = factorProduct
已终局 HalfWin:  factorProduct = factorProduct * (lockedOdds + 1e4) / 2 / 1e4
已终局 HalfLoss: factorProduct = factorProduct / 2
未终局 leg:      factorProduct = factorProduct * lockedOdds / currentQuotedOdds[outcome]

estimatedValue = min(stake * factorProduct / 1e18, maxPayout)
```

该入口的返回值不写入 storage，不释放 synthetic exposure，不更新 `userRiskLedger`，不触发 tax、LP payout window 或任何资金转账。

## 13. 安全约束

强制要求：

1. `placeParlay / settleParlay / claimParlayPayout` 都必须 `nonReentrant`；
2. 用户入口必须 `whenNotPaused`；
3. 结算入口必须 `onlyRole(SETTLER_ROLE)`；
4. module 地址必须非零且 `code.length > 0`；
5. module 只能通过 `delegatecall` 执行，直接调用必须 revert；
6. 循环上限为 `MAX_PARLAY_LEGS = 6`；
7. 不允许循环中做用户转账；
8. 下单、结算、claim 必须遵循 Checks-Effects-Interactions；
9. 所有资金转账使用 `SafeERC20`；
10. 不允许重复 `marketId` 或重复 `matchId`；
11. 不允许底层 market `Locked / Terminal` 后下串关；
12. 结算只能读取已持久化的 market final result；
13. UUPS storage 只能末尾追加字段，并跑 storage layout diff；
14. synthetic exposure 释放必须覆盖 lost / won / refundable / revert 前所有已写状态；
15. `BettingParlayModule` 不得新增独立 reserve 或独立用户风险账本。
16. `openParlayMaxPayout` 必须在下单成功后增加，在 `settleParlay` 的所有终局分支释放；
17. 禁止新增 `cashOutParlay`、`quoteParlayCashOut`、`ParlayState.CashedOut` 或任何串关提前结算入口。
