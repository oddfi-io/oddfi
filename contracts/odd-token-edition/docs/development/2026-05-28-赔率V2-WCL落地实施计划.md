# 赔率 V2 WCL 落地实施计划

**日期：** 2026-05-28
**状态：** 已落地（2026-05-28）
**目标：** 将当前链上赔率风控从 V1 的 `S_i × BaseOdds_i` 估算口径升级为 V2 的逐笔 `lockedOdds` 累计真实赔付口径。

## 1. 背景与目标

计划制定时，`BettingPool` 已经在注单结构中保存 `lockedOdds`，结算派奖也按 `lockedOdds` 计算；但市场级 WCL、信号灯、部分成交和赔率压缩仍以 `totalStakedByOutcome + baseOdds` 估算。该状态会在轻仓持续上浮、Base Odds 更新或历史成交赔率偏离 Base Odds 时低估或错估真实风险敞口。2026-05-28 实施后，市场级风控已切换到下述 V2 目标口径。

V2 目标口径：

```text
P_i = Σ(stake_k × lockedOdds_k)
L_i = P_i - S_i - ΣS_j

等价为：
L_i = P_i - totalStake
```

其中链上实现必须按赔率精度折算：

```solidity
payout = stake * lockedOdds / PrecisionConstants.ODDS_RATE_SCALE;
```

## 2. 原始差距与落地目标

| 主题 | 改造前实现 | V2 目标 |
|---|---|---|
| 市场暴露 | `MarketExposure.totalStakedByOutcome + signalColor` | 额外维护每方向 `payoutByOutcome` |
| WCL | `stake[i] * baseOdds[i] / 1e4 - totalStake` | `payout[i] - totalStake` |
| Base Odds 更新 | 会用新 Base Odds 重估历史 stake 风险 | 只影响新单成交价，不回算历史 `P_i` |
| 红灯容量 | V1 反解：`(red + otherStake) / (baseOdds - 1) - currentStake` | V2 反解：`(red - L_i_old) / (O_new - 1)` |
| 退款风险回滚 | 只扣 `totalStakedByOutcome` | 同时扣 `totalStakedByOutcome` 和 `payoutByOutcome` |
| AH full push | 注单退款但未清市场暴露 | 该 market 双侧 S/P 归零后重算 |
| 信号灯边界 | `L >= threshold` 进入下一灯 | V2 左开右闭：`80k` 绿、`180k` 黄、`280k` 橙、`>280k` 红 |
| 压缩率精度 | 以 `10,000 ODD` 整步取整计算 bps | 中间计算保留全精度，只最终赔率按 0.01 tick 四舍五入 |
| 大小额滑点 | 当前 `previewSignal` 对所有金额都模拟 post-trade 赔率 | `<= 10,000 ODD` 锁当前报价；`> 10,000 ODD` 执行折后赔率预览 |
| 开盘赔率生成 | 合约只接收 operator 传入的 `baseOdds` 并做格式校验 | Sportmonks ref odds 到 Base Odds 的四步法由后端/脚本完成，合约继续只校验最终 `baseOdds` |

## 3. 设计原则

1. 不改变 `Bet.lockedOdds` 的语义；它仍是下单时永久锁定的实际成交赔率。
2. `P_i` 表示若方向 i 赢，平台需支付的总额，包含本金返还。
3. 所有 `P_i` 更新必须与 `S_i` 在同一状态变更中完成，避免中间状态导致 WCL 错误。
4. Base Odds 仅参与新报价生成，不得回算历史注单赔付义务。
5. 部分成交和滑点均为一次性计算，不做递归或多轮迭代。
6. UUPS storage layout 必须向后兼容，不能移动、删除或重排已有 storage 字段。

## 4. 实施范围

### 4.1 Storage

文件：`src/modules/betting/BettingPoolStorage.sol`

推荐方案是在 `MarketExposure` 末尾追加字段：

```solidity
struct MarketExposure {
    uint256[] totalStakedByOutcome;
    SignalColor signalColor;
    uint256[] payoutByOutcome;
}
```

初始化 market 时：

```solidity
exposure.totalStakedByOutcome = new uint256[](outcomeCount);
exposure.payoutByOutcome = new uint256[](outcomeCount);
exposure.signalColor = SignalColor.Green;
```

若担心对已部署 proxy 的嵌套动态数组 layout 可读性，可改用独立 mapping：

```solidity
mapping(bytes32 => uint256[]) internal marketPayoutByOutcome;
```

若选择新增顶层 mapping，必须同步减少 `__gap` 长度，保持 UUPS storage gap 预留语义。

无论选择哪种方案，都必须确认 storage layout diff，不允许覆盖 `marketSettlementProgress`、推荐奖励或结算模块字段。

### 4.1A Base Odds 生成边界

文件：`src/modules/betting/BettingPool.sol`、后端赔率服务/部署脚本

当前 Solidity 合约的 `openMarket` / `updateOdds` 接口只接收已经生成好的 `baseOdds`，不会也不应在链上用 Sportmonks `ref_odds` 计算四步法。赔率 V2 的四步法落地边界为：

1. 后端或开盘脚本从 Sportmonks 拉取 `ref_odds[]`；
2. 后端或脚本执行 `p_implied -> p_true -> p_adj -> Base Odds` 四步法；
3. 将最终 0.01 tick、`>= 1.01` 的 `baseOdds` 传给 `openMarket` / `updateOdds`；
4. 合约继续只执行长度、顺序、下限和 0.01 tick 校验；
5. 若后续仓库加入后端赔率服务，必须补充相应测试，验证禁止使用 `ref_odds × (1 - Margin)` 简化公式。

因此，本 Solidity 改造验收不要求合约接收 `ref_odds` 或在链上实现浮点归一化；但整套 V2 产品验收必须覆盖后端四步法。

### 4.2 赔率库

文件：`src/modules/betting/BettingOddsLib.sol`

新增或改造函数：

```solidity
function currentOutcomeWclV2(
    uint256 currentOutcomePayout,
    uint256 currentTotalStake
) public pure returns (uint256 currentWcl);

function computeWorstCaseLossesV2(
    uint256[] memory payouts,
    uint256 totalStake
) public pure returns (uint256[] memory wcls, uint256 maxWcl);

function computeQuotedOddsV2(
    uint256[] memory baseOdds,
    uint256[] memory stakes,
    uint256[] memory payouts,
    uint256 yellowThreshold,
    uint256 orangeThreshold,
    uint256 redThreshold
) public pure returns (uint256[] memory quotedOdds, uint256 worstCaseLoss, SignalColor signalColor);
```

WCL 计算规则：

```solidity
uint256 wcl = payouts[i] > totalStake ? payouts[i] - totalStake : 0;
```

压缩和上浮继续以 `maxWcl` 决定；赔率输出仍调用 `normalizeOdds`，保持最终报价 0.01 tick 和 1.01 下限。

### 4.3 信号灯边界

文件：`src/modules/betting/BettingOddsLib.sol`

V2 边界：

```text
Green:  maxWcl <= yellowThreshold
Yellow: maxWcl <= orangeThreshold
Orange: maxWcl <= redThreshold
Red:    maxWcl > redThreshold
```

`compressionBpsFor` 也要与边界保持一致：`maxWcl <= yellowThreshold` 时返回 0；`yellowThreshold < maxWcl <= orangeThreshold` 走黄灯压缩；`orangeThreshold < maxWcl <= redThreshold` 走橙灯压缩；`maxWcl > redThreshold` 返回最大压缩。

当前代码使用：

```solidity
uint256 steps = (maxWcl - threshold) / (10_000 * PrecisionConstants.ODD_WAD);
uint256 bps = steps * 40;
```

该写法会把压缩率按 `10,000 ODD` 整步向下取整，和 V2 “中间乘积全精度、只最终赔率四舍五入”不一致。V2 应改为连续线性计算，例如黄灯区间：

```solidity
uint256 bps =
    (maxWcl - yellowThreshold) * 40 / (10_000 * PrecisionConstants.ODD_WAD);
```

橙灯区间同理使用 `(maxWcl - orangeThreshold) * 80 / (10_000 * ODD_WAD)`，并继续保留 4% / 12% 上限。

### 4.4 下注预览与成交写入

文件：`src/modules/betting/BettingPool.sol`

下注写入时同时更新 S/P：

```solidity
uint256 payout = acceptedAmount * lockedOdds / PrecisionConstants.ODDS_RATE_SCALE;
exposure.totalStakedByOutcome[outcome] += acceptedAmount;
exposure.payoutByOutcome[outcome] += payout;
```

`_previewPostTradeSignal` 必须模拟两个数组：

```solidity
stakes[outcome] += acceptedAmount;
payouts[outcome] += acceptedAmount * simulatedLockedOdds / PrecisionConstants.ODDS_RATE_SCALE;
```

这里存在赔率和 `P_i` 的一次性依赖，按 V2 采用固定顺序：

1. 读取当前 quoted odds，作为本单初始候选成交价；
2. 用 `acceptedAmount × candidateOdds` 模拟新增 `P_i`；
3. 基于模拟后的 S/P 计算 WCL 和压缩后赔率；
4. 将步骤 3 得到的下注方向赔率作为本单最终 `lockedOdds`；
5. 不再用最终 `lockedOdds` 重新迭代步骤 2。

该顺序要用注释写入代码，避免后续维护者误改成循环求解。

大小额滑点分支必须同步落地：

- `requestedAmount <= BettingConstants.SLIPPAGE_TRIGGER_AMOUNT`：默认锁定当前 `quotedOdds[outcome]`；若模拟后触红灯，仍进入 V2 部分成交反解；
- `requestedAmount > BettingConstants.SLIPPAGE_TRIGGER_AMOUNT`：按上述一次性 post-trade 模拟返回折后赔率，供前端二次确认；
- 两条路径都必须使用同一套 S/P 红灯容量校验，避免小额单绕过红灯。

### 4.5 红灯部分成交

文件：`src/modules/betting/BettingPool.sol`、`src/modules/betting/BettingOddsLib.sol`

废弃 V1 `maxStakeAtRedThreshold` 公式，新增 V2 反解：

```solidity
function maxStakeAtRedThresholdV2(
    uint256 oldWcl,
    uint256 newOdds,
    uint256 redThreshold
) public pure returns (uint256 maxAcceptableAmount);
```

公式：

```text
maxStake = (redThreshold - oldWcl) / (O_new - 1)
```

链上精度：

```solidity
if (oldWcl >= redThreshold) return 0;
uint256 denominator = newOdds - PrecisionConstants.ODDS_RATE_SCALE;
maxStake =
    (redThreshold - oldWcl) * PrecisionConstants.ODDS_RATE_SCALE / denominator;
```

`O_new` 必须按最终成交赔率处理：

```solidity
uint256 rawFloorOdds = baseOdds[outcome] * 8800 / PrecisionConstants.BPS_SCALE;
uint256 newOdds = BettingOddsLib.normalizeOdds(rawFloorOdds);
if (newOdds < 10_100) newOdds = 10_100;
```

`maxStake` 计算必须使用最终会写入注单的 `newOdds`，避免 `maxStake` 用未舍入赔率计算而实际锁定赔率高 1 tick 后越过红线。结果必须向下取整，确保写入后 `L_i <= redThreshold`。当容量为 0 时返回红灯且拒绝成交。

### 4.6 Base Odds 更新

文件：`src/modules/betting/BettingPool.sol`

`updateOdds` 继续更新 `baseOdds` 与 `updatedAt`，并基于当前 S/P 重算新报价。历史 `payoutByOutcome` 不得变动。

验收点：

- 已有注单 lockedOdds 不变；
- `payoutByOutcome` 不变；
- `quotedOdds` 可变；
- `signalColor` 不应仅因 Base Odds 更新而变化；V2 下信号灯只由当前 S/P 推导出的 WCL 阈值决定。

### 4.7 退款与 AH Push

文件：`src/modules/betting/BettingPool.sol`、`src/modules/betting/BettingSettlementModule.sol`

普通退款、取消退款：

```solidity
uint256 releasedPayout = refundAmount * bet.lockedOdds / PrecisionConstants.ODDS_RATE_SCALE;
exposure.totalStakedByOutcome[bet.outcome] -= refundAmount;
exposure.payoutByOutcome[bet.outcome] -= releasedPayout;
```

AH full push：

- 对应注单本金退回；
- bet 变为 `Refunded`；
- full push 注单逐笔释放对应 `S_i/P_i`；
- 当该 market 全部注单均为 full push 时，分批处理完成后各方向 S/P 会自然归零；
- half win/half loss 只释放退款部分的 S/P，不误清剩余 win/loss 风险记录。

### 4.8 用户风险账本

当前 `userMarketExposure.potentialPayoutCommitted` 已按 `lockedOdds` 记录潜在赔付。V2 不要求改变该语义，但退款和结算释放必须继续使用 `bet.lockedOdds`。修改市场级 `P_i` 时不得破坏用户级赔付上限逻辑。

### 4.9 对外 API 与事件

当前前端 API 可保持兼容。可选新增 view：

5. 红灯 V2 max stake 示例：`L_old=250k`、`O_new=2.20`，容量为 `25,000 ODD`。

### 5.2 集成测试

扩展 `test/ForkMainnetCoverageBetting.t.sol` 或新增 fork-free 测试：

1. 下单后 `S_i` 和 `P_i` 同步增加；
2. 部分退款后 `S_i` 和 `P_i` 同步减少；
3. `updateOdds` 后历史 `P_i` 不变；
4. 红灯部分成交后新 WCL 不超过阈值；
5. AH full push 后 market S/P 归零，quoted odds 回 Base Odds；
6. half win / half loss 只释放退款部分的 S/P，不误清整盘。

### 5.3 Fuzz 与对抗性测试

1. 随机下注金额、赔率、方向，验证 `payoutByOutcome[i] == Σ(activeStake × lockedOdds / 1e4)`；
2. 随机退款金额，验证 S/P 不下溢；
3. 红灯容量 fuzz，验证成交后 `maxWcl <= redThreshold`；
4. 随机 Base Odds 更新，验证历史 P 不变；
5. 多方向并列最大时，所有并列方向同步压缩，其余方向上浮；轻仓为空时不执行上浮。

## 7. 验收标准

V2 任务必须同时满足：

1. 每个 market 每个方向维护 S/P，且 P 为逐笔 `lockedOdds` 累计赔付额；
2. WCL、信号灯、压缩/上浮和红灯部分成交全部基于 S/P；
3. Base Odds 更新不回算历史 P；
4. 普通退款、取消退款、AH full push、half win、half loss 均正确释放 S/P；
5. `lockedOdds` 在注单生命周期内不变，结算派奖继续按该值；
6. 信号灯边界符合 V2 左开右闭规则；
7. 所有新增/修改测试通过；
8. 文档、API、进度与测试报告完成同步。

当前实现结论：

- 已在 `MarketExposure` 末尾追加 `payoutByOutcome`，保持既有 `totalStakedByOutcome / signalColor` 顺序不变；
- 已将 `BettingOddsLib`、下注预览、下注成交、退款和 score-based settlement 的退款分支切换到 V2 S/P 口径；
- 已新增 `getMarketExposure` 供链上核对 S/P 与信号灯；
- AH 盘口保留当前实现的 10 条 line。

## 8. 风险与注意事项

- `MarketExposure` 增加动态数组会影响 storage layout 可读性，开发前必须跑 storage layout 检查。
- V2 预览的一次性计算顺序必须固定；不要引入循环迭代，否则 gas、可预测性和前端 quote guard 都会变复杂。
- AH full push 当前属于正常比分结算，不再有独立 `pushRefundMarket`，清账逻辑必须嵌入 score-based settlement。
- 当前产品文档中的 AH line 已与用户提供的 V2 文本局部不一致：仓库当前实现支持 10 条 AH line，本次赔率 V2 改造默认保留当前 10 线能力，不回退为 3 线。
- 若已部署测试网 proxy 需要原址升级，必须同步升级 `BettingPool` implementation 和 `BettingSettlementModule`，并确认两者共享 storage layout。
