# 结算缺口计算 Hotfix 方案

**日期：** 2026-06-13
**状态：** 已实施并通过本地验证
**模块：** `BettingSettlementModule`、`BettingParlayModule`
**类型：** Hotfix / 账务口径修复
**严重程度：** 高。影响 `platformReserve`、`availableLiquidity` 与自动熔断判断；当前判断不指向资金丢失。

## 1. 背景

测试反馈文件 `/Users/hawkwu/Downloads/ODD-结算缺口计算Bug-修复说明-终版.md` 指出：普通单注正常结算时，`netLoss` 使用 `grossPayout - loserStakes`，没有把赢家自己的本金纳入池内可自付资金，导致冷启动无 LP 时把本不需要兜底的赔付误判为 L4 缺口。

本仓库修复前源码确认存在该问题，并且串关赢单路径存在同类问题：

- 普通单注：`src/modules/betting/BettingSettlementModule.sol` 的 `finalizeMarketSettlement` 使用 `context.grossPayout - context.loserStakes` 计算 `context.netLoss`。
- 串关：`src/modules/betting/BettingParlayModule.sol` 的赢单分支直接把 `context.grossPayout` 作为 `netLoss` 传入 `_applyParlaySettlementAccounting`。

这是一个结算瀑布输入口径问题，不需要调整 ABI、storage layout、权限、下注入口、claim 入口或 LP 合约接口。本次 hotfix 已按最小修复原则只修改两个结算入口的 `netLoss` 输入口径，并补充复现、资金流、E2E、场景矩阵、fuzz/invariant 与非 fork 全量回归验证。

## 2. 修复前问题描述

### 2.1 普通单注问题

修复前结算收口逻辑：

```solidity
context.netLoss = context.grossPayout > context.loserStakes
    ? context.grossPayout - context.loserStakes
    : 0;
```

其中：

- `grossPayout` 是赢家应得总赔付，包含赢家本金；
- `loserStakes` 只包含输家本金，不包含赢家本金；
- 当前实现中 `context.totalStake` 是本次结算后仍留在池内的本金，即 `winStake + lossStake`；`push/refundStake` 已在逐笔处理时退回用户并扣减 `accountedBalance`，不应再作为瀑布可自付资金。

因此，当前公式把赢家本金排除在可自付资金之外。对于平衡盘或盈利盘，代码仍可能向 L2/L3/L4 瀑布发送虚高缺口。

### 2.2 串关问题

修复前串关赢单路径：

```solidity
context.lpLossBooked = _applyParlaySettlementAccounting(
    parlay.parlayRiskId,
    context.marginBase,
    context.grossPayout,
    context
);
```

串关文档此前也明确记录了旧保守口径：

```text
parlayTotalStake = stake
parlayLoserStake = 0
netLoss = grossPayout
```

该口径同样没有把串关用户自己的 `stake` 纳入可自付资金。冷启动无 Global LP 时，串关赢单会把整笔 `grossPayout` 送入 L4 瀑布，再叠加 margin 入账，导致 `platformReserve` 被虚减。

### 2.3 为什么有 LP 时不容易暴露

当 L2 有可请求 LP 流动性时，虚高的 `netLoss` 会先进入 LP payout window：

- `LiquidityPool.distributeLoss / distributeGlobalLoss` 会按 `netLoss` book L2 loss，并设置 payout reserve；
- claim 时实际只在 `BettingPool` 余额不足时通过 `requestPayoutLiquidity` 拉款；
- 未实际拉走的 reserve 后续可以通过 `releasePayoutReserve` 释放。

这使 L2 路径存在自我修正空间，但仍会造成临时虚高的 `lpLossOffsetRemaining` 和 payout window。

无 LP 或 LP 不足时，虚高缺口会继续进入 L3/L4。`taxBuffer` 和 `platformReserve` 没有对应的自动归还机制，因此冷启动阶段会形成永久账本偏差。

### 3.1 普通单注冷启动复现

输入：

```text
无 LP
初始 platformReserve = 1,000,000 ODD
双边各押 1,000 ODD
两边赔率均为 1.8
下注税 1%，结算 margin 10%
主队获胜，用户 1 胜，用户 2 负
```

修复前源码输出：

```text
reserveBefore = 1,000,000 ODD
reserveAfter  =   999,400 ODD
balanceBefore = 1,002,000 ODD
balanceAfter  = 1,002,000 ODD
```

说明：

- BettingPool 真实 ODD 余额没有减少，说明不是资金丢失；
- 当前账本把 `platformReserve` 净扣 `600 ODD`；
- 手算经济结果中，市场本金池 `2,000 ODD` 足以覆盖 `grossPayout = 1,800 ODD`，结算 margin 为 `200 ODD`；
- 该场真实不需要 L4 兜底，`platformReserve` 不应净减。

修复前错误路径：

```text
totalStake = 2,000
grossPayout = 1,800
loserStakes = 1,000
oldNetLoss = 1,800 - 1,000 = 800
platformReserve += 200 margin
platformReserve -= 800 virtual deficit
net platformReserve delta = -600
```

期望路径：

```text
totalMargin = 2,000 * 10% = 200
selfFundedPayout = totalStake - totalMargin = 1,800
newNetLoss = max(grossPayout - selfFundedPayout, 0) = 0
platformReserve += 200 margin
net platformReserve delta = +200
```

## 4. 影响范围

直接影响：

- `platformReserve` 被虚减；
- `taxBuffer` 可能被虚耗；
- `lpLossOffsetRemaining` 和 LP payout reserve 可能被虚高 book；
- `placeBet` 的 `availableLiquidity` 因包含 `platformReserve`，会被虚低的 L4 账本影响；
- `platformReserve <= BettingConstants.EMERGENCY_FLOOR` 可能误触发 `_pause()`。

不直接影响：

- 当前未发现因此造成 `BettingPool` 实际 ODD 余额小于 `accountedBalance`；
- 不改变用户 claim 的 `grossPayout / netPayout`；
- 不改变下注税、派奖税、推荐奖励、staking reward 分配公式；
- 不改变 LP requestable liquidity 接口和 payout reserve release 机制。

## 5. 修复原则

本 hotfix 采用最小修复原则：

1. 不改 ABI。
2. 不改 storage layout。
3. 不新增合约或模块。
4. 不改 `placeBet` / `placeParlay` 的 gross payout 风控口径。
5. 不改 claim、refund、cashout 的外部行为。
6. 不改瀑布顺序，仍为 L2 LP -> L3 taxBuffer -> L4 platformReserve。
7. 只修正结算时传入瀑布的 `netLoss`。
8. 同步测试期望值与文档，避免旧保守口径被再次固化。

## 6. 修复方案

### 6.1 统一公式

结算瀑布只应承担真实缺口：

```text
selfFundedPayout = fundingBase - totalMargin
netLoss = grossPayout > selfFundedPayout
    ? grossPayout - selfFundedPayout
    : 0
```

其中：

- 普通单注 `fundingBase = context.totalStake`，该值必须使用代码中已累计的 `winStake + lossStake`，不能改成 raw accepted total，也不能把已退回的 `refundStake` 加回来；
- 串关赢单 `fundingBase = parlay.stake`，仅适用于 `WonUnclaimed` 分支；`Refundable` 分支已按 `claimablePayout <= stake` 处理为本金退款，不进入瀑布；
- `totalMargin = fundingBase * 1000 / PrecisionConstants.BPS_SCALE`；
- 当前 margin 固定为 10%，因此 `totalMargin <= fundingBase`，无需 `unchecked`。

### 6.2 普通单注改动点

文件：`src/modules/betting/BettingSettlementModule.sol`

位置：`finalizeMarketSettlement` 正常结算分支，`totalMargin` 已计算完成后。

已实施：

```solidity
uint256 totalMargin = context.totalStake * 1000 / PrecisionConstants.BPS_SCALE;
context.lpMarginShare = totalMargin * lpMarginShareBps / PrecisionConstants.BPS_SCALE;
context.platformMarginShare = totalMargin - context.lpMarginShare;

uint256 selfFundedPayout = context.totalStake - totalMargin;
context.netLoss = context.grossPayout > selfFundedPayout
    ? context.grossPayout - selfFundedPayout
    : 0;
```

已删除旧逻辑：

```solidity
context.netLoss = context.grossPayout > context.loserStakes
    ? context.grossPayout - context.loserStakes
    : 0;
```

### 6.3 串关改动点

文件：`src/modules/betting/BettingParlayModule.sol`

位置：`settleParlay` 中 `context.grossPayout > parlay.stake` 的赢单分支。

已实施：

```solidity
uint256 totalMargin = parlay.stake * 1000 / PrecisionConstants.BPS_SCALE;
uint256 selfFundedPayout = parlay.stake - totalMargin;
uint256 netLoss = context.grossPayout > selfFundedPayout
    ? context.grossPayout - selfFundedPayout
    : 0;

context.lpLossBooked = _applyParlaySettlementAccounting(
    parlay.parlayRiskId,
    context.marginBase,
    netLoss,
    context
);
```

旧逻辑中 `context.grossPayout <= parlay.stake` 的 `Refundable` 路径已经不走瀑布，应保持不变；`Lost` 路径也保持 `netLoss = 0`。不要把串关的 `netLoss` 计算下沉到 `_applyParlaySettlementAccounting` 并用 `marginBase` 反推所有状态，因为 `Refundable` 的 `marginBase = stake - claimablePayout`，该路径不应产生任何亏损瀑布。

### 6.4 可选去重

为避免串关分支和 `_applyParlaySettlementAccounting` 重复计算 `totalMargin`，可新增一个很小的内部 pure helper：

```solidity
function _netSettlementLoss(uint256 grossPayout, uint256 fundingBase)
    internal
    pure
    returns (uint256 netLoss)
{
    uint256 totalMargin = fundingBase * 1000 / PrecisionConstants.BPS_SCALE;
    uint256 selfFundedPayout = fundingBase - totalMargin;
    return grossPayout > selfFundedPayout ? grossPayout - selfFundedPayout : 0;
}
```

本次最终实现未抽 helper：普通单注直接复用已有 `totalMargin`，串关赢单分支局部计算 `totalMargin / selfFundedPayout / netLoss`。这样不会改变 ABI、storage layout 或可见函数，也避免把 `Refundable` 的 `marginBase` 误用于亏损瀑布。

## 7. LP payout window 安全性

修复会降低 L2 book 的 `netLoss`，因此需要确认 LP payout reserve window 仍足够覆盖 claim 时真实拉款。以下证明只针对有活跃 LP 权重、确实创建 L2 payout window 的情况；无 LP 时不会创建 L2 window，缺口直接按新 `netLoss` 进入 L3/L4。

### 7.1 普通单注

修复后：

```text
window = grossPayout - totalStake + totalMargin
```

claim 时 BettingPool 在该 market 局部口径下最多需要从 LP 拉的钱：

```text
actualPull = grossPayout - (totalStake - lpMarginShare)
```

两者差值：

```text
window - actualPull
= (grossPayout - totalStake + totalMargin)
  - (grossPayout - totalStake + lpMarginShare)
= totalMargin - lpMarginShare
= platformMarginShare >= 0
```

实际执行中，如果 BettingPool 还有其他可用余额，`requestPayoutLiquidity` 可能少于这个局部上限；因此上述推导是保守上限。新 window 仍然不短缺。

### 7.2 串关

串关将 `totalStake` 替换为 `parlay.stake`，推导相同：

```text
window = grossPayout - stake + totalMargin
actualPull = grossPayout - (stake - lpMarginShare)
window - actualPull = platformMarginShare >= 0
```

因此串关 Global LP payout window 也不会因为本 hotfix 变小而短缺。
