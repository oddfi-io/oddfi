## 1. 测试反馈的 bug

测试反馈文件 `/Users/hawkwu/Downloads/ODD-结算缺口计算Bug-修复说明-终版.md` 指出：普通单注正常结算时，旧口径使用 `grossPayout - loserStakes` 作为 `netLoss`，没有把赢家自己的本金扣除 settlement margin 后的池内可自付资金计入，导致冷启动无 LP 时把本不需要兜底的赔付误判为 L4 缺口。

本次检查确认串关也有同类问题：旧赢单分支直接把整笔 `grossPayout` 作为 `netLoss` 送入 Global L2 -> L3 -> L4 瀑布。

修复后统一口径：

```text
selfFundedPayout = fundingBase - totalMargin
netLoss = max(grossPayout - selfFundedPayout, 0)
```

- 普通单注：`fundingBase = settlement progress.totalStake`，即未退回的 `winStake + lossStake`。
- 串关赢单：`fundingBase = parlay.stake`。
- `Refundable / Lost` 不进入亏损瀑布。

## 2. 修复前复现

普通单注冷启动复现输入：

```text
无 LP
初始 platformReserve = 1,000,000 ODD
双边各押 1,000 ODD
两边赔率均为 1.8
下注税 1%
结算 margin 10%
主队获胜，用户 1 胜，用户 2 负
```

修复前临时 Foundry 复现输出：

```text
platformReserve: 1,000,000 ODD -> 999,400 ODD
BettingPool ODD balance: 1,002,000 ODD -> 1,002,000 ODD
```

结论：真实余额没有减少，不是资金丢失；旧公式把 `grossPayout 1,800 - loserStakes 1,000 = 800 ODD` 当作缺口，导致 `platformReserve` 在已入账 `200 ODD` margin 后仍净减 `600 ODD`。

串关冷启动旧口径模型：

```text
stake = 100 ODD
grossPayout = 400 ODD
totalMargin = 10 ODD
oldNetLoss = grossPayout = 400 ODD
platformReserve delta = +10 - 400 = -390 ODD
```

真实经济缺口应为 `400 - 100 = 300 ODD`。

## 5. 验收结论

1. 普通单注冷启动平衡盘不再虚扣 `platformReserve`，改为只入账 settlement margin。
2. 普通单注真实亏损盘只扣 `grossPayout - (totalStake - totalMargin)`。
3. 串关赢单只扣 `grossPayout - (stake - totalMargin)`，不再把整笔 `grossPayout` 送入 L4。
4. 有 LP 的普通单注和串关资金流仍可 claim，并可释放剩余 payout reserve。
5. `BettingPool.accountedBalance == ODD.balanceOf(BettingPool)` 的资金闭合断言保持通过。
6. 非 fork 全量回归、E2E、场景测试、fuzz 和 invariant 均通过。
