# OddFi 合约场景测试文档（基于 v2.1 规则文档）

> 当前实现说明：本文保留为链上场景验收清单，当前合约实现事实以 `docs/progress/当前开发现状.md`、`docs/development/api.md` 和 `src/` 为准。旧版字符串 revert 预期已统一按当前自定义 error 口径理解。当前结算口径统一为 `getMarketBetIds -> settleMarketBetsByScore -> finalizeMarketSettlement`；Cash Out 已作为用户提前终态路径实现；旧 `settleMarket / settleMarketBets(winningOutcome) / pushRefundMarket` 不再属于当前 ABI。
>
> 2026-06-03 BSC Testnet live 补充：当前 5 秒 `CASH_OUT_QUOTE_TTL` 在真实 RPC/出块窗口下导致未 lock 的 `cashOut` 交易 `status=0`，详见 `docs/testing/2026-06-03-bsc-testnet-cashout-upgrade-report.md`。本地/单元测试通过不等于线上 Cash Out 已验收通过。

**文档目的**
- 本文档用于 OddFi 合约开发完成后的验收测试，目标是验证链上实现是否与当前产品规则文档一致。
- 本文档尽量把“规则描述”翻译成“可执行测试场景”，只保留**能在合约测试里直接断言**的内容。
- 本文档当前只覆盖两类验证：**链上强校验**、**链上账务校验**。

**纯合约范围说明**
- 只测试合约本身的权限、状态流转、账务分配、参数约束、事件、时间边界和跨合约联动。
- **不测试**：Redis、WebSocket、Telegram、PagerDuty、前端弹窗、按钮交互、人工审核队列、运营值班、多签钱包实现、多签审批流程本身、外部赔率拉取、后端排队与缓存。
- 若某条产品规则本质上依赖后端或运营系统，而不是链上合约，本版文档将明确标记为“非合约范围”，不纳入执行。

**基线文档（单一事实源）**

- `代币_规则设计.md`（2026-04-22）

**冲突处理原则**
- 若模块文档与旧版本口径冲突，以 2026-04-22 版本为准。
- 若跨文档存在术语冲突，以 `全局_术语表.md` 为准。
- 若“正常流程”和“当前限制”冲突，验收时应先确认本轮开发范围：
  - 若本轮目标是“按 v2.1 全量规则交付”，则以正常流程为验收目标；
  - 若本轮目标是“MVP/阶段性交付”，则需在测试开始前明确哪些案例属于延期项。

## 一、建议测试环境

### 1.1 部署环境
- 当前本地自动化验收以 Foundry fork-free 测试为准，可直接执行 `forge test --offline --no-match-path 'test/Fork*' -vv`。
- `test/ForkMainnet*.t.sol` 仍保留为主网 fork 验证套件；只有提供 `MAINNET_FORK_RPC_URL` 时才执行。
- 所有代币金额统一按 `18 decimals` 验证。
- 必须支持时间推进（`warp` / `evm_increaseTime`）与块推进。
- 必须可模拟多角色调用与授权地址调用。

### 1.2 角色建议
- `owner`：平台 Owner / 管理员地址。
- `settler`：被合约授权执行结算/退款的地址。
- `treasury`：平台金库地址。
- `alice`、`bob`、`carol`、`dave`：普通下注用户。
- `ref1`、`ref2`：推荐人地址。
- `stk1`、`stk2`：质押用户。
- `lpG1`、`lpG2`：全局池 LP。
- `lpM1`：比赛独立池 LP。
- `ops`：运营观察地址，用于告警/事件验证。

### 1.3 默认初始化参数
- ODD 总量：`100,000,000 ODD`。
- 最小下注：`100 ODD`。
- 下注税：`1%`。
- 派奖税：`5%`。
- 派奖税默认分配：`2pp 质押池 / 1pp L3 taxBuffer / 1pp 平台 / 1pp 推荐人`。
- 最小质押量：`100 ODD`。
- 最小 LP 存入：`1,000 ODD`。
- 全局池档位：`7 / 14 / 28 / 60 / 90 天`。
- 质押档位：`7 / 30 / 60 / 90 / 180 / 360 天`（其中 180/360 天可能仅合约开放）。
- Margin 率：`10%`。
- `BettingConstants.TAX_BUFFER_CAP`：`500,000 ODD`。
- `BettingConstants.EMERGENCY_FLOOR`：`100,000 ODD`。
- `BettingConstants.PLATFORM_RESERVE_INITIAL`：`15,000,000 ODD`，当前仅是常量口径，不会在 `BettingPool.initialize` 中自动写入 `platformReserve`。
- 串关总赔率上限：`x200`。
- 串关最大腿数：`6`。

### 1.4 建议基础夹具
- `Match-A`：1x2 市场，用于下注、结算、派奖税测试。
- `Match-B`：让球 `-1` 市场，用于 AH full push 的正常比分结算测试。
- `Match-C`：大小球 `2.5` 市场，用于独立市场和正常胜负测试。
- 所有市场都准备一组可人工计算的 Base Odds 与下注分布样例。

## 二、全局验收原则

### 2.1 全局不变量
- 所有税额计算、分配计算、rewardPerShare 计算必须可复算。
- 未明确说明向上舍入的地方，一律按文档要求做 `floor`，并验证余数去向。
- 任何状态流转都必须单向，不允许回滚到前态。
- 任何用户都不能重复领取同一笔收益、派奖、推荐奖励。
- 资金分层必须严格遵守 `L1 -> L2 -> L3 -> L4`，除非该层余额本身为 0。

### 2.2 建议统一核对项
每个测试场景至少记录以下内容：
- 交易前后余额变化。
- 合约内部关键账本变化。
- 订单/仓位状态变化。
- 事件是否触发、参数是否正确。
- 若涉及快照：快照前参数、快照值、快照后参数变更是否影响历史订单。

### 2.3 推荐输出格式
每个场景执行后建议记录：
- 用例编号
- 通过 / 失败
- 实际交易哈希
- 实际返回值 / revert 原因
- 与预期不一致点
- 是否阻塞主网 / 审计

## 四、ODD / 基础权限场景

### DEP-001 固定总量与一次性铸造
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §5`
- 前置条件：部署 ODD 合约。
- 步骤：
  1. 读取 `totalSupply()`。
  2. 校验初始接收地址余额。
  3. 检查是否存在额外增发入口，或尝试调用可能的 mint 类方法。
- 预期结果：
  - `totalSupply = 100,000,000e18`。
  - 总量在部署后不再增加。
  - 不存在产品规则之外的增发路径。

### DEP-002 ERC20 / BEP-20 兼容最小能力集
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §5`
- 步骤：
  1. 验证 `transfer / transferFrom / approve / balanceOf / allowance / totalSupply` 正常可用。
  2. 检查 ODD 层是否还保留买入税、卖出利润税、白名单、推荐关系、成本基准等旧接口。
- 预期结果：
  - ODD 仅体现标准 ERC20 + AccessControl + Pausable 能力。
  - ODD 层不存在 v1 已废止逻辑的有效入口。

### DEP-003 ODD 转账不收税
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §5`
- 步骤：
  1. `alice -> bob` 普通转账 `1,000 ODD`。
  2. 再执行 `bob -> carol` `123.456 ODD`。
- 预期结果：
  - 接收方到账金额与转出金额完全一致。
  - 平台、税池、黑洞地址均无额外进账。

### DEP-004 权限边界
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §角色与权限`、`对赌池_规则设计.md §角色与权限`
- 步骤：
  1. 非 owner 尝试 `pause/unpause`。
  2. 非 owner 尝试修改税率、配置金库、配置准备金。
  3. 非授权地址尝试比分分批结算、终态标记或分批退款。
- 预期结果：
  - 全部越权调用失败。
  - 只有文档定义角色能操作对应函数。

### DEP-005 pause 生效范围
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §异常流程`
- 步骤：
  1. `owner` 暂停 ODD。
  2. 尝试普通转账、`placeBet`、`claimPayout`、`claimReferralRewards`。
  3. 恢复 ODD 后重试。
- 预期结果：
  - ODD 暂停期间所有依赖 ODD 转账的路径都失败。
  - 恢复后重新可用。

## 五、推荐关系、下注税、派奖税场景

### REF-001 显式绑定推荐人成功
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §1`
- 前置条件：`alice` 尚未绑定推荐人。
- 步骤：
  1. `alice` 调用 `bindReferrer(ref1)`。
  2. 读取 `referrers[alice]`。
- 预期结果：
  - 绑定成功。
  - `referrers[alice] = ref1`。
  - 后续不可修改或解绑。

### REF-002 首次下注自动绑定推荐人
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §1`
- 前置条件：`bob` 未绑定推荐人。
- 步骤：
  1. `bob` 首次 `placeBet` 时传入 `ref2`。
  2. 下注完成后读取 `referrers[bob]`。
- 预期结果：
  - 下注成功。
  - 推荐关系自动绑定为 `ref2`。

### REF-003 二次绑定被拒绝
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §异常流程`
- 前置条件：`alice` 已绑定 `ref1`。
- 步骤：
  1. `alice` 再次调用 `bindReferrer(ref2)`。
- 预期结果：
  - revert：当前实现为自定义 error `InvalidReferrerBinding()`。

### REF-004 自荐与零地址绑定被拒绝
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §异常流程`
- 步骤：
  1. `alice` 调用 `bindReferrer(alice)`。
  2. `alice` 调用 `bindReferrer(address(0))`。
- 预期结果：
  - 分别 revert：当前实现均为自定义 error `InvalidReferrerBinding()`。

### REF-005 推荐资格与质押状态彻底解耦
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §1`、`质押_规则设计.md §当前限制`
- 步骤：
  1. 使用一个从未质押过、也没有上级推荐人的地址 `ref2`。
  2. 让 `bob` 绑定 `ref2` 并完成下注。
  3. 再让 `ref2` 在始终无质押仓位的前提下领取推荐奖励。
- 预期结果：
  - `ref2` 无需“有效质押量 > 0”即可成为合法推荐人。
  - `ref2` 自身是否有上级推荐关系，不影响其作为他人推荐人的资格。
  - 不应出现 v1 遗留的 `isActiveStaker` 或 stake 门槛限制。

### TAX-001 有推荐人的下注税分配
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §2`
- 前置条件：`alice` 已绑定 `ref1`。
- 步骤：
  1. `alice` 下注 `1,000 ODD`。
  2. 按默认下注税 `1%` 复算税额。
  3. 读取 `referrerRewardsOdd[ref1]` 与 `alice` 余额变化。
- 预期结果：
  - 下注税 = `10 ODD`。
  - 用户总扣款 = `1,010 ODD`。
  - 下注本金记为 `1,000 ODD`。
  - `referrerRewardsOdd[ref1]` 增加 `10 ODD`。

### TAX-002 无推荐人的下注税转平台
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §2`
- 前置条件：`bob` 无推荐关系。
- 步骤：
  1. `bob` 下注 `1,000 ODD`。
  2. 读取平台金库余额变化。
- 预期结果：
  - 平台金库增加 `10 ODD`。
  - `referrerRewardsOdd` 无新增。

### TAX-003 最小下注金额校验
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §2`、`对赌池_规则设计.md §边界条件`
- 步骤：
  1. 使用 `99.999999999999999999 ODD` 下注。
  2. 使用 `100 ODD` 下注。
- 预期结果：
  - 小于 `100 ODD` 的下注 revert：当前实现为自定义 error `BetAmountBelowMinimum(...)`。
  - 等于 `100 ODD` 的下注可继续进入后续校验流程。

### TAX-004 余额不足支付本金+下注税
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §异常流程`
- 前置条件：`carol` 钱包仅有 `1,000 ODD`。
- 步骤：
  1. `carol` 尝试下注 `1,000 ODD`。
- 预期结果：
  - 因还需支付 `10 ODD` 下注税而失败。
  - revert：当前实现为底层 ERC20 allowance / balance 相关错误。

### TAX-005 下注税 floor 舍入
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §边界条件`
- 步骤：
  1. 构造一个会产生非整税额的下注金额，例如 `100.123456789123456789 ODD`。
  2. 读取税额、平台/推荐奖励账本。
- 预期结果：
  - 税额按最小单位向下取整。
  - 用户实付不超过 `amount + floor(amount * taxRate)`。
  - 舍入余数不额外发给用户。

### TAX-006 晚绑定对“未结算订单”的派奖推荐份额生效
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §1`、`§3`
- 前置条件：
  - `bob` 首次下注时无推荐人；
  - 该订单尚未完成 score-based 结算。
- 步骤：
  1. `bob` 下单并进入 `Pending`。
  2. `bob` 之后调用 `bindReferrer(ref2)`。
  3. 市场结算，该订单胜出。
  4. `bob` 调用 `claimPayout`。
- 预期结果：
  - 该订单的下注税仍不追溯给 `ref2`。
  - 该订单在 score-based 结算时锁定的“推荐人派奖份额”归属 `ref2`。
  - `referrerRewardsOdd[ref2]` 在用户 Claim 后增加对应派奖份额。

### TAX-007 晚绑定对“已结算订单”不追溯
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §1`
- 前置条件：
  - `bob` 有一笔无推荐人的已结算胜单，但尚未 Claim；
  - 该订单在 score-based 结算时没有推荐人。
- 步骤：
  1. 订单 score-based 结算完成后，`bob` 再绑定 `ref2`。
  2. `bob` 执行 `claimPayout`。
- 预期结果：
  - 该订单的推荐人派奖份额不归 `ref2`。
  - 该份额并入平台金库。

### TAX-008 默认派奖税分配路径
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §3`
- 前置条件：
  - 一笔胜单 `claimablePayout = 2,000 ODD`；
  - 订单在 `settle` 时锁定默认税率 `5%` 与默认比例 `2/1/1/1`；
  - 用户有推荐人 `ref1`。
- 步骤：
  1. 用户执行 `claimPayout`。
  2. 复算派奖税与四项分配。
- 预期结果：
  - 派奖税 = `100 ODD`。
  - 用户净到账 = `1,900 ODD`。
  - 质押池增加 `40 ODD`。
  - L3 taxBuffer / 对赌池填充入口增加 `20 ODD`。
  - 平台金库增加 `20 ODD`。
  - `referrerRewardsOdd[ref1]` 增加 `20 ODD`。

### TAX-009 无推荐人的派奖税退化路径
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §3`
- 前置条件：一笔无推荐绑定用户的胜单 `claimablePayout = 2,000 ODD`。
- 步骤：用户执行 `claimPayout`。
- 预期结果：
  - 质押池仍获得 `40 ODD`。
  - L3 仍获得 `20 ODD`。
  - 平台金库获得 `40 ODD`（平台份额 `20` + 推荐人份额 `20`）。

### TAX-010 派奖税快照在 score-based 结算锁定，claim 不受后续参数变更影响
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §3`
- 前置条件：
  - 订单 A 在税率 `5%`、分配 `2/1/1/1` 下完成 score-based 结算；
  - 之后 owner 将税率改为 `6%`，分配改为 `3/1/1/1`。
- 步骤：
  1. 订单 A 延后 Claim。
  2. 同时再创建订单 B，并在新配置下 score-based 结算后 Claim。
- 预期结果：
  - 订单 A 仍按 `5%` 和 `2/1/1/1` 扣税。
  - 订单 B 按 `6%` 和 `3/1/1/1` 扣税。
  - 两笔订单快照互不污染。

### TAX-011 派奖税 floor 舍入与余数去向
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §边界条件`
- 步骤：
  1. 构造会产生非整税额的 `claimablePayout`。
  2. 对比理论值与实际到账值。
- 预期结果：
  - 税额按 floor。
  - 用户净到账 = `payout - floor(tax)`。
  - 舍入余数并入平台金库，不改变其余份额的快照比例口径。

### TAX-012 推荐奖励 Claim 成功与零余额失败
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §4`
- 步骤：
  1. 先为 `ref1` 累积一笔推荐奖励。
  2. `ref1` 调用 `claimReferralRewards`。
  3. 再次调用 `claimReferralRewards`。
- 预期结果：
  - 第一次 Claim 成功，累计余额清零或按实际提取量减少。
  - 触发 `ReferralClaimed` 事件。
  - 第二次若余额为 0，revert：当前实现为自定义 error `InvalidReferralClaim()`。

### TAX-013 Owner 成功修改税率、分配比例与平台金库
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §角色与权限`、`§3`
- 步骤：
  1. owner 将下注税从 `1%` 调整为 `2%`。
  2. owner 将派奖税从 `5%` 调整为 `6%`。
  3. owner 将派奖税分配调整为 `3pp / 1pp / 1pp / 1pp`。
  4. owner 更新平台金库地址为新地址 `treasury2`。
  5. 分别创建一笔新下注和一笔新结算胜单进行验证。
- 预期结果：
  - 参数更新成功。
  - 新下注按 `2%` 扣下注税。
  - 在新配置下 `settle` 的胜单，Claim 时按 `6%` 和新四项比例扣税。
  - 平台份额流向新金库地址 `treasury2`。
  - 历史已 `settle` 的旧订单不受影响。

### TAX-014 输注、退款、返本场景不征派奖税
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §3`
- 步骤：
  1. 准备一笔输单。
  2. 准备一笔 AH full push 正常比分结算中的退款注单。
  3. 准备一笔“派彩 <= 本金”的返本/退款兜底单。
  4. 分别执行 score-based 结算或 `finalizeMarketSettlement + refundBets` 退款路径。
- 预期结果：
  - 以上场景均不扣派奖税。
  - 质押池、L3、平台、推荐奖励账本都不应因这些订单发生派奖税分配。

### TAX-015 `payout <= principal` 的兜底路径
- 优先级：`P2 / 合约范围确认`
- 来源：`代币_规则设计.md §3`
- 步骤：
  1. 人为构造一个理论上不应出现、但合约需兜底的订单：`claimablePayout <= principal`。
  2. 执行 Claim 或等价结算路径。
- 预期结果：
  - 该订单按“退款/返本”语义处理，不征派奖税。
  - 不允许产生负税或把返本也当作胜单税基。

### TAX-016 极小派彩的 `payout too small` 兜底
- 优先级：`P2 / 合约范围确认`
- 来源：`代币_规则设计.md §异常流程`
- 步骤：
  1. 在测试环境中直接构造一个极小 `claimablePayout`，使 `payout - tax == 0`。
  2. 调用 `claimPayout`。
- 预期结果：
  - revert：当前实现为自定义 error `PayoutTooSmall()`。
  - 若由于最小下注限制而无法从真实业务流触发，也应通过专用测试夹具覆盖该防御分支。

### TAX-017 推荐人黑名单不在链上校验范围内
- 优先级：`P2 / 合约范围确认`
- 来源：`代币_规则设计.md §边界条件`
- 步骤：
  1. 为 `ref1` 累积推荐奖励。
  2. 在不做任何链上黑名单设置的前提下，由 `ref1` 直接调用 `claimReferralRewards`。
- 预期结果：
  - BettingPool 合约侧不做黑名单校验。
  - 若业务上需要黑名单限制，应由链下账户层或前端拦截，而不是链上静默失败。

## 六、对赌池核心状态流与结算场景

### BET-001 市场开关与下注前置校验
- 优先级：`P0 / 链上强校验`
- 来源：`对赌池_规则设计.md §1`、`§3`
- 步骤：
  1. 创建市场并确认 `open=true`。
  2. 在开赛前下注。
  3. 将时间推进到比赛开始后但比赛结束前，未手动封锁时再次下注。
  4. 由后端手动封锁 market 后再次下注。
  5. 将时间推进到比赛结束后再次下注。
- 预期结果：
  - 开盘状态下注可通过。
  - 未手动封锁且未到 `matchEndTime` 时，比赛开始后下注仍可通过。
  - 手动封锁后下注失败，按自定义 error `MarketLocked(bytes32)` 回滚。
  - 比赛结束后下注失败，按自定义 error `MarketClosed(bytes32)` 回滚。

### BET-002 placeBet 成功后的账本变化
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_规则设计.md §3`
- 步骤：
  1. 用户在某方向下注。
  2. 检查 bet 记录、`totalStaked`、`totalPotentialPayout`、用户未平仓。
- 预期结果：
  - 生成新 betId。
  - bet 状态为 `Pending`。
  - 方向总投注与潜在赔付正确增加。
  - 用户未平仓金额增加。

### BET-003 score-based 分批结算后胜负状态流转
- 优先级：`P0 / 链上强校验`
- 来源：`对赌池_规则设计.md §7`
- 步骤：
  1. 创建同一市场的胜负双方订单。
  2. 通过 `getMarketBetIds` 分页读取 betIds。
  3. 执行 `settleMarketBetsByScore(marketId, homeScore, awayScore, betIds)`。
  4. 全部 bet 处理完后执行 `finalizeMarketSettlement(marketId, 0)`。
- 预期结果：
  - 胜出方向订单从 `Pending -> Won（待 Claim）`。
  - 失败方向订单从 `Pending -> Lost`。
  - 市场状态进入 `Settled`。
  - 获胜订单记录 `claimablePayout` 与税率/分配/推荐快照。

### BET-004 claimPayout 仅允许 Won（待 Claim）状态
- 优先级：`P0 / 链上强校验`
- 来源：`对赌池_规则设计.md §异常流程`
- 步骤：
  1. 对 `Pending`、`Lost`、`Refunded`、`Claimed` 订单分别调用 `claimPayout`。
- 预期结果：
  - 非 `Won（待 Claim）` 的订单全部失败。
  - 已 Claimed 订单再次 Claim revert：当前实现为自定义 error `PayoutAlreadyClaimed(bytes32)` 或等价保护。

### BET-005 claimPayout 成功后的终态
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_规则设计.md §7`
- 步骤：
  1. 对一笔 `Won（待 Claim）` 订单执行 `claimPayout`。
  2. 再次读取订单状态和用户余额。
- 预期结果：
  - 用户收到净派奖。
  - 订单状态变为 `Claimed`。
  - 不允许再次 Claim。

### BET-006 claim 无期限
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_规则设计.md §7`、`§边界条件`
- 步骤：
  1. 订单胜出后不立即 Claim。
  2. 时间推进很长一段时间。
  3. 再执行 Claim。
- 预期结果：
  - 只要订单仍是 `Won（待 Claim）`，无论延迟多久都可以 Claim。

### BET-007 claim 时合约余额不足
- 优先级：`P0 / 链上强校验`
- 来源：`对赌池_规则设计.md §异常流程`
- 步骤：
  1. 人为制造 BettingPool 可用 ODD 余额不足。
  2. 用户对已胜订单执行 `claimPayout`。
  3. 之后补充 ODD 再次 Claim。
- 预期结果：
  - 第一次 Claim revert。
  - 订单状态仍保持 `Won（待 Claim）`。
  - 补充余额后可重新 Claim 成功。

### BET-008 BettingPool 暂停时 settlement 可继续但 claim 仍被阻断
- 优先级：`P1 / 链上强校验`
- 来源：`对赌池_规则设计.md §异常流程`
- 步骤：
  1. 暂停 BettingPool。
  2. 尝试由 `settler` 调用 `settleMarketBetsByScore` 与 `finalizeMarketSettlement`。
  3. 尝试用户 `claimPayout`。
  4. 恢复后再次 `claimPayout`。
- 预期结果：
  - 暂停期间不阻断已接订单的结算收口，避免历史 market 卡死。
  - 暂停期间 `claimPayout` 失败。
  - 恢复后可正常领取。

### BET-009 placeBet / claim / referralClaim 的暂停影响
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §异常流程`
- 步骤：
  1. 暂停 BettingPool。
  2. 分别调用 `placeBet`、`claimPayout`、`claimReferralRewards`。
- 预期结果：
  - 全部失败。
  - 恢复后可再次执行。

### BET-010 Cash Out 提前关闭 Pending 注单
- 优先级：`P0 / 链上强校验`
- 来源：`OddFi-CashOut规则与计算公式-v1.1.md`
- 步骤：
  1. 用户在 `Open` market 下单。
  2. 前端读取当前 bet、market odds 和 `quoteVersion`，计算 `minAmountOut`。
  3. 用户调用 `cashOut(betId, quoteVersion, quotedAt, minAmountOut, deadline)`。
- 预期结果：
  - bet 状态变为 `CashedOut`。
  - 用户收到 `cashOutAmount`。
  - 对应 `S_i/P_i`、用户未结算风险和用户 market 潜在赔付被释放。
  - `dailyAcceptedAmount` 不回滚。
  - 同一 bet 不能再次 Cash Out、refund、settle 或 claim。
  - BSC Testnet live 当前未通过：2026-06-03 验收中真实 `cashOut` 交易 `status=0`，需先修正 5 秒 quote TTL 后重跑。

### BET-011 Locked market 禁止 Cash Out
- 优先级：`P0 / 链上强校验`
- 来源：`OddFi-CashOut规则与计算公式-v1.1.md`
- 步骤：
  1. 用户在 `Open` market 下单。
  2. 后端调用 `lockMarket(marketId)` 手动封锁 market。
  3. 用户尝试对该 bet 调用 `cashOut`。
- 预期结果：
  - Cash Out 失败，当前实现为自定义 error `MarketLocked(bytes32)`。
  - bet 保持 `Pending`，后续只能等待最终结算或退款。

### STK-011 StakingPool 暂停的联动影响

### STK-012 查询接口与下注侧实时读取
- 优先级：`P1 / 链上账务校验`
- 来源：`质押_规则设计.md §角色与权限`、`§5`

- 预期结果：
  - 查询结果与实际活跃本金、VIP 等级一致。
  - 对赌池在下注限额校验时读取的是实时值，而不是缓存值。

### STK-013 多仓位独立 rewardDebt、权重与解锁时间

- 预期结果：
  - 多仓位独立记账。
  - 后创建仓位不应分享创建前已经累积的 rewardPerShare。

### STK-014 到期赎回时合约余额不足

### STK-015 pause 对质押主路径的阻断

  - 暂停期间上述操作均失败。

## 九、做市 LP、Margin、解绑与提取场景

### LP-001 全局池存入档位与最小值
- 优先级：`P0 / 链上强校验`
- 来源：`做市_规则设计.md §1`
- 参数矩阵：

| 档位 | 天数 | 展示乘数 | 预期 |
|-----|-----|---------|-----|
| 7d | 7 | 0.5x | 可存入 |
| 14d | 14 | 1.0x | 可存入 |
| 28d | 28 | 1.8x | 可存入 |
| 60d | 60 | 2.5x | 可存入 |
| 90d | 90 | 3.5x | 可存入 |

- 额外校验：
  - `< 1,000 ODD` 存入失败。
  - `= 1,000 ODD` 存入成功。

### LP-002 比赛独立池存入规则
- 优先级：`P0 / 链上强校验`
- 来源：`做市_规则设计.md §2`
- 步骤：
  1. 在比赛开放期向独立池存入。
  2. 比赛开赛后再次存入。
- 预期结果：
  - 开赛前可存入。
  - 开赛后 `depositOpen=false`，不能继续存入。
  - 独立池乘数固定 `1.0x`。

### LP-003 独立池乘数固定校验
- 优先级：`P2 / 合约范围确认`
- 来源：`做市_规则设计.md §边界条件`、`§当前限制`
- 步骤：
  1. 尝试以非 `1.0x` 值创建或注入独立池参数。
- 预期结果：
  - 理想实现：合约直接拒绝。
  - 若仍处于 H3 限制期，则需记录为已知缺口，不得默认为已满足。

### LP-004 Margin 80/20 分配
- 优先级：`P1 / 链上账务校验`
- 来源：`做市_规则设计.md §3`
- 前置条件：
  - 全局池 `G = 100,000 ODD`；
  - 独立池 `M = 50,000 ODD`；
  - 某场总投注额 `30,000 ODD`，则 Margin = `3,000 ODD`。
- 步骤：结算该场比赛。
- 预期结果：
  - LP 总分 = `2,400 ODD`；平台收益 = `600 ODD`。
  - 全局池分得 `1,600 ODD`；独立池分得 `800 ODD`。
  - `rewardPerShare` 按本金总额记账，不按展示乘数记账。

### LP-005 无 LP 时 Margin 80% 自动记入准备金
- 优先级：`P1 / 链上账务校验`
- 来源：`做市_规则设计.md §3`、`对赌池_准备金瀑布_规则设计.md §4`
- 步骤：
  1. 保持 `G + M = 0`。
  2. 结算一场有 Margin 的比赛。
- 预期结果：
  - 原本应归 LP 的 80% 自动记入 `platformReserve`。
  - 不进入 lpLossOffsetRemaining / taxBuffer 填充逻辑。

### LP-006 L2 亏损按 G/M 比例承担
- 优先级：`P1 / 链上账务校验`
- 来源：`做市_规则设计.md §5`
- 前置条件：
  - `G = 120,000 ODD`，`M = 80,000 ODD`；
  - L1 不足后的剩余亏损 = `50,000 ODD`。
- 步骤：触发结算。
- 预期结果：
  - L2 应扣减 = `50,000 ODD`。
  - 全局池承担 `30,000 ODD`。
  - 独立池承担 `20,000 ODD`。
  - 两池 `rewardPerShare` 相应下降。

### LP-007 LP 本金归零（Liquidated）
- 优先级：`P1 / 链上账务校验`
- 来源：`做市_规则设计.md §5`、`§异常流程`
- 步骤：
  1. 构造 `L2 应扣减 >= G + M` 的极端场景。
  2. 对部分 LP 仓位执行最终提取。
- 预期结果：
  - LP 本金最多扣到 0，不为负。
  - 仓位状态进入 `Liquidated` 或等价终态。
  - 剩余缺口继续抛给 L3/L4。

### LP-008 requestUnbond 只允许 Ready 状态
- 优先级：`P0 / 链上强校验`
- 来源：`做市_规则设计.md §6`
- 步骤：
  1. 对未到期仓位请求解绑。
  2. 对已到期仓位请求解绑。
- 预期结果：
  - 未到期失败。
  - 已到期成功并进入 `Unbonding`。

### LP-009 Unbonding 期间 P&L 冻结
- 优先级：`P1 / 链上账务校验`
- 来源：`做市_规则设计.md §6`、`§当前限制`
- 步骤：
  1. 记录某仓位进入 `Unbonding` 时的价值。
  2. 在等待期内继续发生其他比赛结算。
  3. 再读取该仓位价值。
- 预期结果：
  - 理想实现：Unbonding 后不再参与后续收益和亏损。
  - 若仍存在 M3 限制，应被明确标记为未满足全量规则。

### LP-010 withdraw 等待 2 个完整 Epoch
- 优先级：`P1 / 链上账务校验`
- 来源：`做市_规则设计.md §7`
- 步骤：
  1. 在任意时刻请求解绑。
  2. 先在不足 2 个完整 Epoch 时尝试提取。
  3. 再在满足 `currentEpoch >= unbondingEpoch + 2` 时提取。
- 预期结果：
  - 未到期不可提取。
  - 到期后可提取。
  - 需验证“最短约 2 天、最长约 3 天”的时间窗口。

### LP-011 withdraw 到账金额
- 优先级：`P1 / 链上账务校验`
- 来源：`做市_规则设计.md §7`
- 步骤：
  1. 分别构造 `P&L > 0`、`P&L = 0`、`P&L < 0` 三种仓位。
  2. 执行提取。
- 预期结果：
  - `P&L > 0`：到账 = `本金 + 盈利`。
  - `P&L = 0`：到账 = `本金`。
  - `P&L < 0`：到账 = `max(0, 本金 - 亏损)`。

### LP-012 全局池无提前赎回、独立池赛前无退出

  - 全部失败。

### LP-013 多仓位并存

## 十、准备金瀑布、lpLossOffsetRemaining、taxBuffer 场景

### WFL-001 仅使用 L1 的常规结算
- 优先级：`P0 / 链上强校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §1.2`、`§6`
- 步骤：
  1. 构造“获胜方向应付赔付 <= 输家下注筹码”的场景。
  2. 执行结算。
- 预期结果：
  - 不进入 L2/L3/L4。
  - 不增加 lpLossOffsetRemaining，不动用 taxBuffer / reserve。

### WFL-002 L1 后进入 L2 扣减
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §3`
- 步骤：
  1. 构造一场结算，使 `Δ > 0` 且 `G + M > 0`。
  2. 记录结算前后 LP 账本与 `lpLossOffsetRemaining`。
- 预期结果：
  - 先用输家下注筹码抵扣。
  - 剩余缺口由 L2 按当前池子存量比例承担。
  - 对应扣减累计进入 `lpLossOffsetRemaining`。

### WFL-003 L2 为 0 时允许跳到 L3
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §6`
- 步骤：
  1. 保持 `G + M = 0`，但 `taxBuffer > 0`。
  2. 执行存在缺口的结算。
- 预期结果：
  - 直接从 L3 扣减，不视为违规跳层。
  - `lpLossOffsetRemaining` 不变化。

### WFL-004 taxBuffer 覆盖 L3 缺口
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §3`
- 步骤：
  1. 让 L2 后仍剩余缺口，且 `taxBuffer` 足够覆盖。
- 预期结果：
  - `taxBuffer` 单调减少。
  - 不触发 L4。

### WFL-005 L4 动用并触发 ReserveTapped
- 优先级：`P0 / 链上强校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §3`、`§5`
- 前置条件：
  - L2、L3 之后仍有剩余缺口。
- 步骤：执行结算。
- 预期结果：
  - `platformReserve` 被扣减。
  - 任意金额的 L4 扣减都触发 `ReserveTapped`。

### WFL-006 阶梯阈值告警
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §5.1`
- 步骤：
  1. 先通过 `addPlatformReserve` 或协议内路径把 `platformReserve` 补到 `15,000,000 ODD`。
  2. 将 `platformReserve` 从 `15,000,000` 一次扣减到 `14,750,000`。
- 预期结果：
  - 应跨越 `14.9M`、`14.8M` 两档。
  - 若合约通过事件表达告警，则应按跨越档位数触发对应事件。
  - `ReserveTapped` 事件只需触发一次。

### WFL-007 `BettingConstants.EMERGENCY_FLOOR` 触发熔断
- 优先级：`P0 / 链上强校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §5.2`
- 步骤：
  1. 将 `platformReserve` 扣减至 `<= 100,000 ODD`。
  2. 尝试新下注。
  3. 尝试对已存在订单结算。
- 预期结果：
  - 自动暂停新下注接单。
  - 已接注单仍可正常等待结算。
  - 新下注因 `Pausable` 暂停保护失败。

### WFL-008 addPlatformReserve 恢复与解除熔断
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §5.2`、`§9`
- 步骤：
  1. 在熔断状态下由管理员调用 `addPlatformReserve`。
  2. 将余额恢复到 `> BettingConstants.EMERGENCY_FLOOR`。
  3. 再由管理员手动恢复接单。
- 预期结果：
  - 单纯余额恢复不等于自动恢复交易。
  - 必须完成管理员恢复动作后才能重新下注。

### WFL-009 冲抵/填充优先级：lpLossOffsetRemaining -> taxBuffer -> reserve
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §4`
- 前置条件：
  - `lpLossOffsetRemaining = 30 ODD`；
  - `taxBuffer = 100 ODD`；
  - `BettingConstants.TAX_BUFFER_CAP = 500,000 ODD`；
  - 某次 `claimPayout` 给对赌池注入 `50 ODD`。
- 步骤：执行该次 Claim。
- 预期结果：
  - 先冲抵 `lpLossOffsetRemaining 30`。
  - 剩余 `20` 再进入 `taxBuffer`。
  - 不应直接进 reserve。

### WFL-010 taxBuffer 回满后的溢出进入 reserve
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §4`、`§6`
- 前置条件：
  - `lpLossOffsetRemaining = 0`；
  - `taxBuffer = 499,990 ODD`；
  - 本次注入 `30 ODD`。
- 步骤：执行注入。
- 预期结果：
  - `taxBuffer` 最终为 `500,000 ODD`。
  - 溢出 `20 ODD` 进入 `platformReserve`。

### WFL-011 非法外部转账不计入 platformReserve
- 优先级：`P0 / 链上强校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §7`
- 步骤：
  1. 非管理员直接向 BettingPool 转入 ODD。
  2. 读取 `platformReserve`。
- 预期结果：
  - 钱包余额可能增加，但 `platformReserve` 不因该转账自动增加。
  - 必须通过合法入口记账。

### WFL-012 四层全部耗尽
- 优先级：`P0 / 链上强校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §7`
- 步骤：
  1. 构造一个极端结算，使 L1、L2、L3、L4 全部耗尽后仍存在剩余缺口。
- 预期结果：
  - 结算进入待人工介入/失败处置路径。
  - 不允许静默吞掉差额。
  - 必须留下可追踪状态。

### WFL-013 taxBuffer 和 lpLossOffsetRemaining 不允许异常值
- 优先级：`P0 / 链上强校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §7`
- 步骤：
  1. 尝试通过非预期路径让 `taxBuffer` 减少。
  2. 尝试制造 `lpLossOffsetRemaining < 0`。
- 预期结果：
  - 合约应阻止异常状态。
  - 新结算被阻塞或交易直接失败，而不是带病运行。

### WFL-014 `taxBuffer = 0` 时应直接进入 L4
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §6`
- 步骤：
  1. 构造 `taxBuffer = 0` 且 L2 后仍有剩余缺口的结算。
  2. 执行结算。
- 预期结果：
  - 直接进入 L4，不应卡在 L3。
  - `ReserveTapped` 事件按规则触发。

### WFL-015 阶梯告警同档只触发一次，充值或回注后再次跌破可重触发
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §5.1`
- 步骤：
  1. 将 `platformReserve` 首次跌破某一 100,000 ODD 档位。
  2. 在不回升的情况下再次发生同档位内扣减。
  3. 再人工充值或协议回注到该档位以上，并再次跌破该档位。
- 预期结果：
  - 第一次跌破时触发该档位对应的链上事件/状态变化。
  - 未回升前重复扣减不应重复触发同档位。
  - 充值或回注后再次跌破时，视为新的触发。

### WFL-016 `platformReserve` 允许高于 15,000,000 ODD 常量口径
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §4`、`§6`
- 步骤：
  1. 通过“无 LP 时 Margin 80% 自动注入”或填充溢出等协议内路径提高 `platformReserve`。
  2. 使其超过初始 `15,000,000 ODD`。
- 预期结果：
  - `platformReserve` 允许超过 `BettingConstants.PLATFORM_RESERVE_INITIAL` 常量口径。
  - 不应被强行截断回 `15,000,000`。

### WFL-017 初始准备金未注入时的 L4 空仓场景
- 优先级：`P1 / 链上强校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §8`
- 步骤：
  1. 在未调用 `addPlatformReserve` 初始化准备金的前提下触发一次需要 L4 的结算。
- 预期结果：
  - 该场景等价于“准备金已耗尽”。
  - 不能假定存在隐式 L4 余额。

### WFL-018 `lpLossOffsetRemaining` 冲抵不回补 LP 仓位
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §8`
- 步骤：
  1. 先制造一轮 L2 扣减，形成 `lpLossOffsetRemaining`。
  2. 记录 LiquidityPool 余额、LP 仓位 P&L 与 `totalPrincipal`。
  3. 之后通过胜单 Claim 向对赌池侧持续注入填充资金。
- 预期结果：
  - 注入份额优先减少 `lpLossOffsetRemaining`。
  - 不向 LiquidityPool 转账，不增加 LiquidityPool 余额。
  - 不恢复已扣减 LP 仓位的 P&L 或 `totalPrincipal`。

## 十一、AH full push、大小球、串关等特殊规则场景

### SPC-001 让球 -1 的 AH full push 正常结算
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_规则设计.md §6`、`赔率_规则设计.md §8.3`
- 前置条件：让球 `-1` 市场双边均有 `Pending` 注单。
- 步骤：
  1. 结算结果为主队恰好赢 1 球。
  2. 执行 `settleMarketBetsByScore(marketId, 1, 0, betIds)`。
  3. 执行 `finalizeMarketSettlement(marketId, 0)`。
- 预期结果：
  - 目标 AH 注单按 full push 原额退款，订单状态改为 `Refunded`。
  - market 仍进入 `Settled`，不进入 `Refunded / Cancelled`。
  - 不触发派奖税、margin 或瀑布亏损路径。

### SPC-002 半球线不存在 full push
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_规则设计.md §6`、`赔率_规则设计.md §8.3`、`§9.3`
- 步骤：
  1. 对 `-0.5`、`-1.5`、`1.5/2.5/3.5` 大小球分别测试 score-based 结算。
- 预期结果：
  - 不产生 full push 的整笔 `Refunded` 注单。
  - 只会正常判胜负。

### SPC-003 串关限制
- 优先级：`P2 / 合约范围确认`
- 来源：`赔率_规则设计.md §十`、`对赌池_规则设计.md §边界条件`
- 验收点：
  - 同场不可串关。
  - 最大 `6 串 1`。
  - 总赔率上限 `x200`。
  - 单张最高赔付 `30,000 ODD`。
- 说明：若本轮未实现串关合约或后台，需在范围确认中列出，不可视为已通过。

### SPC-004 AH full push 只影响目标盘口，不污染同场其他市场
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_规则设计.md §5`、`§6`
- 步骤：
  1. 同一场比赛同时存在 1x2、让球 `-1`、大小球市场。
  2. 同一比分下仅让 `-1` AH 市场触发 full push。
  3. 观察其他市场的订单状态和账本状态。
- 预期结果：
  - 只有让球 `-1` 市场的目标注单进入 `Refunded`。
  - 同场的 1x2、大小球及其他让球线不受影响。

## 十二、暂停、异常、越权与回归场景

### SEC-001 BettingPool 暂停不影响已接订单的历史状态
- 优先级：`P1 / 链上账务校验`
- 来源：`代币_规则设计.md §异常流程`、`对赌池_准备金瀑布_规则设计.md §5.2`
- 步骤：
  1. 先创建若干 `Pending` 或 `Won（待 Claim）` 订单。
  2. 暂停 BettingPool。
  3. 读取历史订单状态。
- 预期结果：
  - 历史订单状态不应被暂停动作篡改。
  - 只是新操作被阻断。

### SEC-002 熔断期间仅暂停新接单，不回退历史结算
- 优先级：`P1 / 链上账务校验`
- 来源：`对赌池_准备金瀑布_规则设计.md §5.2`、`§6`
- 步骤：
  1. 触发 `platformReserve <= BettingConstants.EMERGENCY_FLOOR`。
  2. 对熔断前已存在的市场继续执行结算。
- 预期结果：
  - 已接订单仍能按流程处理。
  - 不会因为熔断而把历史单强制退款或清空。

### SEC-003 claimPayout 的幂等性与重放保护
- 优先级：`P0 / 链上强校验`
- 来源：`对赌池_规则设计.md §7`
- 步骤：
  1. 对同一笔胜单连续调用两次 Claim。
- 预期结果：
  - 第一次成功。
  - 第二次失败。
  - 不会重复扣税或重复分配奖励。

### SEC-004 referralClaim 的幂等性与重放保护
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §4`
- 步骤：
  1. 累积一笔推荐奖励。
  2. 连续 Claim 两次。
- 预期结果：
  - 第二次在余额为 0 时失败。
  - 不会出现重复提取。

### SEC-005 参数修改的上限保护
- 优先级：`P0 / 链上强校验`
- 来源：`代币_规则设计.md §角色与权限`
- 步骤：
  1. owner 尝试把下注税设置到 `> 3%`。
  2. owner 尝试把派奖税设置到 `> 10%`。
  3. owner 尝试设置“四项比例之和 != 当前派奖税率”。
- 预期结果：
  - 全部失败。
  - 只允许在文档上限内调整。

### SEC-006 最小/最大参数边界回归
- 优先级：`P1 / 链上账务校验`
- 建议覆盖：
  - 最小下注 `100 ODD`。
  - 最小质押 `100 ODD`。
  - 最小 LP 存入 `1,000 ODD`。
  - 下注税上限 `3%`。
  - 派奖税上限 `10%`。
  - `BettingConstants.TAX_BUFFER_CAP = 500,000 ODD` 的溢出处理。
  - `BettingConstants.EMERGENCY_FLOOR = 100,000 ODD` 的熔断边界。
- 预期结果：
  - 每个边界值都应有明确且可重复的行为。
