## 1. 适用范围

### 1.1 适用
- 对赌池市场结算（`settle` 类动作）中，获胜方向应付赔付超出该市场输家下注筹码时的资金承担顺序。
- 派奖税中分配给对赌池的锁定份额进入对赌池侧后的冲抵与缓冲填充分配规则（v2 起，默认 1pp）。
- 平台准备金的状态告警与熔断暂停接单机制。

### 1.2 不适用
- 获胜方向应付赔付 ≤ 输家下注筹码的常规结算（全部由 L1 抵扣，不进入瀑布）。
- 下注阶段的风控（信号灯、滑点、漂移）——另见 `对赌池_规则设计.md`。
- 派奖税的分配比例（默认 **2pp 质押 / 1pp L3 对赌池 / 1pp 平台 / 1pp 推荐人**，运营期可动态调整）——属 `代币_规则设计.md §3` 范围。
- 下注税 1% 与推荐人 Claim swap 规则——属 `代币_规则设计.md` 范围。
- AH full push / half win / half loss 的本金退回部分——另见 `对赌池_规则设计.md`。

## 2. 角色与权限

| 角色 | 权限 | 说明 |
|------|------|------|
| 结算服务（Remy 后端 + 合约） | 触发四层瀑布扣减、产生 ReserveTapped 事件、触发熔断 | 严格按 L1→L4 顺序执行，不得跳层 |
| BettingPool 合约 | 在 `settle` 锁定胜单的派奖税率/分配比例快照，并在 `claimPayout` 时将该订单锁定给对赌池的份额（默认 1pp）按顺序用于冲抵 lpLossOffsetRemaining、填充 taxBuffer、注入 reserveBalance | v2 起由派奖税自动驱动；v1 由 ODD 合约层 `_transfer` 驱动的路径已废止 |
| 运营监控 | 订阅 ReserveTapped 事件与阶梯阈值告警；决定是否补仓、暂停市场 | 事件告警 P1，阶梯告警 P2 |
| Admin 多签 | 唯一人工调用 `addPlatformReserve` 的主体，用于准备金充值 | 直接转账至 BettingPool 不计入 platformReserve；协议内自动记账增量除外 |
| LP（用户） | 被动承担 L2 扣减；当前实现不按 lpLossOffsetRemaining 对历史 LP 仓位做真实回补 | 无主动操作权限 |

## 3. 正常流程（获胜方向应付赔付 > 输家下注筹码）

> 本节描述**一次市场结算**内的承担顺序。进入本流程的前提：该市场结算计算得出"赔付缺口" Δ = 获胜应付 − 输家下注筹码 > 0。

| 步骤 | 动作 | 资金来源 | 扣减规则 | 触发事件 |
|------|------|---------|---------|---------|
| 1 | 抵扣 L1：输家下注筹码 | loserStakes（该市场本场） | 先全额用于支付获胜方向；剩余赔付缺口 Δ 进入后续层 | — |
| 2 | 扣减 L2：用户 LP | 全局池 + 该比赛独立池 | 两池按**当前存量**比例分摊 Δ；对每个仓位按存量比例扣减 P&L；扣减量累计进入 lpLossOffsetRemaining 作为后续派奖税缓冲份额的优先冲抵指标 | LP 仓位 P&L 更新事件 |
| 3 | 扣减 L3：taxBuffer | 对赌池层 taxBuffer | 仅在 L2 仍不足时启用；taxBuffer 单调扣减，直至为 0 | — |
| 4 | 扣减 L4：reserveBalance | 平台准备金 | 仅在 L3 仍不足时启用；任何扣减（不论金额）触发 ReserveTapped | ReserveTapped（P1） |
| 5 | 熔断判定 | reserveBalance 余额 | 若扣减后余额 ≤ emergencyFloor（100,000 ODD）自动暂停接单 | ReserveBelowFloor（P0） |
| 6 | 阶梯告警判定 | reserveBalance 余额 | 每跌破 100,000 ODD 档位一次，触发阶梯告警（P2）；共 150 级 | ReserveStepAlert（P2） |

> 说明：步骤 2→3→4 不要求"全部消耗前一层后再进入下一层"之外的任何额外条件；跳层即违规。

## 4. 冲抵与缓冲填充流程（派奖税中分配给对赌池的锁定份额进入对赌池侧）

触发入口：用户调用 `BettingPool.claimPayout` 时，胜单在 `settle` 时锁定给对赌池的派奖份额（默认 1pp）流入对赌池地址。

> v2 变更（2026-04-19）：v1 的"ODD 合约 `_transfer` 分配 4pp 对赌池"已废止；注入速率从 v1 的"每笔盈利卖出 4pp"改为"每笔胜注 claimPayout 的已锁定对赌池份额（默认 1pp）"；对冷启动期 taxBuffer 填充速度有显著影响，已纳入§8 当前限制。

| 优先级 | 目标 | 条件 | 动作 |
|--------|------|------|------|
| 1 | lpLossOffsetRemaining 冲抵 | lpLossOffsetRemaining > 0 | 将本次份额优先用于减少 lpLossOffsetRemaining 指标；不向 LiquidityPool 转账，不恢复 LP 仓位的历史亏损 |
| 2 | taxBuffer 回蓄 | lpLossOffsetRemaining = 0 且 taxBuffer < taxBufferCap（500,000 ODD） | 填充至 taxBufferCap 为止；未达到 cap 前继续蓄积 |
| 3 | reserveBalance 回注 | lpLossOffsetRemaining = 0 且 taxBuffer = taxBufferCap | 剩余税收进入准备金；无上限（准备金可超过初始 15,000,000 ODD） |

> 单次处理不得跨优先级累加；必须按 1→2→3 依次判定，前一优先级未满足条件不得进入下一优先级的判定。
> 单场结算时平台 20% Margin 留在 BettingPool，并直接记入 `reserveBalance`。
> 另：若单场结算时 `G + M = 0`，原本应分配给 LP 的 Margin 80% 不进入本流程，而是直接自动记入 `reserveBalance`。

## 5. 告警机制

### 5.1 双保险告警
| 类型 | 触发条件 | 级别 | 通道 |
|------|---------|------|------|
| 事件告警（ReserveTapped） | 任意一次 L4 扣减 | P1 | Telegram + PagerDuty |
| 阶梯阈值告警（ReserveStepAlert） | 准备金余额每跌破 100,000 ODD 档位 | P2 | Telegram |

- 两类告警**独立**触发，不互相覆盖。
- 阶梯档位以准备金初始 15,000,000 ODD 向下计数，共 150 级（14.9M、14.8M、…、0.1M）。
- 同一档位只触发一次；准备金充值或自动回注后再次跌破同一档位，视为新的一次触发。

### 5.2 熔断
| 阈值 | 行为 | 解除条件 |
|------|------|---------|
| reserveBalance ≤ emergencyFloor（100,000 ODD） | 自动暂停所有对赌池接单（已接注单正常结算） | Admin 多签调用 `addPlatformReserve` 使余额恢复至 > emergencyFloor 且经运营确认后手动恢复接单 |

## 6. 边界条件

| 场景 | 规则 |
|------|------|
| Δ = 0 | 不进入瀑布，仅 L1 抵扣后剩余输家筹码进入 LP 收益分配（按 `对赌池_规则设计.md` 既有规则） |
| L2 扣减时 LP 存量为 0 | 跳过 L2（不视为违规跳层），直接进入 L3；lpLossOffsetRemaining 不变化 |
| L2 扣减时全局池与比赛独立池仅一方有存量 | 全部由有存量一方承担；另一方 lpLossOffsetRemaining 不增加 |
| taxBuffer = 0 | 跳过 L3，直接进入 L4 |
| reserveBalance 单次扣减超过余额 | 扣至 0，剩余 Δ 进入"准备金已耗尽"异常流程（见 §7） |
| taxBuffer 因份额注入溢出 taxBufferCap | 溢出部分按 §4 优先级 3 进入 reserveBalance |
| reserveBalance 因份额注入超过初始 15,000,000 ODD | 允许；不回退至初始值，不触发新档位 |
| 同一笔 ReserveTapped 同时跨越多个 100,000 ODD 档位 | 按实际跨越档位数触发相应次数阶梯告警，事件告警仅触发一次 |
| 熔断期间新用户下注请求 | 拒绝，返回 MARKET_CLOSED（与红灯统一口径） |
| 熔断期间已接注单 | 正常等待结算，不受熔断影响 |

## 7. 异常流程

| 异常 | 判定 | 处理 |
|------|------|------|
| 准备金已耗尽（L4 扣减后余额 = 0 且 Δ 仍 > 0） | 单次结算出现"四层全部耗尽仍欠赔付" | 结算终止；该市场进入"待人工介入"状态；运营 P0 告警；由 Admin 多签决定补仓或按失败处置 |
| addPlatformReserve 以外的外部 ODD 转账到 BettingPool | 余额增加但 platformReserve 不增加 | 视为"非法注入"，运营定期核对，使用 recoverStuckBalance 类管理员操作清退，不进入瀑布与告警体系；协议内自动记入 `reserveBalance` 的结算增量不属于本异常 |
| taxBuffer 减少但非来自 L3 扣减 | 违规 | 合约侧锁定；产品层视为"状态异常"，阻塞新结算直至复核 |
| lpLossOffsetRemaining 负数 | 违规 | 同上 |
| 告警通道故障 | 事件/阶梯告警未送达 | 运营每日对账 reserveBalance 日终快照；恢复后补推历史告警 |

## 8. 当前限制

1. **准备金初始注入依赖 Admin 多签单点**：首次 15,000,000 ODD 必须通过 `addPlatformReserve` 一次性注入；在该动作完成前，所有 L4 场景均等价于 §7 "准备金已耗尽"。
2. **taxBufferCap 暂锁 500,000 ODD**：未经市场真实消耗数据验证，6/1 审计前按现值执行；不支持运营端动态调整。
3. **emergencyFloor 暂锁 100,000 ODD**：同上。
4. **阶梯告警不支持跨场聚合**：若多场同时扣减准备金，运营端会收到多次独立告警，无合并视图。
5. **lpLossOffsetRemaining 不是 LP 应收账款**：当前实现只将后续派奖税缓冲份额优先用于冲抵该指标，不把 ODD 转回 LiquidityPool，也不恢复已扣减仓位；已赎回仓位不存在追溯回补。
6. **税收冲抵与缓冲填充可能长期断流**：v2 起冲抵和填充来源为胜单在 `settle` 时锁定给对赌池的派奖份额（默认 1pp，每笔胜注 `claimPayout` 触发）；若平台流水或胜注频次长期低迷，该份额可能接近 0；准备金单调递减不可自动恢复。运营端按月对账；连续 30 天注入 < 10,000 ODD 时触发运营复评，由产品决定是否人工注资或调整规则。
7. **v2 冷启动期 taxBuffer 填充慢**：默认对赌池份额 1pp 相对 v1 的 4pp 注入速率大幅降低；taxBufferCap 500k ODD 冷启动期可能长期未填满；L3 层级在该期间等效"有缓冲容量但少或空"。运营侧按首两周内测数据复评 cap；不阻塞 L4 兜底。

## 9. 人工介入点

| 介入点 | 触发条件 | 操作主体 | 动作 |
|--------|---------|---------|------|
| 准备金充值 | 阶梯告警累积到运营预判阈值；或准备金耗尽异常 | Admin 多签 | 调用 addPlatformReserve 注入指定数量 ODD；不影响协议内自动入账逻辑 |
| 熔断解除 | reserveBalance 恢复至 > emergencyFloor | 运营值班 | 确认链上余额无误后，手动恢复接单 |
| taxBufferCap / emergencyFloor 调整 | 6/1 审计后或市场消耗速率异常 | 产品 + 运营联审 | 通过合约升级调整，不支持热更新 |
| 准备金耗尽时的市场处置 | 出现 §7 "四层全部耗尽" | Admin 多签 + 运营 | 决定补仓继续结算，或按预定失败处置（用户按比例赔付/退款） |
| 非法注入清退 | 非 addPlatformReserve 入账 | Admin 多签 | 管理员操作清退多余余额 |

## 10. 不适用范围（再次明示）

- **代码实现**：本文档不定义合约函数签名、事件结构、存储槽位、升级脚本；实现需求需另行归档，当前仓库未收录。
- **链下监控架构**：告警通道的具体实现（订阅方式、去重逻辑、通道降级）由后端自行设计。
- **做市功能细则**：L2 扣减时 LP 仓位按存量比例分摊的具体算法、P&L 记账单位换算，属 `做市功能` 范围。
- **代币税收触发逻辑**：派奖税何时扣、如何计算 5pp 分配，属 `代币_规则设计.md §3` 范围；下注税 1% 不注入本瀑布。
