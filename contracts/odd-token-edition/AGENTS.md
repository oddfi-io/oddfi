# AGENTS.md

本文件为所有协助此项目开发的 SOLIDITY智能合约项目 提供统一规则。

## 1. 开始工作前必须阅读文档

修改代码前，至少先阅读：
1. `docs/README.md`
2. `docs/progress/` 当前开发现状
3. 与任务相关的 `docs/architecture/` 文档
4. 任务已有实施清单或开发文档 `docs/development/` 文档

必须严格区分 `architecture/`（架构设计）与 `progress/`（当前真实实现状态，按模块区分）。

- **已有**设计文档与当前代码不一致 → 以代码和 `progress/` 为准，由人工决定是否回写设计文档
- **新的变更** → 必须先更新设计文档再改代码（见第4节）

功能开发须在 `development/` 找到对应文档才能开始，以下操作豁免：
- Bug 修复（hotfix）、Typo / 格式修正
- 测试用例补充（不涉及业务逻辑变更）
- 纯重构（不改变外部行为）
- 项目初始化 / bootstrap 阶段的基础骨架搭建

豁免操作完成后仍需同步更新 `docs/progress/`。

## 2. docs 目录与协作规则

- `docs/` 根目录只允许保留 `README.md`，新文档必须归入子目录：`architecture/` | `development/` | `progress/` | `research/` | `deployment/` | `testing/` | `product/`
- 新建 docs 子目录须先获得用户许可
- 文档、注释、变更说明、PR 说明需要完整记录变更
- 做出结构性调整时必须留下文档记录；发现文档与代码长期偏离时，必须至少修正一侧

## 3. 编码红线

- 以当前仓库真实技术栈为准，功能开发以 DDD 为准（见 `docs/architecture/solidity-ddd-mapping.md`）
- 使用 `require`/`revert`/自定义 `error` 处理错误，禁止 `assert` 做业务校验

### 智能合约安全红线

以下为强制要求，违反即视为不可验收：

**编码规范：**
- 外部调用必须遵循 Checks-Effects-Interactions 模式；涉及资产转移的函数必须添加 `nonReentrant`
- 禁止循环中无上限的外部调用或状态写入；数组遍历必须有长度上限
- `unchecked` 块必须附带注释说明安全性理由（Solidity >=0.8 依赖内置溢出检查）
- 所有管理函数必须有 `onlyOwner`/`onlyRole` 等访问控制，禁止裸露管理接口
- 禁止 `tx.origin` 验证身份，必须用 `msg.sender`
- 禁止 `selfdestruct`（除非架构文档明确说明并经安全评审）
- `receive()`/`fallback()` 必须有明确处理逻辑或显式 revert
- 多签由钱包侧实现（如 Safe），合约内禁止实现多签逻辑，只需校验 `msg.sender` 权限

**安全审计工具（提交前必须通过）：**
- **Slither**：所有 High/Medium 告警必须修复或标注豁免理由
- **Foundry fuzz testing**：关键业务函数必须编写 fuzz 测试
- 鼓励但不强制使用 Mythril 进行符号执行分析

**Gas 优化底线：**
- 禁止在链上存储可在链下计算的数据
- 频繁读取的 storage 变量应缓存到 memory
- event 应优先于 storage 用于记录历史数据

## 4. 文档同步规则

**强制规则：若任务改变了实现状态却没有更新对应文档，则任务不应视为完成。**

**架构变化（先改文档再改代码）：** 域边界、API 合约、核心交互流程、安全模型、部署架构发生变化时，必须先更新 `docs/architecture/`。

**实现进度变化：** 功能完成、开发中、范围调整/回退/延后、占位实现变为可用实现 → 任务结束前必须同步更新 `docs/progress/`，文档按功能模块命名。

**过程归档：** 调研结论 → `research/`；开发文档与实施清单 → `development/`；部署说明 → `deployment/`；测试与审计报告 → `testing/`。

## 5. 开发与验收流程

- 变更顺序：存储/数据层 → 基础设施 → 业务逻辑 → 接口
- 功能开发需有开发文档（豁免见第1节）
- Bug 修复至少 2 次复现验证，保留输入、输出、期望结果；首次修复失败后先补 Research 再继续
- 调研前先检查 `docs/research/` 是否已有相关材料，新调研必须归档到 `docs/research/`
- 复杂功能或高风险改动至少 3 轮验证后再验收，验收须做对抗性测试（定义见下方）
- 开发完成后必须重新跑构建、测试、类型检查

### 对抗性测试定义

从"攻击者/挑刺者"视角主动寻找漏洞：

**代码层面：** 边界值与异常输入（零值、最大值、溢出）、权限越权、重入攻击、Gas 极端场景（循环上限、大数组）、前置/后置条件违反。

**文档层面：** 规则矛盾或歧义、流程死锁或无限循环、模拟 Agent 严格执行验证工作流可达性、术语一致性。

## 6. 需求变更与开发工作流

对于新增或变更的需求，严格遵循以下工作流。**通用规则：每步评审/验证最多 3 轮迭代，超过须请求人工介入。**

1. **需求调研**：深入调研业务逻辑、技术可行性及影响范围
2. **调研评审**：评审调研结果，发现问题须重新调研
3. **架构与设计文档更新**：调研通过后更新 `docs/architecture/` 及相关设计文档
4. **文档评审**：评审架构与设计文档的正确性、完整性与一致性
5. **产品文档验证**：如需修改产品文档，修改后须经对抗性测试验证（见第5节）
6. **开发文档设计**：产品文档验证通过后编写开发实现文档，归档到 `docs/development/`
7. **开发文档评审**：多轮 Review，修正逻辑漏洞与规范不符之处
8. **任务分配与开发**：开发文档定稿后方可分配 Sub-agents 进入编码
9. **遵循开发规则**：严格遵循本文件定义的所有规则
